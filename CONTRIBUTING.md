# Contributing — EV-ServiceDesk

## Ветвление (git-flow)

| Ветка | Откуда | Куда мержится | Назначение |
|---|---|---|---|
| `main` | — | — | Прод-готовый код, защищена |
| `develop` | `main` | — | Интеграционная ветка, защищена, ветка по умолчанию |
| `feature/<issue>-<slug>` | `develop` | `develop` | Новая функциональность |
| `release/<version>` | `develop` | `main` + `develop` | Стабилизация перед релизом |
| `hotfix/<issue>-<slug>` | `main` | `main` + `develop` | Срочные прод-фиксы |

Примеры: `feature/23-auth-sms-login`, `hotfix/41-ticket-sla-bug`.

`develop` — ветка по умолчанию (с 2026-10-10): в неё по умолчанию открываются PR, а `Closes #<issue>`
закрывает issue при merge в `develop`. `main` получает изменения только через `release/*` и `hotfix/*`.

Номер `<issue>` — обязателен (см. трекер задач, шаг 6) — это и есть
привязка веток к задачам из чек-листа.

## Процесс Pull Request

1. Открыть PR в `develop` (или в `main` — только для `hotfix/*` и `release/*`).
2. Заполнить шаблон PR (описание, `Closes #<issue>`, чек-лист самопроверки).
3. Дождаться зелёного `ci-gate` — единственной обязательной проверки (workflow `ci.yml`,
   запускается на каждом PR, ADR 0008). Ветка PR должна быть актуальной относительно базовой
   (`gh pr update-branch`).
4. Squash-merge — история `develop`/`main` линейная. Ветка на GitHub удаляется автоматически
   (`delete_branch_on_merge`). Локально после squash-merge `git branch -d` откажет — Git не видит
   commit-предка; удалять через `git branch -D feature/...`.

## Защита веток `main` и `develop`

Включена 2026-10-10 (`scripts/setup-branch-protection.sh`), проверено отказом прямого push:

- изменения только через PR, прямой push запрещён;
- обязательная проверка `ci-gate` (только от GitHub Actions), ветка PR — актуальная;
- линейная история, force-push и удаление ветки запрещены;
- правила распространяются и на администратора (`enforce_admins`) — обойти их нельзя никому.

## Трекер задач

**GitHub Issues** — не Jira/Trello: бесплатно, уже часть репозитория, привязка
веток к задачам «из коробки» через номер issue (см. соглашение об именовании
веток выше и `Closes #<issue>` в шаблоне PR). Шаблоны — `.github/ISSUE_TEMPLATE/`
(баг / функциональность), у каждого — поле «Глава чек-листа» для трассировки
к мастер-чек-листу.

## Код-ревью — текущая политика

Команда — один разработчик (+ AI-ассистент). GitHub не позволяет одобрить собственный PR, поэтому
**обязательного approve нет** (`required_approving_review_count: 0`). Это осознанное ограничение, а не
скрытый компромисс: ревью вторым человеком сейчас не выполняется.

Что гарантируется автоматически: прямой push в `main`/`develop` невозможен ни для кого, мерж без
зелёного `ci-gate` заблокирован. Что остаётся на совести автора: самопроверка по чек-листу шаблона PR.
Прод-деплой дополнительно требует одобрения в GitHub Environment `production` (см. `docs/ENVIRONMENTS.md`).

**Когда появится второй человек:** `REVIEWS=1 ./scripts/setup-branch-protection.sh` — включит
обязательный approve для `main` и `develop`.

## CODEOWNERS

Фиксирует владение кодом по путям с первого дня. При соло-разработке не
блокирует ничего (review не required), но когда команда вырастет — новые
пути сразу получат нужного ревьюера без дополнительной настройки.
