# Contributing — EV-ServiceDesk

## Ветвление (git-flow)

| Ветка | Откуда | Куда мержится | Назначение |
|---|---|---|---|
| `main` | — | — | Прод-готовый код, защищена |
| `develop` | `main` | — | Интеграционная ветка, защищена |
| `feature/<issue>-<slug>` | `develop` | `develop` | Новая функциональность |
| `release/<version>` | `develop` | `main` + `develop` | Стабилизация перед релизом |
| `hotfix/<issue>-<slug>` | `main` | `main` + `develop` | Срочные прод-фиксы |

Примеры: `feature/23-auth-sms-login`, `hotfix/41-ticket-sla-bug`.

Номер `<issue>` — обязателен (см. трекер задач, шаг 6) — это и есть
привязка веток к задачам из чек-листа.

## Процесс Pull Request

1. Открыть PR в `develop` (или в `main` — только для `hotfix/*`).
2. Заполнить шаблон PR (описание, `Closes #<issue>`, чек-лист самопроверки).
3. Дождаться зелёного CI (Глава 4, шаг 4) — обязательный статус-чек,
   мерж технически заблокирован до зелёного после включения branch protection.
4. Squash-merge — история `develop`/`main` остаётся линейной и читаемой.
   ⚠️ После squash-merge Git считает feature-ветку «не смерженной»
   (`git branch -d` откажет) — это ожидаемо, squash не создаёт commit-предка.
   Удалять через `git branch -D feature/...` — проверено на реальном цикле.

## Трекер задач

**GitHub Issues** — не Jira/Trello: бесплатно, уже часть репозитория, привязка
веток к задачам «из коробки» через номер issue (см. соглашение об именовании
веток выше и `Closes #<issue>` в шаблоне PR). Шаблоны — `.github/ISSUE_TEMPLATE/`
(баг / функциональность), у каждого — поле «Глава чек-листа» для трассировки
к мастер-чек-листу.

## Код-ревью — текущая политика (честно, не тихий компромисс)

Команда сейчас — один разработчик (+ Claude как техническая пара).
Обязательный review от второго человека на каждый PR при таком составе
невозможен технически (GitHub не даёт approve собственного PR по
умолчанию), поэтому:

- **Сейчас:** живой review не required — но самопроверка по чек-листу
  PR-шаблона обязательна, а зелёный CI — единственный автоматический гейт
  перед мержем. Прямой push в `main`/`develop` запрещён branch protection
  в любом случае — только через PR.
- **Когда появится второй человек** (сокурсник, сотрудник
  ЕТСавтоГомель, руководитель на код-ревью): включить
  `required_approving_review_count: 1` в branch protection для `main` и
  `develop` — правка одной строки в `scripts/setup-branch-protection.sh`,
  инфраструктура уже готова.

## CODEOWNERS

Фиксирует владение кодом по путям с первого дня. При соло-разработке не
блокирует ничего (review не required), но когда команда вырастет — новые
пути сразу получат нужного ревьюера без дополнительной настройки.
