**Тема дипломного проекта: **«Service Desk система с модулем «Цифровой паспорт автомобиля» для технического сопровождения владельцев электромобилей после русификации» (сокращённое название — «EV-ServiceDesk»).

Ниже приведено техническое задание на разработку системы, структурированное по разделам и логическим блокам.

**1. ОБЩИЕ СВЕДЕНИЯ**

**Наименование системы: **Service Desk система с модулем «Цифровой паспорт автомобиля» для технического сопровождения владельцев электромобилей после русификации / технического обслуживания («EV-ServiceDesk»).

**Область применения: **автоматизация процессов постпродажного сопровождения, технической поддержки и информирования клиентов компании ООО «ЕТСавтоГомель» — владельцев электромобилей (Zeekr, BYD, Li Auto и др.), прошедших русификацию мультимедийной системы и/или техническое обслуживание.

**Основание для разработки: **задание на дипломное проектирование по специальности «Программная инженерия».

**Заказчик и пользователи системы: **ООО «ЕТСавтоГомель» (заказчик и оператор системы); конечные пользователи — клиенты компании (владельцы автомобилей), инженеры технической поддержки, администратор сервиса.

**2. НАЗНАЧЕНИЕ И ЦЕЛИ СОЗДАНИЯ СИСТЕМЫ**

**Назначение: **приложение устанавливается клиенту сотрудником ООО «ЕТСавтоГомель» после русификации или технического обслуживания автомобиля. Клиент получает персональный «цифровой паспорт» автомобиля с наглядной диагностикой состояния агрегатов, историей обслуживания, обучающими материалами и каналом связи с сервисом.

**Цели разработки:**

- снижение времени первичного ответа на обращение клиента (целевой показатель — до 15 минут);

- повышение прозрачности технического состояния автомобиля для владельца;

- формирование единой базы знаний по типовым сбоям ПО (баги прошивок, слетевшие приложения, проблемы связи eSIM) и по регламентам ТО (масла, фильтры, фреон);

- увеличение повторных обращений в сервис за счёт напоминаний о плановой замене расходников и push-уведомлений об акциях;

- снижение количества «пустых» звонков в поддержку за счёт раздела самопомощи (инструкции, перезагрузка, пошаговые планы устранения неполадок).

**3. ФУНКЦИОНАЛЬНАЯ КОНЦЕПЦИЯ (ОБЗОР ПО БЛОКАМ)**

Функциональность системы разбита на 4 логических блока:

**БЛОК 1. Цифровой паспорт автомобиля и умная диагностика** — ядро клиентского приложения.

- Регистрация клиента по номеру телефона (SMS-код) и привязка автомобиля по **VIN-номеру** — данные марки, модели и комплектации подтягиваются автоматически.

- Карточка автомобиля: марка, модель, пробег, список выполненных работ с датами и пробегом на момент выполнения.

- Интерактивная схема автомобиля с кликабельными зонами-агрегатами: при тапе открывается статус, дата/пробег последней замены, остаток ресурса.

- Базовый набор агрегатов на схеме: масло в двигателе, масляный фильтр, воздушный фильтр, салонный фильтр, масло в редукторе, фреон кондиционера — набор расширяем через админ-панель.

- Статус каждого агрегата отображается по принципу «светофора» (см. раздел 5).

**БЛОК 2. Обучение, поддержка и устранение неисправностей** — раздел самопомощи клиента.

- Персональный раздел «Обучение» для каждой модели авто: инструкции по мультимедиа и прошивке после русификации.

- Туториалы по типовым ошибкам: пошаговый план действий (например, «завис экран → мягкая перезагрузка → жёсткая перезагрузка → тикет в поддержку»).

- Создание тикета прямо из карточки ошибки с автоматическим прикреплением модели авто, версии прошивки и фото/видео.

- Чат с инженером поддержки и история всех обращений клиента.

**БЛОК 3. Уведомления, новости и вовлечение клиента** — удержание клиента и допродажа услуг ТО.

- Push-уведомления о выходе новой прошивки для конкретной модели/версии авто клиента.

- Уведомления о приближении срока замены агрегата (за N дней/км до порога «требуется замена»).

- Новости компании и акции, таргетированные по модели авто и истории обслуживания.

**БЛОК 4. Рабочее место инженера и CRM/аналитика** — сторона организации.

- Канбан-доска тикетов с приоритизацией по SLA и категории обращения.

- База знаний с готовыми инструкциями для быстрой отправки клиенту.

- Админ-панель: конструктор регламентов ТО, публикация новостей/прошивок, аналитика по проблемным моделям и среднему времени закрытия тикета.

**4. ТРЕБОВАНИЯ К ФУНКЦИОНАЛЬНОЙ СТРУКТУРЕ**

**4.1. Роли пользователей: **Клиент, Инженер поддержки (Оператор), Администратор.

**4.2. Модуль «Личный кабинет клиента / Цифровой паспорт автомобиля»:**

- регистрация/авторизация по номеру телефона (SMS-код), привязка Telegram;

- добавление автомобиля по VIN-номеру, поддержка нескольких авто на аккаунт;

- отображение марки, модели, пробега и полной истории выполненных работ;

- интерактивная схема автомобиля со статусами агрегатов «заменено / скоро менять / требуется замена»;

- раздел «Обучение» под конкретную модель и версию прошивки;

- раздел «Устранение неполадок» с деревом решений и переходом в тикет;

- создание тикета (категории: «Навигация», «Звук», «SIM/связь», «Сбой приложения», «Агрегаты/ТО») с прикреплением фото/видео;

- центр уведомлений: прошивки, регламент ТО, новости и акции.

**4.3. Модуль «Рабочее место инженера поддержки»:**

- канбан-доска активных тикетов с фильтрацией по SLA и категории;

- изменение статуса заявки: «В работе», «Ожидает ответа вендора», «Решено»;

- быстрый доступ к базе знаний для отправки клиенту готовой инструкции;

- просмотр карточки автомобиля клиента (история ТО, статусы агрегатов) из тикета.

**4.4. Модуль «Администрирование, база знаний и аналитика»:**

- конструктор статей базы знаний (гайды, файлы прошивок, видео);

- конструктор регламентов ТО: интервалы замены агрегатов по моделям авто;

- публикация уведомлений о прошивках, новостях и акциях с таргетингом;

- аналитика: среднее время закрытия тикета, проблемные модели, конверсия в запись на ТО.

**5. ЛОГИКА СТАТУСОВ АГРЕГАТОВ («СВЕТОФОР»)**

Статус агрегата рассчитывается автоматически по пробегу/дате последней замены и регламентному интервалу, заданному администратором для модели авто:

| **Агрегат** | **Индикатор** | **Условие статуса** |
| --- | --- | --- |
| Масло в двигателе | 🟢 Заменено / 🟡 Скоро менять / 🔴 Требуется замена | 🟢 — до 70% интервала; 🟡 — 70–100%; 🔴 — интервал превышен |
| Масляный фильтр | 🟢 / 🟡 / 🔴 | Привязан к интервалу замены масла |
| Воздушный фильтр | 🟢 / 🟡 / 🔴 | По регламенту модели |
| Салонный фильтр | 🟢 / 🟡 / 🔴 | По регламенту модели |
| Масло в редукторе | 🟢 / 🟡 / 🔴 | По регламенту модели |
| Фреон кондиционера | 🟢 / 🟡 / 🔴 | По регламенту модели / году последней заправки |

Пороговые значения интервалов настраиваются в админ-панели и не «зашиты» в код — это позволяет ООО «ЕТСавтоГомель» самостоятельно актуализировать регламенты без привлечения разработчика.

**6. ТРЕБОВАНИЯ К ЭРГОНОМИКЕ И ТЕХНИЧЕСКОЙ ЭСТЕТИКЕ**

- **Адаптивность: **личный кабинет клиента — mobile-first; рабочее место инженера — под десктоп (Full HD).

- **Доступность: **контрастность текста не менее 4.5:1 (WCAG); статус агрегата дублируется иконкой/подписью, а не только цветом.

- **Тёмная тема **для инженеров, работающих в ночные смены.

- **Правило 3-х кликов: **создание тикета, просмотр статуса агрегата, переход к обучающему материалу — не более 3 тапов из главного экрана.

- **Минимизация ввода: **модель авто, симптом ошибки и категория тикета — через выпадающие списки, а не свободный текст.

- **Интерактивная схема **остаётся читаемой от 360 px, зона тапа по агрегату — не менее 44×44 px.

**7. ТРЕБОВАНИЯ К НАДЁЖНОСТИ И БЕЗОПАСНОСТИ**

- Время доступности системы — не менее 99.5% (Up-time).

- Пароли/коды доступа хранятся в хэшированном виде (bcrypt/argon2); авторизация — по SMS-коду с ограничением попыток.

- Разграничение прав доступа на уровне API — ролевая модель RBAC (Клиент/Инженер/Администратор).

- VIN и номер телефона — чувствительные данные; обработка соответствует законодательству о персональных данных.

- Уведомления о прошивке носят информационный характер — приложение не выполняет удалённую перепрошивку автомобиля.

**8. ТЕХНИЧЕСКИЙ СТЕК**

- **Мобильное приложение клиента: **Flutter или React Native (iOS/Android), push-уведомления — Firebase Cloud Messaging.

- **Веб-интерфейс инженера/администратора: **React.js / Vue.js + Tailwind CSS или Bootstrap.

- **Backend: **Python (FastAPI/Django) или Node.js; REST API.

- **База данных: **PostgreSQL / MySQL.

- **Хранилище файлов: **S3-совместимое хранилище (фото/видео к тикетам, файлы прошивок).

- **Интеграции: **SMS-провайдер, опционально VIN-декодер API, Telegram Bot API.

**9. ВИЗУАЛИЗАЦИЯ И РОЛИ**

Проект строится на 3 типах интерфейсов:

- **Мобильное приложение клиента: **переключатель автомобилей и интерактивная схема агрегатов на главном экране; нижняя навигация — «Авто» / «Обучение» / «Поддержка» / «Новости».

- **Веб-кабинет инженера: **канбан-доска тикетов слева, справа — карточка обращения с контекстом автомобиля клиента и быстрыми ответами из базы знаний.

- **Админ-панель: **конструктор регламентов ТО, конструктор статей базы знаний, лента публикаций (прошивки/новости/акции), дашборд аналитики.

**10. СОСТАВ И СОДЕРЖАНИЕ РАБОТ ПО РАЗРАБОТКЕ**

- **Анализ и проектирование: **сбор требований ООО «ЕТСавтоГомель», UML-диаграммы (Use Case, Class, Sequence), проектирование схемы БД.

- **Эргономическое проектирование: **прототипы в Figma (в т.ч. интерактивной схемы авто и дерева решений по ошибкам), тестирование User Flow.

- **Разработка программного кода: **серверная часть, мобильное приложение клиента, веб-интерфейсы инженера и администратора, интеграция push-уведомлений.

- **Тестирование и внедрение: **функциональное и UI/UX-тестирование, развёртывание на сервере, составление отчёта.

**11. ПОРЯДОК КОНТРОЛЯ И ПРИЁМКИ**

Приёмка осуществляется на основании демонстрации выполнения функциональных требований: регистрация клиента по VIN, корректный расчёт статусов агрегатов, создание и обработка тикета от клиента до закрытия инженером, публикация и получение push-уведомления, — а также предоставления исходного кода вместе с пояснительной запиской диплома.
