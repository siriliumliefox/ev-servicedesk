# 0031. Повтор создания тикета и сообщения чата: ключ `client_request_id` черновика

**Статус:** Принято, 2026-10-19 (Issue #111, дефект X1 исследовательского тестирования главы 23, S3;
fix-PR до бета-пилота по ADR 0029 п. 4; решение — рекомендация агента, принята по правилу владельца
2026-10-12)

## Контекст
Исследовательское тестирование X1 (глава 23): клиент пишет в чат обращения, связь с сервером
пропадает (backend приостановлен), через 20 с приложение показывает «Нет подключения к интернету»,
текст остаётся в поле, клиент отправляет ещё раз. Когда связь восстанавливается, сервер
обрабатывает и запросы, на которые клиент получил тайм-аут, — одно сообщение появляется в чате 2–3
раза у клиента и у инженера. То же возможно при создании обращения. Факты:
- `POST /tickets` и `POST /tickets/{id}/messages` (ADR 0017) каждый раз создают новую запись;
- тайм-аут мобильного клиента — 20 с (ADR 0022), после него запрос мог дойти до сервера; веб
  кабинета инженера повторяет отправку тем же текстом из поля или кнопкой быстрого ответа;
- сообщение пишется под блокировкой строки тикета (`FOR UPDATE`, ADR 0017 п. 8), тикет — под
  `FOR SHARE` авто (п. 6): одновременные создания тикетов на одно авто не упорядочены;
- вложения привязываются один раз: после commit загрузка удаляется из `uploads/` (ADR 0017 п. 10),
  повтор с теми же вложениями получил бы 422 ATTACHMENT_NOT_FOUND;
- лимиты (10 тикетов в час, 30 сообщений в минуту) считают созданные объекты (ADR 0017 пп. 7–8).

## Варианты
- **Где ключ:** заголовок `Idempotency-Key` с кэшем ответа в Redis / поле `client_request_id` в теле
  и колонка с UNIQUE в БД / без ключа — сервер ищет «такой же текст за последние N секунд».
- **Ответ на повтор:** 201 с записанным (как исходный ответ) / 200 / 409 со ссылкой на запись.
- **Тот же ключ, другое содержимое:** вернуть записанное / 422.
- **Область ключа:** пользователь / авто (тикет) и тикет + автор (сообщение).
- **Одновременные повторы:** advisory lock по ключу / существующие блокировки и UNIQUE.

## Решение
1. **Ключ — поле `client_request_id`** (UUID, необязательное) в `TicketCreateRequest` и
   `TicketMessageCreateRequest`; хранится в `ticket.client_request_id` и
   `ticket_message.client_request_id` (миграция 0018). Кэш ответа в Redis не нужен: ответ строится из
   записи, а UNIQUE в БД держит гарантию и после перезапуска Redis. Поиск похожего текста отвергнут:
   два одинаковых коротких ответа («Спасибо») — законный случай.
2. **Область ключа = UNIQUE:** тикет — `(vehicle_id, client_request_id)` (владелец авто неизменяем,
   ADR 0003); сообщение — `(ticket_id, author_id, client_request_id)`. NULL в UNIQUE не совпадают:
   без ключа — прежнее поведение.
3. **Повтор — 201 с записанным**, как ответ на исходный запрос: клиенту не нужно различать «создано»
   и «уже было». Без новой записи, без события `message.created`, без учёта в лимите; вложения
   повтора не привязываются (их привязал исходный). Повтор сообщения в решённый после записи тикет —
   тоже 201: сообщение уже было до решения. Видимость — как у чтения: тикет, который пользователь
   больше не видит, — 404 и для повтора.
4. **Тот же ключ, другое содержимое — 422 `CLIENT_REQUEST_ID_REUSED`** (поле `client_request_id`):
   сообщение — другой `body` (после обрезки пробелов), тикет — другие `category` или `description`.
   Клиент создаёт ключ заново, если черновик изменился, — до ошибки доходит только ошибка программы.
5. **Одновременные повторы** (сервер «отмёрз» и обрабатывает исходный запрос и повторы вместе):
   сначала поиск записи с ключом без блокировок; сообщение — повторный поиск под блокировкой строки
   тикета (второй ждёт commit первого и откатывает свою попытку, копии вложений удаляет
   `attachments.bind`); тикет — блокировки авто не упорядочивают, вставку второго останавливает
   UNIQUE ключа до commit первого, IntegrityError по этому ограничению → записанный тикет. Повтор,
   начавший работу до commit исходного, мог упасть на его следах (422 ATTACHMENT_NOT_FOUND —
   загрузку уже привязали): любая ошибка API при наличии записи с ключом заменяется ответом с ней.
6. **Клиенты.** Ключ — на черновик: тот же текст и те же вложения при повторе — тот же ключ,
   изменённый черновик — новый, после успеха — сброс. Мобильный клиент — `RetryKey` (UUID v4 из
   `Random.secure`, без новой зависимости) в форме обращения и в чате; кабинет инженера —
   `crypto.randomUUID()` в отправке ответа и быстрого ответа. Прототипы (Flutter и `web-shared`)
   повторяют поведение backend.
7. **Контракт 1.13.0** — аддитивно (`oasdiff` без ломающих): схема `ClientRequestId`, поле в двух
   запросах, правила повтора в описаниях `createTicket` и `createTicketMessage`.

## Последствия
- Повтор после обрыва связи не создаёт дубль ни сообщения, ни обращения; проверено тестами всех
  веток гонки (`backend/tests/api/test_ticket_retry.py`), одновременными повторами на MinIO
  (`test_ticket_concurrency.py`, 4 запроса с одним ключом и вложением → одна запись, одна копия
  вложения) и сценарием «ответ потерян → повтор» в мобильном клиенте и кабинете инженера.
- Клиент без ключа (старые сборки, скрипты E2E и k6) работает как прежде.
- Ключ не возвращается в ответах и событиях: сопоставлять отправку с событием `message.created`
  клиентам не нужно — сообщения в чате и так уникальны по `id`.
