# 0023. Схема агрегатов в мобильном клиенте: контур в SVG, замена и работа различаются в истории ТО, сверка статусов на 5 тестовых авто

**Статус:** Принято, 2026-10-12 (владелец проекта, Issue #79, grill-with-docs Q1–Q13; рекомендации
приняты по правилу владельца от 2026-10-12)

## Контекст
Глава 19 доводит интерактивную схему агрегатов клиента: SVG-схема с кликабельными зонами
(hit-area ≥ 44×44), статусы из Aggregates Service с цветовой индикацией, карточка агрегата
(боттом-шит) с деталями и историей замены, нейтральный fallback для агрегата без данных. Проверки —
ширины 360–430 px, сверка цветов и порогов главы 5 на 5 тестовых авто, доступность (статус не только
цветом); DoD — «схема протестирована на реальном устройстве и 2+ размерах экрана, статусы совпадают
с backend на 100% случаев». Факты на начало главы:
- схема уже есть (глава 7, ADR 0011; глава 18, ADR 0022): контур рисуется `CustomPaint`, зоны 48 px
  с Semantics «агрегат: статус», шит со статусом, остатком ресурса, последней заменой и историей;
- шит строит «Историю замен», выкачивая всю историю ТО и фильтруя по коду агрегата. В backend
  `maintenance_record` нет признака замены: `replaceAggregateStatus` пишет такую же строку, как
  `createMaintenanceRecord`. Различие «замена / работа по агрегату» есть в глоссарии (v1.4) и
  ADR 0016 п. 1, но не в данных;
- `GET /vehicles/{id}/aggregate-statuses` клиент читает без `page_size` (только первая страница);
- `flutter_svg` не подключён; симуляторы — iPhone 17e, 17, 18 Pro, Air; Android-устройства нет.

## Варианты
- **Контур:** SVG-ассет (`flutter_svg`) / оставить `CustomPaint`.
- **История агрегата:** признак замены в БД и контракте / переименовать раздел в «Историю работ»
  без различия.
- **Старые записи:** восстановить признак по `vehicle_aggregate_status.last_replaced_*` / считать
  все работами.
- **Сверка со backend:** только API-тест / API + UI в симуляторе + визуально на устройстве.

## Решение
1. **Контур — SVG (Q1).** `mobile/assets/scheme/car_top.svg` через `flutter_svg`: только кузов,
   колёса, стёкла. Цвета контура — из токенов темы (светлая и тёмная), не зашиты в SVG.
   Зоны остаются виджетами поверх контура — hit-area ≥ 44×44 и Semantics не зависят от рисунка.
2. **Замена и работа различаются (Q2, Q10–Q12).**
   - Миграция `0014`: `maintenance_record.kind` — PostgreSQL ENUM `maintenance_record_kind`
     (`replacement`, `work`; стабильный набор — нативный ENUM, как `app/models/enums.py`, ADR 0003),
     по умолчанию `work`; CHECK — замена только по агрегату. `replaceAggregateStatus` пишет
     `replacement`, `createMaintenanceRecord` — всегда `work` (запрос не меняется).
   - Существующие строки получают `work`: production-данных нет (сервер — глава 26), а
     сопоставление с `last_replaced_*` ненадёжно (замены задним числом, повторы). Принятое ограничение.
   - Контракт 1.9.0 (аддитивно): обязательное поле ответа `MaintenanceRecord.kind`, фильтр
     `aggregate_type_code` в `listMaintenanceRecords`; неизвестный код — `200` с пустым списком.
   - Шит: раздел «История агрегата» — замены и работы по агрегату одним списком, новые сверху,
     метка «Замена» / «Работа», по 20 записей с «Показать ещё»; «Последняя замена» — из статуса.
3. **Fallback (Q3).** `unknown` — серая зона «Нет данных» и нейтральный текст в шите, не ошибка.
   Агрегат без места на схеме — только в списке под схемой. Пустой ответ (у модели нет
   регламентов) — контур и «Регламент ТО для модели ещё не задан», не ошибка.
4. **Сбой загрузки (Q4).** Ошибка сети или сервера — экран ошибки с «Повторить»; зоны не
   перекрашиваются в «Нет данных».
5. **Обновление (Q5).** Pull-to-refresh на экране «Авто» и повторное чтение статусов при возврате
   приложения из фона. Статусы читаются одной страницей максимального размера (`page_size=100`).
6. **Ширины и доступность (Q6).** Виджет-тесты 360/375/390/414/430 px при масштабе текста 1.0 и 1.1:
   каждая зона нажимается, ≥ 44×44, зоны не перекрываются и не выходят за экран, слова подписей не рвутся.
   Подписи на схеме ограничены масштабом 1.1 — уточнено в ревью перед merge: при 1.3 самое длинное слово
   («кондиционера») не помещается в подпись и рвётся посреди слова; список под схемой и карточка агрегата
   масштабируются без ограничения. Проверки `labeledTapTargetGuideline`, `iOSTapTargetGuideline`,
   `androidTapTargetGuideline`, `textContrastGuideline`; скринридер читает «агрегат: статус словом» сверху вниз.
7. **5 тестовых авто (Q7).** Пороги по умолчанию 70/100. Авто: 1 — всё 🟢; 2 — 🟡 ровно на 70,0 %;
   3 — 🔴 на 100,1 %; 4 — новое без истории (`unknown`); 5 — смешанное: 69,9 % 🟢, 100,0 % 🟡,
   электромобиль с редуктором. `api_e2e` сравнивает ответ API с ожидаемой таблицей по сценариям
   главы 5; UI E2E в симуляторе — метку каждой зоны со статусом из API; на iPhone владелец сверяет
   экран с той же таблицей из отчёта главы.
8. **Размеры экрана для DoD (Q8).** Реальный iPhone 17 Air (владелец) и симуляторы iPhone 17e и
   iPhone 18 Pro; ширины 360–430 — виджет-тестами (Android-устройства нет, ADR 0022).
9. **Глоссарий (Q9).** «Работа по агрегату» — v1.11.
10. **Клиенты контракта (Q13).** `npm run gen:api`, Swagger; фикстуры web получают `kind` без новых
    экранов, метка в кабинете инженера — глава 21.

## Последствия
- Глава 19 меняет backend (миграция, ORM, DDL/ERD, контракт, тесты), а не только мобильный клиент.
- История ТО, созданная до миграции `0014`, показывается как работы — в т. ч. на локальных и
  тестовых стеках со старыми данными.
- Новая зависимость клиента — `flutter_svg`.
- Проверка на реальном iPhone — действие владельца; до неё глава — PARTIAL.
