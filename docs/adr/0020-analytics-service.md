# 0020. Analytics Service: витрина фактов (materialized view) с фоновым обновлением, период по Минску, формулы A-05/A-06, контракт 1.7.0

**Статус:** Принято, 2026-10-12 (владелец проекта, Issue #69, grill-with-docs Q1–Q14)

## Контекст
Глава 16 реализует тег Analytics контракта (OpenAPI 1.6.0) — три операции `/analytics/*`,
заложенные в главе 3 (A-05, A-06): время реакции и решения тикетов, проблемные модели, конверсия
в ТО. Данные уже есть в таблицах глав 12, 13, 15 (`ticket`, `maintenance_record`, `notification`,
`notification_recipient`, `notification_delivery`). Контракт и требования оставляли открытыми:
- шаг чек-листа «фоновые задачи предрасчёта тяжёлых агрегатов» — что и как предрасчитывать,
  если периоды и фильтры произвольные, а медиана не складывается из частичных итогов;
- часовой пояс периода `date_from`/`date_to` (даты без времени);
- как учитывать переоткрытые тикеты, тикеты без ответа, удалённые и переданные авто;
- единицу и окно воронки «уведомление → открытие push → работа ТО»; что делать с окном
  30 дней, которое у свежих уведомлений ещё не истекло;
- как сверить показатели «на staging», если staging — проверенный образ до главы 26 (ADR 0013).

## Варианты
- **Предрасчёт:** только расчёт при запросе + индексы / снимки стандартных периодов 7/30/90
  дней (два пути расчёта) / суточные итоги по (дата, модель, категория) — медиана не собирается /
  materialized view «факты» с фоновым обновлением.
- **Где обновлять:** в `notifications-worker` / отдельный `analytics-worker` / pg_cron.
- **Воронка уведомлений:** строгая (ТО только среди открывших) / среди всех получателей.
- **Незакрытое окно 30 дней:** считать как есть / исключать / отдельное поле в контракте.

## Решение
1. **Витрина фактов (Q1).** Три materialized view PostgreSQL (миграция `0013`):
   `analytics_ticket_fact` — строка на тикет (дата создания по Минску, модель, категория, часы до
   первичного ответа и до решения, «решён с просрочкой», есть ли работа ТО по тикету) и
   `analytics_reminder_fact` — строка на пару «напоминание о ТО, получатель» (дата по Минску,
   модель авто, открыто ли, была ли работа ТО в окне) и `analytics_vehicle_model_fact` — число
   активных авто модели. Все три операции агрегируют только витрину:
   путь расчёта один, работают любые периоды и фильтры, медиана — `percentile_cont(0.5)`.
   Тяжёлая часть (соединения тикет → авто → модель, поиск работ ТО и открытий) выполняется при
   обновлении, а не на каждом запросе. Цена — данные отстают на интервал обновления.
2. **Обновление (Q10, Q11).** Отдельный процесс `analytics-worker` (тот же образ,
   `python -m app.workers.analytics`; `--once` — разовое обновление для smoke и тестов) раз в
   `ANALYTICS_REFRESH_SECONDS` (300) и сразу при старте выполняет `REFRESH MATERIALIZED VIEW
   CONCURRENTLY` под advisory lock (две копии не обновляют одновременно; чтение не блокируется).
   В `notifications-worker` не встраивается — обновление не должно задерживать push (< 10 с).
   Миграция создаёт витрину заполненной (`WITH DATA`): API отвечает и до первого запуска worker.
3. **Свежесть (Q12, Q13).** Время последнего обновления — служебная таблица
   `analytics_refresh` (строка на витрину); в ответах всех трёх операций — обязательное
   `computed_at` (самое раннее из времён витрин, по которым построен ответ). Контракт 1.7.0 —
   аддитивно (ADR 0007). Принудительного пересчёта через API нет.
4. **Период (Q2).** `date_from`/`date_to` включительно, по Europe/Minsk; тикет и напоминание
   относятся к периоду по дате создания (глоссарий «Период аналитики»). `date_to` в будущем
   допустим. `422` — `date_from > date_to` или период длиннее 366 дней.
5. **A-05 (Q3).** `tickets_created` — тикеты периода; `tickets_resolved` — из них решённые сейчас
   (переоткрытый и не решённый снова — не решён); время решения — от `created_at` до последнего
   `resolved_at`, календарное, включая время после переоткрытия и «ожидает вендора» (глоссарий
   «Время решения тикета», как SLA, ADR 0017 п. 1); `tickets_resolved_overdue` — решённые с
   `resolved_at > sla_due_at`; первичный ответ — `first_response_at − created_at`, тикеты без
   ответа в среднее не входят; медиана — `percentile_cont(0.5)`; часы — с округлением до 0,01
   (десятичная арифметика БД, половина — от нуля), `null` при пустой выборке. Доли воронок —
   до 0,0001 так же.
6. **Проблемные модели (Q4).** Тикеты удалённых и переданных авто учитываются по модели авто;
   `vehicles_total` — активные авто модели на момент обновления витрины (не на конец периода);
   сортировка — `tickets_total` по убыванию, затем название модели (марка, модель), затем `id`;
   `by_category` — все пять категорий, в т. ч. с нулём; модели без тикетов за период не входят.
7. **Тикет → ТО (Q5).** `tickets_total` — тикеты периода (с фильтром модели);
   `tickets_with_maintenance` — те, к которым привязана хотя бы одна работа ТО
   (`maintenance_record.ticket_id`), без окна. Работа, записанная администратором (без тикета),
   в эту воронку не попадает.
8. **Напоминание → ТО (Q6, Q7).** Единица — пара «напоминание о ТО (`type = maintenance`),
   получатель»; два напоминания одному клиенту — два получения. `notifications_opened` — пары,
   где открыта хотя бы одна доставка на устройство этого получателя (`opened_at`).
   `recipients_with_maintenance` — среди всех получателей (не только открывших): любая работа ТО
   по авто напоминания с `performed_at` от даты напоминания по Минску до +30 дней включительно
   (глоссарий «Конверсия в ТО»). `rate` = с ТО / получатели, `null` при нуле. Окно у свежих
   напоминаний не исключается — ограничение описано в контракте.
9. **Контрольный набор (Q9).** Ручной расчёт — `docs/ANALYTICS_CONTROL.md` (утверждает
   владелец), данные и ожидаемые ответы — в коде; проверка дважды: тест в backend-ci и шаг smoke
   на образе `backend:staging` (загрузка набора, `analytics-worker --once`, сравнение ответов API).
10. **Производительность (Q14).** Тест в backend-ci на каждом PR: 10 000 тикетов за 2 года,
    20 моделей, 5 000 авто, 20 000 получений напоминаний, 30 000 доставок, 8 000 работ ТО
    (`generate_series`); каждая операция за 366 дней, с фильтрами и без — p95 из 20 вызовов
    < 300 мс; полное обновление витрины < 5 с.
11. **Клиенты (Q8).** web-admin остаётся на фикстурах — фикстуры приводятся к формулам и
    `computed_at`; подключение к API — глава 22.
12. **ПД.** В витрине только идентификаторы; анонимизация (глава 25) попадает в витрину при
    следующем обновлении. Права не меняются: все операции — только `admin`.

## Последствия
- Новый процесс `analytics-worker` в docker compose (профиль `full`) и в развёртывании главы 26;
  если он не работает, данные устаревают — это видно по `computed_at`.
- Схема витрины меняется только миграцией (DROP + CREATE); ORM-моделей у витрины нет —
  запросы строятся через `sqlalchemy.table()`.
- Глоссарий baseline v1.8: «Период аналитики», «Время решения тикета», «Проблемная модель»,
  «Конверсия в ТО».
