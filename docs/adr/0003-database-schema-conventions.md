# 0003. Соглашения схемы БД: ID, ENUM, soft-delete, ON DELETE, timestamps

**Статус:** Принято, 2026-10-08 (владелец проекта, Issue #8)

## Контекст
Аудит главы 2: DDL писался вручную, ORM и Alembic отсутствовали, все FK имели неявный
`NO ACTION`, `vehicle.vin` был глобально уникален (после soft-delete авто нельзя добавить снова),
`updated_at` не было нигде, таблица называлась зарезервированным словом `user`.

## Варианты
- **ID:** `BIGSERIAL` / `BIGINT IDENTITY` / UUID.
- **Наборы значений:** PostgreSQL ENUM / `VARCHAR + CHECK` / таблица-справочник.
- **Удаление авто:** `is_active` / `deleted_at`; VIN — глобально уникален / уникален среди активных.
- **Источник истины схемы:** ручной DDL / Alembic-миграции.

## Решение
1. **Источник истины** — `backend/app/models` + `backend/alembic/versions`. `docs/EV_ServiceDesk_Glava2_DDL.sql`
   и `docs/ERD_EV_ServiceDesk_Glava2.mermaid` генерируются (`scripts/export_ddl.py`, `scripts/export_erd.py`),
   синхронность проверяют тесты и backend-ci.
2. **ID** — `BIGINT GENERATED BY DEFAULT AS IDENTITY`: в OpenAPI уже `integer`, UUID не даёт выгоды в монолите.
3. **Наборы значений** — нативный PostgreSQL ENUM для стабильных наборов (`user_role`, `ticket_status`,
   `ticket_category`, `attachment_type`, `kb_article_type`, `notification_type`); расширяемый админом
   список агрегатов — справочник `aggregate_type` (A-07), seed — миграция `0002`.
4. **Таблица пользователей** — `app_user` (`user` — зарезервированное слово, `SELECT * FROM user` возвращает `current_user`).
5. **Soft-delete авто** — `vehicle.deleted_at`; частичный уникальный индекс
   `uq_vehicle_vin_active (vin) WHERE deleted_at IS NULL`. `vin`, `user_id`, `vehicle_model_id` неизменяемы
   (триггер `vehicle_guard`). Смена владельца = soft-delete старой записи + новая запись с тем же VIN:
   история ТО и тикеты привязаны к `vehicle.id` и не видны новому владельцу (ПД, N-07).
   В API `Vehicle.is_active` = `deleted_at IS NULL`.
6. **Пробег** — CHECK `mileage >= 0` + триггер `vehicle_guard` запрещает уменьшение (SQLSTATE 23514).
   Сервисный слой делает `UPDATE ... WHERE mileage <= :new RETURNING id`; 0 строк → `409`.
7. **ON DELETE задаётся явно у каждого FK** (тест `test_foreign_keys_have_explicit_on_delete`):
   - `RESTRICT` — бизнес-данные (авто, тикеты, история ТО, справочники): физическое удаление запрещено;
   - `CASCADE` — технические зависимые строки (`refresh_token`, `push_token`, `notification_recipient`,
     `notification_delivery`, `decision_tree_node`, кэш `vehicle_aggregate_status`);
   - `SET NULL` — необязательные ссылки на редактируемый контент (`ticket.source_article_id`,
     `ticket.source_node_id`, `maintenance_record.ticket_id`).
8. **Составные FK** для инвариантов «тот же родитель»: прошивка авто/статьи/уведомления —
   той же модели; вложение и его сообщение — одного тикета.
9. **Timestamps** — `created_at` во всех таблицах, `updated_at` в изменяемых; `TIMESTAMPTZ`,
   `DEFAULT now()`, `updated_at` обновляет ORM (`onupdate`).
10. **3НФ** — владелец и модель тикета берутся из неизменяемого `vehicle`, поэтому в `ticket` нет
    `client_id`/`vehicle_model_id`. `ticket.firmware_release_id` — снимок прошивки на момент создания
    (N-09): прошивка авто меняется, значит это самостоятельный факт, а не транзитивная зависимость.
    Единственное осознанное отступление от 1НФ — `decision_tree_node.options` (JSONB-массив переходов);
    целостность `next_node_id` проверяет `validateDecisionTree` (Глава 14).

## Последствия
- Любое изменение схемы — новая Alembic-ревизия + перегенерация DDL/ERD; применённые ревизии не правятся.
- Добавление значения ENUM — `ALTER TYPE ... ADD VALUE` в отдельной ревизии; удаление — через пересоздание типа.
- Исправление ошибочно введённого пробега вниз невозможно даже админу — требует отдельного
  аудируемого сценария (техдолг).
- `updated_at` не обновляется прямыми SQL-UPDATE в обход ORM.
- Полнота `next_node_id` и соответствие `source_node_id` статье `source_article_id` проверяются
  в сервисном слое (главы 13–14), не в БД.
