# 0019. Notifications Service: исходящая очередь в БД, снимок аудитории, напоминания о ТО за N км/дней, мягкий отзыв push-токенов

**Статус:** Принято, 2026-10-12 (владелец проекта, Issue #66, grill-with-docs Q1–Q26)

## Контекст
Глава 15 реализует тег Notifications контракта (OpenAPI 1.5.0) поверх таблиц главы 2
(`push_token`, `notification`, `notification_recipient`, `notification_delivery`, `firmware_release`)
и Aggregates Service (глава 12, ADR 0009). Контракт и требования оставляли открытыми:
- как ставить рассылку «в очередь» — в проекте нет ни планировщика, ни worker;
- что значит «таргетинг по версии» прошивки, если контракт таргетирует только по модели;
- порог N для напоминания «за N км/дней до порога «требуется замена»» (N-10; ADR 0009 —
  «отдельной настройкой»), повторы напоминаний;
- `notification_delivery → push_token ON DELETE CASCADE`: удаление токена стирает журнал доставок,
  на котором строится аналитика открываемости (глава 16);
- контракт пишет только `read_at`; `opened_at` записать нечем; ленты публикаций для admin нет
  (ADR 0012 п. 5); перед массовой рассылкой нельзя проверить аудиторию (U-45);
- push о сообщениях и статусах тикета (ADR 0017 п. 12);
- push на iOS идёт через APNs — нужен платный Apple Developer; staging-сервера нет до главы 26;
- передача push-токена и текста в FCM/APNs (США) — `PD_99Z_CHECKLIST.md` п. 12 не выполнен.

## Варианты
- **Очередь:** таблица `notification_delivery` + worker / `BackgroundTasks` FastAPI / arq или Celery.
- **Аудитория:** снимок при публикации / вычисление ленты на лету по модели авто.
- **Напоминание о ТО:** отдельная настройка «за N км / N дней» / переход в жёлтый статус.
- **Токены:** физическое удаление / мягкий отзыв с частичной уникальностью.
- **Проверка на устройстве:** iPhone (платный Apple Developer + Firebase) / Android / только фейк.

## Решение
1. **Устройство (Q1):** iPhone — владелец оформляет Apple Developer, APNs-ключ `.p8` и
   Firebase-проект; ключи вводит только владелец скриптом (как A1, ADR 0013). Пока аккаунта нет,
   код и автотесты делаются с фейковым отправщиком, глава — `PARTIAL` до E2E на устройстве.
2. **Исходящая очередь в БД (Q2):** строка `notification_delivery` на каждый активный токен
   получателя, `delivered_at IS NULL` — ждёт отправки. Отдельный процесс `notifications-worker` в
   том же образе забирает строки `FOR UPDATE SKIP LOCKED` (несколько реплик безопасны), будится
   Redis pub/sub после публикации и страхуется опросом. Отправка — через интерфейс `PushSender`:
   FCM HTTP v1 (`httpx` + OAuth сервисного аккаунта) и фейк для тестов, CI и локальной работы.
3. **Снимок аудитории (Q3, Q18):** при публикации создаются `notification_recipient` для всех
   подходящих клиентов (глоссарий «Аудитория»). В аудиторию входят только активные `client` с
   действующим согласием ПД и неудалёнными авто нужной модели (`null` — все модели); клиент с
   несколькими такими авто получает одно уведомление; клиент без токенов — запись в ленте без push.
4. **Прошивка по версии (Q4, Q25):** аудитория — владельцы авто модели, у которых текущая
   прошивка не указана или выпущена раньше нового релиза (`released_at`, при равенстве — `id`).
   `POST /firmware-releases` одной транзакцией создаёт релиз и уведомление с текстом сервера
   «Для {марка модель} доступна прошивка {версия}». Ручная публикация `firmware` через
   `POST /notifications` разрешена с тем же таргетингом. `GET /firmware-releases` клиенту отдаёт
   все релизы; `PATCH /vehicles/{id}/firmware` ничего не рассылает.
5. **Порог N (Q5):** в единственной записи порогов ADR 0009 — `reminder_before_km` (по умолчанию
   1000) и `reminder_before_days` (14), чтение и изменение — существующими
   `GET`/`PUT /aggregate-status-thresholds` (аддитивные поля). Напоминание «скоро замена» —
   `remaining_km ≤ N_km` или `remaining_days ≤ N_days`.
6. **Напоминания о ТО (Q20):** на цикл замены (от последней замены агрегата) — не более двух:
   «скоро замена» и «просрочено» (красный). Новая замена — новый цикл; правка регламента в том же
   цикле повторного «скоро» не даёт; агрегат без истории замен (`unknown`) напоминаний не получает.
   Учёт — таблица `maintenance_reminder` (авто, агрегат, вид, начало цикла, уведомление) с
   уникальностью. Каждое напоминание — уведомление `maintenance` на одного получателя с
   `vehicle_id` и `aggregate_type_id`. Тип `maintenance` — только системный: публикация
   администратором — `422 NOTIFICATION_TYPE_RESERVED` (Q19).
7. **Расписание (Q15):** worker раз в сутки в 10:00 `Europe/Minsk` запускает напоминания под
   advisory lock PostgreSQL (один экземпляр задачи); разовый запуск —
   `python -m app.workers.maintenance_reminders` (тесты, smoke, E2E).
8. **Мягкий отзыв токенов (Q8, Q12):** `push_token.revoked_at`; уникальность токена — только
   среди активных (частичный индекс). `DELETE /push-tokens/{token}`, ответ FCM `UNREGISTERED`,
   отзыв согласия ПД (все токены пользователя) — проставляют `revoked_at`; журнал доставок
   сохраняется. Регистрация своего токена — `201` и обновление `updated_at`; токен другого
   пользователя (сменили аккаунт на телефоне) — старая строка отзывается, создаётся новая, `201`.
9. **Повторы (Q13):** в `notification_delivery` — `attempts`, `next_attempt_at`, `failed_at`,
   `error_code`. 429/5xx/сеть — до 5 попыток с экспоненциальной паузой (10 с → ~10 мин);
   `UNREGISTERED`/`INVALID_ARGUMENT` — сразу `failed_at` и отзыв токена; исчерпаны попытки —
   `failed_at`.
10. **«Доставлено» (Q14):** `delivered_at` — FCM принял сообщение; показ на устройстве сервер не
    видит. Открытие push пишет приложение (п. 12). Порог «< 10 с» на устройстве — по отметкам
    времени вручную; в CI — от публикации до вызова отправщика.
11. **Содержимое push (Q16, Q11):** заголовок по типу — «Новая прошивка», «Пора на ТО», «Новости»,
    «Акция», «Поддержка»; текст — `message`; `data` — `notification_id`, `type` и при наличии
    `vehicle_id`/`aggregate_type_id`/`ticket_id`. ФИО, телефона и VIN в push нет. Текст — 1–1000
    символов после обрезки пробелов (`422`, проверка сервера, схема контракта не сужается — как
    ADR 0017 п. 13) (Q23).
12. **Контракт 1.6.0 — только аддитивно (Q17, Q26):**
    - `GET /notifications/published` (admin) — публикации `news`/`promo`/`firmware` (без
      напоминаний о ТО), фильтры `type`, `target_vehicle_model_id`, счётчики «аудитория /
      доставлено / ошибки / открыто / прочитано» — закрывает ADR 0012 п. 5;
    - `POST /notifications/audience-preview` (admin) — тело создания, ответ — число клиентов и
      устройств, без отправки (U-45; подтверждение — UI главы 22);
    - `POST /notifications/{id}/opened` (client) — `{token}`: `opened_at` доставки этого устройства
      и `read_at`, если ещё нет;
    - `Notification.vehicle_id`, `Notification.aggregate_type_id` — необязательные;
    - `AggregateStatusThresholds.reminder_before_km`, `reminder_before_days`.
13. **Push по тикетам (Q7, Q21):** сообщение персонала клиенту и смена статуса тикета → push
    «Новое сообщение по обращению №N» / «Статус обращения №N: {статус}» без содержимого сообщения.
    Без записи в ленте и журнале, текст в лог не пишется; сообщения клиента push не вызывают.
    Источник — события тикета в Redis (ADR 0017 п. 9), Tickets не меняется.
14. **Таргетинг новостей/акций (Q6)** — только по модели; «по истории обслуживания» (C-14) — бэклог.
15. **Не в v1 (Q10, Q24):** отзыв публикации, отложенная отправка, тихие часы, Telegram (C-15),
    фильтр статей по прошивке (глава 21), экраны центра уведомлений (главы 20, 22). Файлы прошивок
    к публикациям исключены совсем: уведомления информационные (ТЗ, раздел 7) — ADR 0018 п. 14.
16. **Термины (Q9):** глоссарий v1.7 — «Push-уведомление» (уточнение), «Уведомление»,
    «Публикация», «Аудитория», «Напоминание о ТО».
17. **ПД (Q11):** в FCM/APNs уходят токен и текст без ПД. Основание трансграничной передачи и текст
    согласия — до бета-пилота (главы 25/27); E2E на устройстве владельца с тестовыми данными этим
    не блокируется. Срок хранения журнала доставок — глава 25 (Q26).
18. **Проверка на устройстве (Q22):** Flutter только получает FCM-токен, показывает его на
    отладочном экране (`--dart-define=PUSH_DEBUG=true`, вне навигации) и принимает push; токен
    регистрирует `scripts/push_e2e.py` во входе тестовым клиентом в `backend:staging`, запущенный
    на Mac. `GoogleService-Info.plist` в git не попадает. Экраны уведомлений — глава 20.
19. **«На staging»** — как ADR 0013/0014/0016–0018: интеграционные тесты backend-ci на PostgreSQL
    (таргетинг X/Y, cron на «просроченных» агрегатах, очередь и повторы на фейке), smoke образа.
    Деплой — глава 26. DoD «≥ 3 сценария на реальном устройстве»: прошивка модели X (владелец Y
    не получает), напоминание о ТО, новость/акция с записью открытия и прочтения.

## Последствия
- Миграция `0012`: `push_token.revoked_at` и частичная уникальность, поля повторов в
  `notification_delivery`, `notification.vehicle_id`/`aggregate_type_id`, пороги N,
  `maintenance_reminder`; экспорт DDL/ERD.
- Новый процесс `notifications-worker` (compose, образ тот же); переменная
  `FCM_SERVICE_ACCOUNT_JSON` — секрет окружения, фейковый отправщик при пустом значении вне
  production.
- Аудитория не пересчитывается: клиент, купивший авто модели X после публикации, её не увидит.
- Отозванные токены копятся в `push_token`; очистка — вместе со сроками хранения (глава 25).
