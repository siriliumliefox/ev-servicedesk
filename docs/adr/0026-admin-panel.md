# 0026. Админ-панель: вход только администратора, HTTP-слой `web-shared`, пользователи и сброс пароля (контракт 1.11.0), подтверждение аудитории, E2E «регламент → статус клиента»

**Статус:** Принято, 2026-10-13 (Issue #90, grill-with-docs Q1–Q20, проведён агентом по поручению
владельца; рекомендации приняты по правилу владельца 2026-10-12 и подтверждены владельцем; Q20 — решение
владельца без рекомендации)

## Контекст
Глава 22 переводит админ-панель (`web-admin`) с фикстур главы 8 (ADR 0012) на реальный API:
авторизация администратора, конструктор регламентов ТО (CRUD, привязка к моделям), конструктор
статей базы знаний и публикация новостей/прошивок, дашборд аналитики, управление пользователями и
ролями. Проверки — «изменение регламента ТО отражается на статусах клиента без нового деплоя» и
ручная сверка дашборда; DoD — «протестирована ответственным сотрудником ЕТСавтоГомель, фидбек
внесён». Факты на начало главы:
- `web-admin` — прототип на `PrototypeRepository` (`main.tsx`), без входа, CSP, прокси `/v1` и
  переключателя прототип/API; экрана пользователей нет; 37 тестов Vitest;
- контракт 1.10.0 покрывает почти всё: тег Users (реализован в главе 17: список с фильтрами
  `role`/`is_active`/`search`, создание сотрудника `{phone, role, password}`, смена роли
  engineer↔admin, блокировка; client→staff — `409 ROLE_CHANGE_NOT_ALLOWED`, последний активный
  администратор — `409 LAST_ADMIN`), `audience-preview`, `notifications/published` со статистикой,
  версии статей, `assignTicket` и фильтр `assigned_engineer_id`;
- **смены и сброса пароля сотрудника нет** ни в API, ни в CLI — забытый пароль чинится только в БД;
- изменить себя (понизить, заблокировать) backend разрешает, если администратор не последний;
- тикеты заблокированного или пониженного инженера остаются за ним, переназначает администратор;
- статус «светофор» не хранится и не кэшируется — считается при каждом запросе из активных
  регламентов и порогов; мобильный клиент перечитывает статусы при открытии экрана, pull-to-refresh
  и возврате из фона;
- модели авто — только справочник из миграции (`0006`), создавать их через API нельзя;
- дерево решений опубликованной статьи не меняется (`409 ARTICLE_PUBLISHED`), загрузки медиа для
  статей нет (ADR 0018 — ссылки в Markdown);
- публикация необратима; уведомление о прошивке создаётся вместе с релизом;
- аналитика — из витрины, обновляемой раз в 300 с; контрольный набор
  `tests.support.analytics_control` (`load` / `verify`, период — март 2026);
- открытые замечания юзабилити по админке: U-05, U-40, U-41, U-42, U-43, U-44, U-45
  (U-03, U-04, U-08, U-09, U-17, U-18, U-46 исправлены в главе 9);
- HTTP-слой главы 21 (`ApiSession`, `HttpEngineerRepository`) лежит в `web-shared/src/data/http/`;
  `web-e2e.yml` и фильтр `ci.yml` знают только `web-engineer`.

## Варианты
- **Сброс пароля:** операция администратора в контракте / смена пароля самим сотрудником / оба /
  без изменений (CLI или БД).
- **Тикеты инженера при блокировке:** переназначение из карточки пользователя / отдельный экран
  тикетов в админ-панели / администратор работает в кабинете инженера.
- **Изменение себя:** запрет в UI / новое правило backend (контракт) / без ограничений.
- **Медиа статей:** ссылки в Markdown / загрузка через S3 (контракт).
- **Сверка дашборда:** только вручную / автоматическая сверка экрана с контрольным набором + вручную.
- **E2E админ-панели:** своя конфигурация и seed, общий `web-e2e.yml` по матрице приложений /
  отдельный workflow / только локально.

## Решение
1. **Вход (Q1).** Только `admin`: `staffLogin` по телефону и паролю, `ApiSession` из `web-shared`
   (ключ refresh — `ev-admin-refresh` в `sessionStorage`). Инженер и клиент получают отказ с
   выходом из сессии: «Инженер работает в кабинете инженера». API — тот же origin `/v1`, CSP в
   `<meta>` при сборке, прокси Vite — как ADR 0025 п. 2, 4. Без `VITE_API_BASE_URL` — режим
   прототипа (фикстуры, демо-панель) сохраняется.
2. **HTTP-слой (Q2).** Общие методы `HttpEngineerRepository` выносятся в `HttpCommonRepository`;
   новый `HttpAdminRepository` наследует его. `AdminRepository` дополняется операциями контракта:
   `previewNotificationAudience`, версии статей, Users, сброс пароля, `listTickets`/`assignTicket`
   для переназначения; `listPublishedNotifications` — с фильтрами, пагинацией и статистикой
   (комментарий «операции нет» устарел). `PrototypeRepository` реализует то же — тесты Vitest и
   демо работают на фикстурах. Тексты ошибок админских операций — в `errors.ts`, тест сверяет коды
   с контрактом.
3. **Тема (Q3).** «Как в системе / Светлая / Тёмная», по умолчанию «как в системе» (ADR 0025 п. 13).
4. **Пользователи (Q4, Q5).** Экран «Пользователи»: фильтр роли и «заблокирован», поиск по
   телефону, пагинация. Клиент — только блокировка/разблокировка; сотрудник — роль
   engineer↔admin, блокировка, сброс пароля; анонимизированный — «Данные удалены», без действий.
   Создать можно только сотрудника; пароль вводится или генерируется кнопкой (криптостойко, 16
   символов) и показывается один раз для передачи. Блокировка, смена роли и сброс пароля — с
   подтверждением; `409 LAST_ADMIN` — понятный текст.
5. **Сброс пароля (Q6) — контракт 1.11.0 (аддитивно).** `POST /users/{userId}/password`
   `{password}` (12–128) → `204`, только admin; хэш argon2id; отзываются все refresh-токены
   сотрудника — его сессии заканчиваются, выданный access-токен доживает свой срок (до 15 мин); клиент — `409 PASSWORD_NOT_ALLOWED`, анонимизированный —
   `404 USER_NOT_FOUND`. Смена пароля самим сотрудником — бэклог (глава 25).
6. **Изменение себя (Q7).** В UI для своей учётной записи роль и блокировка недоступны с
   подсказкой «Попросите другого администратора»; правило backend не меняется.
7. **Тикеты инженера (Q8).** В карточке инженера — его нерешённые тикеты (`listTickets`
   `assigned_engineer_id`) с переназначением другому активному инженеру или возвратом в очередь
   (`assignTicket`). Подтверждение блокировки и смены роли предупреждает: «У инженера N нерешённых
   тикетов — переназначьте их».
8. **Регламенты ТО (Q9, Q10).** Привязка — выбор существующей модели; новые модели — миграцией
   (справочник). Пересмотр — новая версия, прежняя в архиве; интервалы — км и месяцы (контракт).
   Подсказка ADR 0009: при регламенте масляного фильтра показывать интервал масла той же модели.
   U-42 — пороги подписаны «Общие для всех моделей», «износ, %» вместо «% выработки», без
   технических фраз. U-44 — версии нумеруются по порядку; дата и автор версии требуют контракта —
   бэклог.
9. **Статьи (Q11).** Медиа — ссылками в Markdown (ADR 0018). Экран версий статьи — список и
   просмотр только для чтения. Дерево опубликованной статьи заблокировано с подсказкой «Снимите с
   публикации, чтобы изменить дерево» (правило backend). U-05/U-43 — «Сохранить и опубликовать» и у
   новой статьи, и при несохранённых правках. U-40 — шаги дерева по тексту вопроса, а не `#id`,
   «Ведёт к» без обрезки, без «можно публиковать» у опубликованной. Внутренние заметки — бэклог
   (контракта нет).
10. **Публикации (Q12, U-45).** Перед публикацией — подтверждение с `audience-preview`:
    «Получат N клиентов (M устройств)» и предупреждение «Отменить нельзя». Для релиза прошивки
    (уведомление создаётся вместе с релизом, его ещё нет для `audience-preview`) — оценка сверху:
    «Получат не больше N владельцев {модели}» (preview `news` на модель). Лента опубликованного —
    из `notifications/published` со статистикой доставки и открытий, фильтры типа и модели.
11. **Дашборд (Q13, U-41).** Фильтры периода, модели и категории (что поддерживает операция);
    «Данные на ЧЧ:ММ, обновляются раз в 5 минут» из `computed_at`, кнопка «Обновить»; часы — до 0,01,
    как в API (сверка с ручным расчётом); при смене периода старые цифры не показываются;
    «Самая проблемная модель» → «Больше всего тикетов»,
    пояснение «на 10 авто».
12. **Конструктор SLA (Q14)** — не делается (не в чек-листе, ADR 0017): нормативы — миграцией.
13. **E2E «регламент → статус клиента» (Q15).** Playwright: администратор в админ-панели
    пересматривает регламент тестового авто — статус «светофор» клиента
    (`GET /vehicles/{id}/aggregate-statuses` клиентским токеном) меняется на том же стеке без
    перезапуска и деплоя; обратно — пересмотр к прежнему интервалу. Дополнительно — ручная проверка
    в iOS Simulator (pull-to-refresh) в сессии владельца.
14. **Сверка дашборда (Q16).** Автоматически: на стек загружается контрольный набор,
    `analytics-worker --once`, Playwright сравнивает числа на экране за март 2026 с
    `docs/ANALYTICS_CONTROL.md`. Вручную: владелец сверяет экран с документом в сессии проверки.
15. **E2E-инфраструктура (Q17).** `web-admin` — своя `playwright.config.ts` и `scripts/e2e.sh` на
    том же `integration_stack.sh`; seed `backend/scripts/e2e_admin.py` на общих помощниках
    `e2e_backend.py` (администратор, инженер, клиент с авто, регламент, опубликованная статья);
    `web-e2e.yml` получает вход `app` и вызывается из `ci.yml` по матрице; `web-admin/**` — в
    фильтр `web_e2e`. CI — Chromium, три браузера — ручной запуск (как ADR 0025 п. 14). Сценарии:
    вход и отказ инженеру, регламент → статус клиента, пользователи (создание → вход, блокировка →
    401, сброс пароля → старый не подходит, переназначение тикета), публикация с числом получателей,
    равным `stats.recipients`, статья → видна клиенту, дашборд = контрольный набор. `LAST_ADMIN` на
    стеке не воспроизвести (вошедший администратор — уже второй активный) — проверяют тесты backend
    и Vitest. Сценарии меняют данные стека — один браузер на прогон.
16. **«На staging» (Q18).** cd-staging собирает `web-admin` с `VITE_API_BASE_URL=/v1` и проверяет
    CSP и `/v1` в сборке, как `web-engineer`; артефакт `web-admin-staging-<sha>`; деплой — глава 26.
17. **Замечания юзабилити (Q19).** Закрываются U-05, U-40, U-41, U-42, U-43 (без заметок), U-45;
    U-44 — частично (нумерация), остальное — бэклог.
18. **«Ответственный сотрудник ЕТСавтоГомель» (Q20) — отклонение от DoD (решение владельца).**
    Сотрудника для проверки нет: владелец проходит сценарий проверки в роли администратора
    (вход, регламент → статус клиента в iOS Simulator, статья, публикация, пользователи, сверка
    дашборда), фидбек вносится до merge; проверка ответственным сотрудником — бета-пилот (глава 27).
    Уточнение 2026-10-13: по поручению владельца («сделай всё это сам») прогон выполнил агент — админ-панель
    в браузере, клиент в iOS Simulator; итог и найденное — `docs/reviews/ADMIN_PANEL_22.md`.

## Последствия
- Контракт 1.11.0 (аддитивно: `resetUserPassword`), backend + тесты, `npm run gen:api`, Swagger,
  `backend/tests/contract`; `oasdiff` — без ломающих.
- `web-e2e` удлиняется вторым приложением; изменения `web-admin/**` запускают E2E.
- Production-развёртывание админ-панели требует прокси `/v1` и CSP (глава 26), как у кабинета
  инженера.
- DoD главы отмечен в `MASTER_CHECKLIST.md` с отклонением (п. 18).
- Глоссарий v1.14: «Учётная запись сотрудника», «Пересмотр регламента ТО».
- Отложено: смена пароля самим сотрудником (глава 25), дата и автор версии регламента, внутренние
  заметки статей, конструктор SLA и категорий, загрузка медиа статей, создание моделей авто из
  админ-панели.
