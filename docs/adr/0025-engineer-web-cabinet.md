# 0025. Веб-кабинет инженера: API через тот же origin, канбан с перетаскиванием и опросом, конфликт взятия, фильтр `resolved_since`, проверка владельцем в двух ролях

**Статус:** Принято, 2026-10-13 (владелец проекта, Issue #87, grill-with-docs Q1–Q23; Q9 — решение
владельца без рекомендации, остальные — рекомендации, принятые владельцем)

## Контекст
Глава 21 переводит веб-кабинет инженера с фикстур на реальный API: авторизация инженера (роль
RBAC), канбан-доска с drag-n-drop сменой статуса, карточка тикета с контекстом авто и историей чата,
быстрые ответы из базы знаний, тёмная тема. Проверки — E2E «тикет в работу → ответ из базы знаний →
закрытие → синхронизация у клиента в реальном времени» и конкурентный доступ «два инженера берут
один тикет»; DoD — «протестирован минимум 2 реальными инженерами без критичных замечаний». Факты на
начало главы:
- `web-engineer` — прототип главы 8 (ADR 0012) на `PrototypeRepository`: канбан с фильтрами SLA,
  карточка, быстрые ответы (вставить / отправить), тёмная тема по умолчанию; статус меняется только
  кнопками, перетаскивания нет; сетевого слоя нет (`createApiClient` — заготовка под Prism);
- контракт 1.9.0 покрывает почти всё: `staffLogin`/`refresh`, атомарный `claimTicket` (чужой —
  `409 TICKET_ALREADY_CLAIMED`), граф статусов (ADR 0017 п. 4: в очередь вернуть нельзя),
  `TicketDetail.vehicle_context`, история ТО и статусы агрегатов, чат с `after_id`, WebSocket
  тикета с `message.created` и `ticket.updated`; вложения в ответах — presigned GET на 15 минут;
- WebSocket есть только у тикета — события очереди нет; `listTickets` для инженера упорядочен по
  `sla_due_at` по возрастанию, `page_size` ≤ 100 — решённые тикеты копятся, старые идут первыми;
- CORS в backend нет; cd-staging собирает кабинет с `vars.STAGING_API_BASE_URL`, которой нет, —
  артефакт фактически в режиме прототипа;
- инженеров, кроме владельца, для проверки нет.

## Варианты
- **Токены:** access в памяти + refresh в `sessionStorage` / только память / httpOnly-cookie
  (меняет контракт) / `localStorage`.
- **Доступ к API:** тот же origin через прокси / CORS в backend.
- **Перетаскивание:** `@dnd-kit` с клавиатурой / нативный HTML5 DnD.
- **Обновление доски:** опрос / новый канал WebSocket очереди (контракт) / кнопка «Обновить».
- **Колонка «Решено»:** фильтр `resolved_since` (контракт) / все страницы на клиенте / без колонки.
- **E2E:** Playwright в CI против стека из образа-кандидата / только локально / Flutter-клиент в CI.
- **«2 реальных инженера»:** два настоящих инженера / владелец в двух ролях / один инженер + владелец.

## Решение
1. **Токены (Q1).** Access-токен — в памяти, refresh — в `sessionStorage` (живёт до закрытия
   вкладки, переживает перезагрузку). Риск XSS снижает CSP (п. 4). Контракт не меняется; новая
   вкладка требует входа, сессия между вкладками не синхронизируется (Q13).
2. **Тот же origin (Q2).** Кабинет обращается к API по относительному адресу `/v1`: в dev — Vite
   proxy (`/v1` и WebSocket), в production — nginx раздаёт статику и проксирует `/v1` (глава 26).
   CORS в backend не добавляется.
3. **Адреса и сессия (Q13).** `/login`, `/board`, `/tickets/:id` (react-router), после входа —
   возврат на запрошенный адрес. Вход — только роль `engineer` (client и admin получают отказ).
   Неудачный refresh (истёкшая сессия, блокировка) — экран входа «Сессия завершена, войдите снова»;
   черновик сообщения не сохраняется.
4. **CSP (Q14)** — `<meta>` в `index.html` при сборке: `default-src 'self'`, `script-src 'self'`,
   `connect-src 'self'`, `img-src`/`media-src 'self'` + origin S3 (`VITE_MEDIA_ORIGIN`, presigned
   GET вложений). Глава 26 дублирует заголовком nginx и добавляет `frame-ancestors 'none'`.
5. **Режим прототипа (Q7).** Без `VITE_API_BASE_URL` — `PrototypeRepository` (фикстуры, демо-панель),
   с ним — HTTP-репозиторий (как ADR 0022). Сборка staging — `VITE_API_BASE_URL=/v1` (п. 14).
6. **HTTP-слой в `web-shared` (Q21)** — `web-shared/src/data/http/`, его переиспользует глава 22:
   `ApiSession` (токены, один refresh на параллельные `401`, выход), `HttpCommonRepository`,
   `HttpEngineerRepository`, `TicketLive` (WebSocket тикета: авторизация первым кадром, догрузка по
   `after_id` после `ready`, на `4401` — refresh и переподключение, экспоненциальная пауза,
   отключение при скрытой вкладке дольше 5 минут). Тексты ошибок — по коду контракта; тест сверяет,
   что у каждого кода ошибки `docs/openapi.yaml` есть русский текст. Экраны зависят только от
   `EngineerRepository`.
7. **Канбан (Q3, глоссарий «Канбан-доска»).** Колонки — статусы: очередь («Новые»), «В работе»,
   «Ожидает вендора», «Решено». Перетаскивание — `@dnd-kit` с управлением с клавиатуры; подсвечены
   только допустимые по графу колонки: «Новые → В работе» — `claimTicket`; «В работе ↔ Ожидает
   вендора», «→ Решено» — `updateTicketStatus` («Решено» — с подтверждением); «Решено → В работе» —
   переоткрытие; в «Новые» — нельзя. Перенос оптимистичный, при ошибке карточка возвращается и
   показывается причина. Кнопки статуса в карточке сохраняются.
8. **Обновление доски (Q4, Q12, Q23).** Опрос `listTickets` раз в 15 с, при возврате на вкладку и
   после своих действий; открытая карточка — по WebSocket. Активные колонки выгружаются постранично,
   не больше 5 страниц (500 тикетов), в шапке — `total_items`, при превышении — «Показаны первые 500,
   сузьте фильтр». Новые тикеты очереди подсвечиваются, счётчик — в заголовке вкладки; системных
   уведомлений браузера и звука нет. Канал WebSocket очереди — вне главы.
9. **Колонка «Решено» (Q11, Q19) — контракт 1.10.0 (аддитивно).** `listTickets` получает
   необязательный `resolved_since` (date-time): тикеты с `resolved_at >= resolved_since`;
   переоткрытые (`resolved_at = NULL`) не попадают; действует для всех ролей в пределах видимой
   выборки (RBAC-04 без изменений), порядок прежний; значение в будущем — пустой результат,
   неверный формат — `422`. Доска показывает решённые за 7 дней, сортирует их по `resolved_at` по
   убыванию; колонка свёрнута до 20 карточек со ссылкой «Показать все».
10. **Конфликт взятия (Q5, глоссарий «Взять в работу»).** Проигравший в гонке получает `409
    TICKET_ALREADY_CLAIMED`: карточка возвращается, сообщение «Тикет уже взял в работу другой
    инженер», тикет пропадает с его доски. Если открытый тикет переназначен админом (`ticket.updated`
    с чужим `assigned_engineer_id`), карточка становится только для чтения с плашкой «Тикет
    переназначен» и закрывается.
11. **Быстрый ответ (Q6, глоссарий «Быстрый ответ»).** Как в прототипе: «вставить в черновик» и
    «отправить сразу» (заголовок + текст опубликованной статьи; инженер видит только опубликованные,
    RBAC-05). Ссылка на статью в сообщении (`article_id`) — вне главы.
12. **Карточка (Q15, Q16).** Контекст авто только для чтения: модель, VIN, прошивка на момент тикета
    и текущая, пробег, «светофор» агрегатов, история ТО постранично. Вложения клиента — просмотр
    (миниатюры, полный размер, видео); истёкшая ссылка (403 от S3) — перечитать карточку. Вложения
    инженера и запись ТО из кабинета — отдельные задачи после главы.
13. **Тема (Q17).** Переключатель «Как в системе / Светлая / Тёмная» в `localStorage`, по умолчанию
    — «Тёмная» (утверждённый прототип, ADR 0012); контраст обеих тем — WCAG 4.5:1, автотест по
    токенам и скриншоты.
14. **E2E и «на staging» (Q8, Q20, Q22).** Playwright (Chromium) в CI-job `web-e2e` в составе
    `ci-gate` против стека из образа-кандидата (как ADR 0021/0022); запуск при изменениях
    `web-engineer/`, `web-shared/`, `backend/`, `docs/openapi.yaml`, `docs/asyncapi.yaml`. Сценарий
    чек-листа: инженер берёт тикет перетаскиванием → быстрый ответ → «Решено»; «клиент» — тестовый
    подписчик WebSocket с клиентским токеном получает `message.created` и `ticket.updated(resolved)`
    быстрее 2 с. Конкурентный тест — два контекста браузера с разными инженерами. Локально перед
    merge — тот же набор в WebKit и Firefox и один ручной прогон с мобильным клиентом в iOS
    Simulator (результаты в отчёте). cd-staging собирает кабинет с `VITE_API_BASE_URL=/v1`,
    `VITE_MEDIA_ORIGIN` — из переменной окружения staging (до главы 26 пусто); web-admin до главы 22
    — прототип. «На staging» = артефакт `web-engineer-staging-<sha>` в режиме API + `web-e2e` по той
    же ревизии; деплой на сервер — глава 26.
15. **«2 реальных инженера» (Q9, Q18) — отклонение от DoD (решение владельца).** Других инженеров
    нет: владелец проходит сценарий в двух ролях — два аккаунта инженера в двух окнах Chrome
    (обычное и инкогнито), включая гонку за один тикет; ответы клиенту — в мобильном приложении в iOS
    Simulator. Стек и данные (2 инженера, клиент, 6 тикетов разных категорий и сроков SLA,
    опубликованные статьи) поднимает `web-engineer/scripts/engineer_run.sh`; пароли — вне
    репозитория (`~/.config/ev-servicedesk/engineers.local`), в чат и логи не попадают.
    **Критичное замечание** — блокирует сценарий, теряет или портит данные, показывает чужой тикет;
    некритичные — в Issues. Чек-лист и замечания — `docs/reviews/ENGINEER_WEB_21.md`. Проверка
    настоящими инженерами — бета-пилот (глава 27).

## Последствия
- Контракт 1.10.0 (аддитивно: `resolved_since`), `npm run gen:api`, Swagger, тесты контракта и
  backend; `oasdiff` — без ломающих.
- Backend без CORS; production-развёртывание кабинета требует прокси `/v1` на том же origin и
  заголовка CSP (глава 26).
- Глава 22 переиспользует `ApiSession`, `HttpCommonRepository`, `TicketLive`.
- Новая CI-job `web-e2e` (Playwright, стек из образа-кандидата) удлиняет PR, затрагивающие web и
  backend.
- Глоссарий v1.13: «Канбан-доска» (уточнение), «Взять в работу», «Быстрый ответ».
- Отложено: канал WebSocket очереди, `article_id` в сообщении, вложения инженера, запись ТО из
  кабинета, синхронизация сессии между вкладками.
