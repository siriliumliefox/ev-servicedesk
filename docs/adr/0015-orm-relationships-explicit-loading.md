# 0015. ORM-связи только с явной загрузкой: `lazy="raise"` + `selectinload`

**Статус:** Принято, 2026-10-11 (владелец проекта, refactor-PR после ревью главы 11). Развивает
ADR 0003, ADR 0007, ADR 0014.

## Контекст
До главы 11 в `app/models` не было ни одного `relationship`. Ответы Vehicle Service собирались
вручную: presenter получал `Session`, пакетно догружал модели, прошивки, коды агрегатов и
авторов (словари id → объект) и раскладывал поля в схему по одному. Каждый следующий сервис
(глава 12 — агрегаты и ТО, главы 13–15 — тикеты, база знаний, уведомления) повторил бы этот код;
ошибка в нём — либо N+1 запросов, либо расхождение ответа с контрактом.

## Варианты
- **`relationship` с запретом ленивой загрузки** (`lazy="raise"`), связи грузит запрос через
  `selectinload`; схемы ответа читают ORM-объект (`from_attributes`).
- **`relationship` с ленивой загрузкой по умолчанию** — удобно, но N+1 незаметен в коде и тестах.
- **Без `relationship`:** `select` с `join`, возвращающий кортежи; presenter собирает ответ из
  кортежа. Модели не меняются, но каждый запрос повторяет join-ы, а `paginate()` и схемы
  работают с кортежами вместо объектов.

## Решение
1. Связи ORM объявляются с `lazy="raise"`: обращение к незагруженной связи — ошибка, а не скрытый
   запрос. Загрузка — явно, опциями запроса `selectinload(...)` (один `IN`-запрос на страницу,
   не наследует `FOR UPDATE` основного запроса).
2. Сервис возвращает объекты с загруженными для ответа связями (наборы опций рядом со
   сценариями, например `VEHICLE_OUT`, `RECORD_OUT` в `app/domain/vehicles/service.py`). После
   `commit`, когда значения меняют триггеры БД, объект перечитывается `Session.get(...,
   options=..., populate_existing=True)` вместо `refresh` (refresh теряет связи, не загруженные
   eager-опцией).
3. Схемы ответа — `ConfigDict(from_attributes=True)`, без `Session` и ручной раскладки полей.
   Отображение значений БД в контракт — в схеме (например, `trim = ''` → `null` валидатором),
   производные признаки — свойства модели (`Vehicle.is_active`,
   `MaintenanceRecord.aggregate_type_code`).
4. Скалярное значение по составному FK (версия прошивки авто: FK «прошивка той же модели»
   `(current_firmware_release_id, vehicle_model_id)`) — `column_property` со scalar subquery,
   без отдельной связи.
5. `relationship` не меняет схему БД: DDL, Alembic и `tests/db` не затрагиваются.

## Последствия
- Vehicle Service переведён на связи (`Vehicle.vehicle_model`, `MaintenanceRecord.aggregate_type`,
  `MaintenanceRecord.performed_by`); сгенерированный OpenAPI и ответы API не изменились.
- Главы 12–15 добавляют связи тем же способом; пропущенная опция загрузки падает в тестах
  (`InvalidRequestError`), а не превращается в N+1 на staging.
- `column_property` выполняется при каждой загрузке `Vehicle` — подзапрос по PK
  `firmware_release`, дешёвый; при росте числа таких полей — `deferred(...)` и явная загрузка.
