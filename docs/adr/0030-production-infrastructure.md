# 0030. Production-инфраструктура: две ВМ на Docker Compose, деплой по SSH с автооткатом, pgBackRest, Prometheus/Loki с алертами в Telegram, план отката

**Статус:** Принято, 2026-10-19 (Issue #138, grilling Q1–Q33; рекомендации приняты по правилу владельца
2026-10-12; провайдер, серверы, аттестация, договоры, домен, канал и часы алертов, вливание в `main` —
решения владельца)

## Контекст
Глава 26 требует production-серверы и ресурсы, мониторинг (Prometheus/Grafana) и алерты на error rate и
падение сервиса, автоматическое резервное копирование БД и план восстановления, план отката релиза,
централизованный сбор логов (ELK/Loki); проверки — учебное восстановление из бэкапа и тест алертов
(«искусственный сбой → уведомление ответственному в целевое время»); DoD — «production готов,
мониторинг/алерты работают, план отката опробован на staging». Факты на начало главы:
- серверов нет: `deploy-staging` в `cd-staging.yml` — заглушка (ADR 0008 п. 6); «на staging» в главах
  10–25 — опубликованный и проверенный образ `backend:staging-<sha>` (ADR 0013 п. 1, 0021, 0027 п. 5);
- образ один на API и worker'ы, fail closed (`ENVIRONMENT=production` по умолчанию, `app.preflight`),
  `WEB_CONCURRENCY=2`, без root; в production запрещены фейковые SMS и push (ADR 0013, 0019) — production
  не стартует без ключей A1 и FCM;
- процессы — профиль compose `full`: `migrate`, API, `notifications-`, `analytics-`, `privacy-worker`;
- есть `/health`, журнал без ПД (`PiiFilter`, свой журнал доступа); метрик Prometheus, nginx, бэкапов,
  конфигураций сервера нет;
- откат — перетегирование `backend:staging-<sha>` → `backend:staging` без пересборки (ADR 0008 п. 5);
- `main` — каркас глав 1–4, на 90 коммитов позади `develop`; на `main` и `develop` — линейная история;
- ТЗ (раздел 7, X-04): доступность ≥ 99,5 % — ≈ 3,6 ч простоя в месяц;
- отложено «до главы 26»: nginx — статика кабинетов, `/v1` и WebSocket, TLS, HSTS, CSP заголовком,
  `frame-ancestors`, список `SECURITY_HEADERS` (ADR 0025 пп. 2, 4; 0029 пп. 8, 21); `FORWARDED_ALLOW_IPS`
  и деление `SMS_PROVIDER_RPS` (ADR 0013); провайдер S3 и `nosniff` (ADR 0017); IP сервера для A1 и
  сценарий X5 (ADR 0027 п. 11); шифрование диска и бэкапов (ADR 0005); прогон нагрузки на сервере,
  настройки PostgreSQL, Grafana для k6, ночные прогоны (ADR 0028 пп. 5, 14–16); ZAP на сервере (ADR 0029
  п. 7); аудит целостности в мониторинге (ADR 0021); 99-З — уполномоченные лица (п. 11), класс ИС и ТКЗИ
  (п. 25), уведомление НЦЗПД об инциденте (п. 22);
- справка по провайдерам и нормам (2026-10-18): класс ИС — «3-ин» (приказ ОАЦ № 66: неспециальные ПД,
  подключение к Интернету), аттестация СЗИ обязательна до ввода в эксплуатацию с реальными ПД и может
  опираться на аттестованное облако провайдера (п. 15 Положения); для 3-ин журналы событий ИБ — не
  менее года; управляемого PostgreSQL и шифрования дисков у провайдеров РБ нет; Указ № 60 обязывает
  юрлица, продающие товары и услуги в РБ через Интернет, размещать ресурсы в РБ; страны ЕАЭС — в перечне
  НЦЗПД с надлежащим уровнем защиты (приказ № 14); Promtail снят с поддержки 02.03.2026; pgBackRest —
  не ниже 2.59.3 (слабые ключи шифрования в более ранних); разрешённый IP в A1 добавляют администраторы
  платформы по обращению.

## Варианты
- **Провайдер:** hoster.by (защищённое облако) / beCloud / A1 Digital / Timeweb Cloud (Россия, ЕАЭС).
- **Топология:** одна ВМ / две ВМ / три ВМ (мониторинг отдельно).
- **Среда исполнения:** Docker Compose / k3s / PaaS.
- **Описание инфраструктуры:** shell + compose / Ansible / Terraform.
- **Деплой:** SSH из job окружения / агент на сервере (Watchtower) / self-hosted runner.
- **Мониторинг и журналы:** свой Prometheus + Loki / Grafana Cloud / ELK.
- **Бэкап PostgreSQL:** pgBackRest / WAL-G / `pg_dump` по cron / управляемая БД.
- **Канал алертов:** Telegram / Telegram + e-mail / e-mail.
- **Вливание в `main`:** merge-коммит / теги на `develop` / squash с выравниванием.
- **Аттестация СЗИ:** в главе 26 / до пилота / не аттестовать.

- **Серверы в главе:** заказать сейчас / код и проверки на локальном стенде, серверные шаги — после заказа.

## Решение
1. **Провайдер (решение владельца, Q27–Q28).** Timeweb Cloud (аккаунт ООО «ЕТСавтоГомель», в нём же
   виртуальный хостинг сайта и домен `etsautogomel.by`): production — Санкт-Петербург (ru-1), staging —
   Москва (ru-3), обе — Ubuntu 24.04, публичный IPv4 на сервер (закреплён за аккаунтом — годится для
   белого списка A1). Россия — член ЕАЭС, перечень НЦЗПД (приказ № 14 п. 1): передача ПД допустима без
   ограничений, сообщается в политике (глава 27). Виртуальный хостинг сайта не подходит (проверено
   2026-10-19: общий узел, без root и Docker, PostgreSQL нет, Python 3.10, общий IP). Управляемый
   PostgreSQL Timeweb не используется: почти удваивает цену, PITR не заявлен, привязал бы к провайдеру.
2. **Серверы не заказаны (решение владельца 2026-10-19).** Глава делает всё, что не требует оплаты:
   `deploy/`, CI, метрики, документы — и проверяет их на локальном стенде (п. 23); серверные шаги
   (bootstrap, деплой, X5, ZAP и нагрузка на сервере, запуск production) включаются заданием секретов и
   переменных окружений, без правки кода. До заказа глава — PARTIAL.
3. **Топология (Q1, Q15, Q27).** Две ВМ: production 4 vCPU / 10 ГБ / 120 ГБ NVMe, staging 2 / 6 / 60
   (≈ 14 480 ₽/мес с S3 и IPv4 по прейскуранту 2026-10-19). На каждой — один и тот же стек: приложение и
   мониторинг (Prometheus, Alertmanager, Grafana, Loki, Alloy, экспортёры); окружение — метка. Журналы
   production не покидают его ВМ. Каждая ВМ проверяет `/health` другой снаружи (blackbox);
   Alertmanager обеих шлёт Watchdog во внешний dead-man-сервис (healthchecks.io, без ПД). WireGuard не
   нужен. Grafana, Prometheus и Alertmanager без публичного адреса — доступ через SSH-туннель.
4. **Среда исполнения (Q2).** Docker Compose: `migrate` (разовый) → API (`WEB_CONCURRENCY=2`) →
   `notifications-`, `analytics-`, `privacy-worker` (по одному) + PostgreSQL 16 (pgBackRest), Redis 7
   (AOF `everysec`), nginx, certbot. Выкладка — пересоздание контейнеров, простой до 30 с; blue/green нет.
5. **Описание инфраструктуры (Q3, Q32).** Каталог `deploy/`: compose приложения и мониторинга, конфигурации
   nginx, PostgreSQL, Prometheus (правила алертов и их тесты), Alertmanager, Loki, Alloy, Grafana
   (источники и дашборды), скрипты `bootstrap.sh` (идемпотентная подготовка Ubuntu: вход только по ключу,
   без root, ufw 22/80/443, fail2ban, unattended-upgrades, Docker, пользователь `deploy`, NTP, таймеры
   бэкапа), `deploy.sh`, `rollback.sh`, `backup.sh`, `restore.sh`. В репозитории (публичном) нет IP,
   паролей и ключей — только переменные. Terraform не используется: ВМ и бакеты создаёт владелец в панели
   по чек-листу (`docs/runbooks/OWNER_ACTIONS_26.md`).
6. **Проверка конфигураций (Q3).** Job `infra` в `ci.yml` (входит в `ci-gate`): `docker compose config`,
   `nginx -t`, `promtool check config` и `promtool test rules` (юнит-тесты каждого алерта), `amtool
   check-config`, `loki -verify-config`, `alloy fmt`, shellcheck; сверка заголовков nginx со
   `SECURITY_HEADERS` и CSP сборки — тест `web-shared`.
7. **Деплой (Q4).** Job окружения (`staging` / `production`) подключается по SSH пользователем `deploy`;
   ключ ограничен `command="deploy.sh"` (forced command), ключ хоста закреплён в секрете. Образ
   подтягивается по digest временным `GITHUB_TOKEN` job'а (stdin, `docker logout` после) — постоянных
   учётных данных ghcr на сервере нет. Статика кабинетов — архив артефакта в `web/<sha>/`, текущая
   версия — symlink. `deploy.sh`: проверка digest → `migrate` → `up -d` → `/health` и smoke через nginx →
   при неудаче — автоматический откат на предыдущий digest (`current` → `previous`) и код выхода 1.
   Без секретов сервера job пишет «сервер не настроен» и завершается успешно (п. 2).
8. **Выпуск в production (Q5, решение владельца).** «Собрали один раз — продвигаем»: production получает
   тот же digest `backend:staging-<sha>`, что прошёл staging и regression; web собирается под production
   из того же sha (свой `VITE_MEDIA_ORIGIN`). `cd-production.yml` — push в `main`, окружение `production`
   (Approve — владелец). Release-PR `develop → main` вливается **merge-коммитом**: с `main` снимается
   линейная история (`scripts/setup-branch-protection.sh`), `develop` — squash и линейная история.
   Первый выпуск — `v1.0.0-rc.2` после учений (п. 23) и заказа серверов.
9. **Бэкапы (Q6, Q16, Q29).** pgBackRest ≥ 2.59.3 (слабые ключи в ранних) в образе `deploy/postgres`:
   непрерывный архив WAL (`archive_timeout` 60 с), полный бэкап раз в неделю, разностный — ежедневно,
   PITR за 14 дней. Два репозитория: repo1 — бакет S3 production (Санкт-Петербург), repo2 — staging-ВМ
   по SFTP (Москва, внешняя площадка). Шифрование на клиенте (AES-256, `repo-cipher-pass`); ключ — секрет
   окружения и копия у владельца офлайн (секреты GitHub не читаются обратно — без копии восстановление
   невозможно). На staging ключа production нет: там только шифротекст, правило «данных production на
   staging нет» сохраняется. **RPO ≤ 5 мин, RTO ≤ 2 ч.** Таймеры: `pgbackrest check` и `verify` —
   еженедельно; проверка восстановления — ежемесячно, в изолированный контейнер без сети на той же ВМ,
   с `app.tools.integrity` и сверкой счётчиков строк. Итоги — метрики textfile-collector node_exporter.
   Redis не бэкапится (коды, лимиты и `jti` с TTL).
10. **S3 (Q17, Q30).** Бакеты `<окружение>-media` и `<окружение>-backup` в S3 Timeweb (только
    Санкт-Петербург, SigV4, lifecycle, версионирование не отключается). Media: `uploads/` — 1 сутки,
    старые версии — 7 дней (privacy-worker удаляет вложения; ПД не должны пережить срок 99-З — 15 дней).
    Backup: ретенцию ведёт pgBackRest, старые версии — 1 сутки. `X-Content-Type-Options` на объекты
    Timeweb не задаётся — **принятый S4**: `Content-Type` задаётся подписью presigned GET
    (`response-content-type`), список MIME закрыт (ADR 0017 п. 10), медиа — на чужом origin без сессий
    кабинетов, браузеры не исполняют `image/*`/`video/*` как HTML; прокси через nginx ломает SigV4.
11. **Шифрование (Q18, ADR 0005).** Диски не шифруются: провайдер не предлагает, LUKS требует ручной
    разблокировки после каждой перезагрузки (противоречит 99,5 %). Бэкапы шифруются на клиенте (п. 9).
    Пользовательский трафик — TLS 1.2/1.3. Сертифицированное канальное шифрование (приказ ОАЦ № 66,
    3-ин п. 5.1) — вопрос аттестации (п. 21).
12. **Мониторинг (Q7, Q15).** Prometheus 3.13 LTS, Alertmanager 0.34, Grafana OSS 13.2, Loki 3.7, Grafana
    Alloy 1.20 (Promtail снят с поддержки), node_exporter, cAdvisor, postgres_exporter, redis_exporter,
    blackbox_exporter, nginx — журнал в Loki; образы закреплены по digest. Дашборды: «Обзор» (запросы,
    5xx, p95 по маршрутам, доступность за 30 дней против 99,5 %, worker'ы, PostgreSQL, Redis, бэкапы,
    ресурсы) и «Нагрузка k6».
13. **Метрики приложения (Q8).** API — `/metrics` (`prometheus_client`, multiprocess на процессы uvicorn,
    вне `/v1` и контракта): `ev_http_requests_total{method,route,status}` и
    `ev_http_request_duration_seconds{method,route}` — по шаблону маршрута, как журнал доступа (значения
    параметров пути не пишутся). nginx отдаёт `/metrics` снаружи как 404. Worker'ы — свой порт
    (`METRICS_PORT`): `ev_worker_last_success_timestamp_seconds{worker}`,
    `ev_worker_cycle_errors_total{worker}`, очередь push (`ev_push_queue_pending`,
    `ev_push_queue_oldest_age_seconds`), очередь анонимизации (`ev_privacy_queue_size`,
    `ev_privacy_queue_oldest_age_seconds`), свежесть витрины (`ev_analytics_data_age_seconds`); раз в
    сутки `analytics-worker` запускает аудит `app.tools.integrity` — `ev_integrity_violations`. Контракт
    API не меняется.
14. **Алерты (Q9, решения владельца).** Канал — Telegram-бот (Alertmanager `telegram_configs`), ответственный —
    владелец; critical — круглосуточно, warning — 08:00–22:00 по Минску (ночные ждут утра). В текстах
    алертов нет ПД (метки — сервис, маршрут, окружение). **Critical** (уведомление ≤ 5 мин от начала
    сбоя: проба 30 с, `for` 2 мин, `group_wait` 30 с): `/health` недоступен снаружи; 5xx > 5 % за 5 мин;
    PostgreSQL или Redis недоступен; worker без успешного цикла дольше трёх интервалов; архив WAL старше
    15 мин или бэкап старше 26 ч (полный — 8 сут); клиент в очереди анонимизации дольше 14 дней; диск
    > 95 %; нарушения целостности > 0. **Warning:** 5xx > 1 % за 15 мин; p95 чтения > 300 мс за 10 мин
    (норматив ADR 0028); очередь push старше 10 мин; диск > 85 %; память > 90 %; перезапуски контейнера;
    сертификат истекает через < 14 дней. Watchdog — dead-man (п. 3).
15. **Журналы (Q10, Q19).** В staging и production — JSON-журнал (`LOG_FORMAT=json`; `PiiFilter`
    остаётся). Журнал nginx — JSON без строки запроса (`$uri`, без `$args`; ADR 0029 п. 17). Новый
    логгер `app.security` — события безопасности: вход сотрудника и клиента (успех, неудача), выход,
    повтор refresh-токена, смена и сброс пароля, создание сотрудника, смена роли, блокировка, отзыв
    согласия, анонимизация, публикации и регламенты администратора; идентификатор пользователя, роль и
    IP, без телефона и текстов. Хранение в Loki: поток `security` — 365 дней (3-ин п. 1.2–1.3, на случай
    аттестации), остальное — 30 дней в production и 7 в staging. Доступ — Grafana за входом.
16. **План отката (Q11).** Релиз = digest образа + sha статики + ревизия Alembic. Правило миграций —
    совместимость с предыдущим релизом (expand → contract в следующем): откат — предыдущий digest без
    downgrade. Страж в cd-staging: предыдущий опубликованный образ стартует на схеме кандидата и проходит
    smoke; несовместимая миграция — пометка в PR и `alembic downgrade` (проверен в backend-ci). Последняя
    линия — PITR. Статика — переключение symlink. Health или smoke после выкладки не прошли —
    автооткат (`deploy.sh`); critical-алерт в течение 30 мин после релиза — `rollback.sh` вручную.
17. **Секреты (Q12).** Источник истины — GitHub Environment Secrets (ADR 0008): job передаёт env-файл
    через stdin SSH, на сервере — `.env` 0600 пользователя `deploy`. Новые: `POSTGRES_PASSWORD`, ключи S3
    (media, backup), `PGBACKREST_CIPHER_PASS`, пароль Grafana, ключ SSH деплоя и ключ хоста, токен бота и
    `chat_id` алертов, ссылка dead-man. Генерируемые создаёт `scripts/set-environment-secrets.sh`
    (`SECRETS=…`); сторонние (A1, FCM, бот, S3, dead-man) вводит владелец скриптами со скрытым вводом.
    Ключ шифрования бэкапов владелец создаёт в своём терминале и сохраняет в менеджер паролей.
18. **Сеть и nginx (Q13, Q31).** Имена — поддомены `etsautogomel.by` (DNS — Timeweb): `api.`, `engineer.`,
    `admin.` и `api.staging.`, `engineer.staging.`, `admin.staging.`; мобильное приложение — `api.`,
    кабинеты — `/v1` своего origin (ADR 0025 п. 2). TLS — Let's Encrypt, HTTP-01 через nginx (токен API
    DNS на сервере не хранится), продление — certbot, перечитывание nginx; запасного бесплатного УЦ для
    `.by` нет — риск принят, алерт за 14 дней. nginx: HSTS (`max-age=31536000`), CSP заголовком —
    политика сборки + `frame-ancestors 'none'`, список `SECURITY_HEADERS` (`web-shared/vite.ts`) — один
    источник, тест сверяет файл nginx; прокси `/v1` и WebSocket (`Upgrade`, чтение до 1 ч); nginx
    перезаписывает `X-Forwarded-For` своим `$remote_addr`, backend доверяет только подсети nginx
    (`FORWARDED_ALLOW_IPS`). Наружу — 22 (только ключи, fail2ban), 80, 443.
19. **SMS и push (Q14, Q22, Q23).** A1 на staging и production (A1 разрешает оба IP по обращению
    владельца); на staging — ещё `SMS_TEST_PHONES` для автотестов; X5 — на staging с телефоном
    владельца. `SMS_PROVIDER_RPS`: API — 4 на процесс × 2, privacy-worker — 1 (итого 9 ≤ 10 у A1).
    Push: production — FCM отдельного Firebase-проекта `ev-servicedesk-prod`, staging — `fake`.
20. **Нагрузка и ZAP на сервере (Q20, Q21).** Полный прогон ADR 0028 (`mixed`, `peak`, `soak`) — на
    production-ВМ до запуска в режиме staging (сид), k6 в той же Docker-сети, затем облегчённый —
    через nginx и TLS; тома удаляются, production инициализируется с нуля. Ночной облегчённый прогон —
    на staging (расписание GitHub → SSH), итоги k6 → Prometheus staging → дашборд. ZAP (`security.yml`) —
    цель «staging-сервер» через nginx: API от имени трёх ролей и кабинеты, раз в неделю и вручную; на
    production — один пассивный baseline после запуска. До заказа серверов ZAP проверяет nginx на
    локальном стенде (п. 23).
21. **99-З и ОАЦ (Q24, Q33, решения владельца).** Класс ИС — «3-ин»; **аттестация СЗИ не проводится**
    (решение владельца 2026-10-19) — ввод в эксплуатацию с реальными ПД без неё — ASSUMPTION и риск,
    записан в `docs/compliance/OAC_3IN.md` (проект акта класса, требования приложения 3 и что из них
    закрыто) и чек-листе 99-З (п. 25). Договоры с уполномоченными лицами (хостинг, S3, A1, FCM) —
    отложены владельцем; перечень и обязательные пункты — в `OAC_3IN.md` (п. 11 чек-листа). Указ № 60
    (ресурсы юрлица РБ, продающего через Интернет, — в РБ): размещение в России — риск, перед
    коммерческим пилотом — юридическая проверка или переезд к провайдеру РБ; стек переносим (п. 1, 4).
    Runbook инцидента — `docs/runbooks/INCIDENT_PD.md`: нужно ли уведомлять (приказ НЦЗПД № 13), срок —
    не позднее 3 рабочих дней, форма на cpd.by, состав уведомления (п. 2.2).
22. **Учебное восстановление и тест алертов (Q25, Q26).** DR drill: бэкап staging восстанавливается на
    новую временную ВМ строго по runbook (`bootstrap` → PITR → стек → аудит целостности и счётчики →
    замер RTO и RPO → ВМ удаляется). Тест алертов на staging: остановка backend → ServiceDown;
    остановка PostgreSQL под облегчённой нагрузкой → HighErrorRate; остановка privacy-worker →
    WorkerStale; выключение staging → проба с production и dead-man; время «начало сбоя → сообщение в
    Telegram» — critical ≤ 5 мин. Перед запуском production — короткий ServiceDown.
23. **Локальный стенд (п. 2).** `scripts/infra_stack.sh` поднимает на одной машине два compose-проекта
    из `deploy/` — `staging` и `production` (свои сети и тома, самоподписанный УЦ, MinIO вместо S3,
    SFTP-контейнер вместо repo2) из образа-кандидата и выполняет учения: выкладку и откат N → N+1 →
    N с миграцией, автооткат сломанного релиза, DR drill (удаление томов → восстановление из репозитория,
    замер RTO/RPO), тест алертов (сбой → Alertmanager → приёмник с отметкой времени; Telegram — если
    владелец создал бота), ZAP baseline через nginx. Тот же стенд — workflow `infra-drill.yml` (вручную
    и раз в неделю). Сервер повторяет учения, когда появится (п. 22).
