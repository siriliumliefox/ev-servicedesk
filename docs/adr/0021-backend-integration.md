# 0021. Интеграция backend: стек из образа-кандидата, сверка ответов с OpenAPI вместо Pact, тег Users, право на уведомление при отправке, тестовые номера SMS, аудит целостности

**Статус:** Принято, 2026-10-12 (владелец проекта, Issue #72, grill-with-docs Q1–Q16; рекомендации
приняты по правилу владельца от 2026-10-12)

## Контекст
Глава 17 проверяет, что сервисы глав 10–16 работают согласованно: единая staging-среда,
contract-тесты между сервисами (в чек-листе — Pact), согласованность данных («удаление клиента не
оставляет осиротевших тикетов»), ревью на дублирование и рассинхронизацию контрактов, полный
regression и сквозной сценарий «регистрация → авто → тикет → уведомление → аналитика»;
DoD — тег `backend v1.0-beta`. Факты на начало главы:
- backend — модульный монолит: один образ API и два процесса (`notifications-worker`,
  `analytics-worker`); модули вызывают друг друга в процессе и делят одну БД — HTTP между
  сервисами нет;
- staging-сервера нет до главы 26 (ADR 0008); «staging» — проверенный образ (ADR 0013);
- из 65 операций контракта не реализованы 4 — тег Users (`listUsers`, `createStaffUser`,
  `getUser`, `updateUser`): заблокировать пользователя через API нельзя;
- удаления клиента нет: FK на `app_user` — `RESTRICT`, анонимизация (`anonymized_at`) — глава 25
  (ADR 0013 п. 9, `PD_99Z_CHECKLIST.md` п. 14); авто удаляется мягко (`deleted_at`);
- push по событиям тикета уходит владельцу авто без учёта удаления авто; доставки, поставленные в
  очередь до блокировки, отзыва согласия или удаления авто, всё равно отправляются;
- ответы сверяются с контрактом только там, где тест вызывает `assert_contract` (17 файлов);
- SMS-код в `ENVIRONMENT=staging` снаружи не получить: `FakeSmsProvider` хранит его в памяти
  процесса, отладочный маршрут есть только в `local`; миграции в docker compose не применяются.

## Варианты
- **Среда:** compose-стек из образа-кандидата / `ENVIRONMENT=local` с отладочными маршрутами /
  k8s namespace / ждать сервер главы 26.
- **Contract-тесты:** Pact (нет HTTP между сервисами — нечего сверять) / Schemathesis против
  стека / сверка каждого ответа тестов и сквозного сценария со схемой `docs/openapi.yaml`.
- **Тег Users:** реализовать сейчас / в главе 22 вместе с админ-панелью.
- **SMS для сквозного сценария:** `ENVIRONMENT=local` / клиент создаётся прямо в БД (без
  регистрации) / тестовые номера с кодом из секрета вне production.
- **Целостность:** только тесты / проверочный модуль в образе, запускаемый где угодно.

## Решение
1. **Staging главы 17 (Q1, Q10).** Стек `docker compose --profile full` из образа-кандидата
   (`BACKEND_IMAGE`), `ENVIRONMENT=staging`: API, `notifications-worker`, `analytics-worker`,
   PostgreSQL, Redis, MinIO. Разовый сервис `migrate` (`alembic upgrade head`) — API и worker'ы
   стартуют после него; у API — healthcheck `/health`. Стек поднимается job'ом `integration` в
   `backend-ci` (каждый PR с backend, под `ci-gate`) и шагом `cd-staging` до перетегирования
   образа в `staging`. Реальный сервер — глава 26.
2. **Вместо Pact (Q2).** (а) Каждый ответ API-тестов к операции контракта автоматически
   сверяется с `docs/openapi.yaml`: статус объявлен у операции, тело валидно по схеме (обёртка
   `TestClient`; исключения — явный список с причиной). (б) Сквозной сценарий сверяет каждый
   ответ живого стека. (в) Стыки модулей (Tickets → Vehicle/Aggregates/Knowledge, Notifications →
   Aggregates/Tickets, Analytics → таблицы) покрыты тестами сценариев.
3. **Тег Users (Q3, Q11).** Реализуется в главе 17 — backend полон по контракту; тест требует
   реализации всех операций контракта. Блокировка (`is_active=false`): отзываются все
   refresh-токены (обещано контрактом) и push-токены пользователя, открытые WebSocket закрываются
   с 4401; `409 LAST_ADMIN`, `409 ROLE_CHANGE_NOT_ALLOWED` — по контракту. Тикеты
   заблокированного инженера остаются назначенными; переназначает администратор (`/assign`).
   Разблокировка возвращает только вход: токены выдаются заново.
4. **Жизненный цикл (Q4).** Проверяются блокировка/разблокировка, отзыв согласия ПД, удаление и
   восстановление авто, смена владельца. Анонимизация и физическое удаление — глава 25.
5. **Право на уведомление при отправке (Q5).** Перед отправкой каждой доставки и push по событию
   тикета получатель проверяется заново: активный клиент с действующим согласием ПД; для
   уведомлений, привязанных к авто, — авто не удалено и принадлежит получателю. Иначе доставка
   отменяется без отправки. Push по тикету удалённого авто не отправляется.
6. **Тестовые номера SMS (Q6, Q13).** `SMS_TEST_PHONES` — список номеров E.164,
   `SMS_TEST_CODE` — секрет (6 цифр). Для этих номеров код равен секрету, SMS не отправляется;
   TTL, HMAC, попытки и лимиты — как у обычных номеров. В production конфигурация с ними не
   стартует (fail closed, проверяет smoke образа).
7. **Первый администратор (Q12).** CLI в образе `python -m app.cli create-admin --phone …`,
   пароль из stdin (не в аргументах и окружении); повторный запуск для существующего телефона —
   ошибка. Нужен сквозному сценарию и staging главы 26.
8. **Аудит целостности (Q13).** `python -m app.tools.integrity` в образе — именованные
   SQL-проверки инвариантов между модулями; нарушения печатаются (только идентификаторы, без ПД),
   код выхода 1. Запуск: pytest, стек после сквозного сценария, мониторинг глав 26/28. Ожидание —
   0 нарушений.
9. **Сквозной сценарий (Q14).** `backend/scripts/e2e_backend.py` (poetry-окружение backend,
   `--base-url`, `--job-runner` для разовых задач — в CI `docker compose exec`): CLI создаёт
   администратора → администратор создаёт инженера и регламент → клиент регистрируется по
   тестовому номеру и добавляет авто → базовая замена агрегата, клиент поднимает пробег →
   задача напоминаний, worker отправляет, клиент видит напоминание и открывает его → клиент
   создаёт тикет → инженер берёт, отвечает, фиксирует замену по тикету, решает → обновление
   витрины → администратор видит тикет и обе конверсии в аналитике → аудит 0 → блокировка
   клиента → 401 → аудит 0. Каждый ответ сверяется с контрактом.
10. **Regression (Q15).** Весь pytest одним прогоном на общих PostgreSQL, Redis, MinIO
    (`backend-ci`) — регрессия всех сервисов; job `integration` добавляет стек, сквозной
    сценарий и аудит, pytest на стеке не дублируется.
11. **Ревью (Q7).** Обход всех модулей на дублирование логики и расхождения с контрактом —
    отчёт `docs/reviews/BACKEND_REVIEW_17.md`; мелкое исправляется в PR главы, крупное — issues.
12. **Тег (Q8).** Аннотированный `backend-v1.0-beta` на merge-коммит главы в `develop` после
    зелёного `cd-staging`.
13. **Перенос хвостов «до главы 17» (Q9).** Связка «замена агрегата → запись ТО» и
    `vehicle_context` тикета реализованы (главы 12, 13) — описания в контракте уточняются.
    Защита от двойного клика при замене — глава 21 (веб-кабинет инженера); чат в реальном
    времени в мобильном приложении — глава 20; доска инженера в реальном времени — глава 21;
    подтверждение владения Telegram — глава 25 (нужен бот и токен владельца).

## Последствия
- Контракт: тег Users реализован без изменения схем; уточняются только описания (Users,
  `replaceAggregateStatus`, `getTicket`) — версия 1.7.1, без ломающих.
- Новые переменные окружения `SMS_TEST_PHONES`, `SMS_TEST_CODE` (`.env.example`); в production
  запрещены.
- В образе появляются `app.cli` и `app.tools.integrity` — эксплуатационные команды главы 26.
- Глоссарий baseline v1.9: «Блокировка пользователя».
