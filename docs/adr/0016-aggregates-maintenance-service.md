# 0016. Aggregates & Maintenance Service: замена агрегата, версии регламентов, проверка алгоритма

**Статус:** Принято, 2026-10-11 (владелец проекта, Issue #55, grilling Q1–Q17)

## Контекст
Глава 12 реализует тег Aggregates контракта (OpenAPI 1.3.1) поверх таблиц главы 2 и чистой
функции «светофора» главы 5 (ADR 0009, `docs/specs/AGGREGATE_STATUS_ALGORITHM.md`). Контракт и
спецификация оставляли открытыми:
- сбрасывает ли счётчик запись в истории ТО (`createMaintenanceRecord`) с кодом агрегата;
- что делать с пробегом замены выше пробега авто (история работ в этом случае пробег поднимает,
  ADR 0014 п. 5, а спецификация требует `409`);
- замену агрегата без активного регламента, коды ошибок регламентов, гонку двух пересмотров;
- доступ инженера к замене и связь с тикетом;
- как проверять DoD «алгоритм покрыт тестами ≥ 90% сценариев главы 5».

## Варианты
- **Запись в истории с кодом агрегата:** сбрасывает счётчик / не сбрасывает (только `replace`).
- **Пробег замены выше текущего:** `409` / поднимать пробег, как в истории работ.
- **Замена без активного регламента:** `404` / фиксировать (статус `unknown`).
- **Неизвестные модель/агрегат в теле пересмотра регламента:** `422` / новый `404` в контракте.
- **Пересмотр с теми же интервалами:** всегда новая версия / вернуть текущую.
- **Два одновременных пересмотра:** сериализовать, оба `201` / второму `409` (нет в контракте).
- **Повтор того же запроса замены:** принимать / `409` для точного дубля (нет в контракте).

## Решение
1. **Счётчик сбрасывает только замена агрегата** (`replaceAggregateStatus`). Запись в истории ТО
   с кодом агрегата — «работа по агрегату» (осмотр, долив) и выработку не меняет. Термин
   «Замена агрегата» — в глоссарии (baseline v1.4).
2. **Замена агрегата** (`POST /vehicles/{id}/aggregate-statuses/{code}/replace`):
   - доступ — как изменение авто (ADR 0014 п. 4, `access.for_change`): инженер — по своему тикету
     не в `resolved`, категория тикета не проверяется; удалённое авто — `403`/`404`;
   - `replaced_at` позже сегодняшней даты (`Europe/Minsk`) → `422 REPLACED_AT_IN_FUTURE`;
   - `mileage_at_replacement` выше пробега авто → `409 MILEAGE_AHEAD_OF_VEHICLE`
     (`details.current_mileage`); пробег не поднимается — ошибочный пробег замены испортил бы
     статус, поэтому сначала `updateVehicleMileage`;
   - неизвестный код агрегата → `404 AGGREGATE_TYPE_NOT_FOUND`;
   - **без активного регламента замена фиксируется**: ответ `200` со `status: unknown`,
     `percentage` и остатками `null`, `last_replaced_*` заполнены. Факт замены — реальное событие:
     когда администратор заведёт регламент, статус сразу будет верным. Глоссарий: «Неизвестно» —
     выработку нельзя рассчитать (замены не было или нет регламента);
   - всегда создаётся `maintenance_record` (`description` из запроса, `performed_by` — текущий
     пользователь, `ticket_id` — как ADR 0014 п. 5); `vehicle_aggregate_status` обновляется по
     правилу E5/E6 (`becomes_current`) под блокировкой строки авто и строки статуса;
   - повтор того же запроса создаёт вторую запись в истории (идемпотентности в контракте нет) —
     известное ограничение; защита от двойного клика — UI (глава 17).
3. **Регламенты ТО:**
   - пересмотр (`POST /maintenance-regulations`) всегда архивирует активную версию и создаёт
     новую — даже с теми же интервалами (контракт обещает `201` «новая активная версия»);
   - одновременные пересмотры одной модели выполняются по очереди: строка `vehicle_model`
     блокируется `FOR NO KEY UPDATE` (не мешает FK-проверкам при добавлении авто этой модели) —
     так очередь есть и тогда, когда активной версии ещё нет; ответ всегда `201`, побеждает
     последний, `uq_maintenance_regulation_active` не нарушается (тест гонки, проверен мутацией);
   - неизвестные модель или агрегат → `422 VEHICLE_MODEL_NOT_FOUND` / `AGGREGATE_TYPE_NOT_FOUND`
     (ссылка в теле запроса, как в главе 11);
   - `DELETE` архивного или несуществующего регламента → `404 REGULATION_NOT_FOUND`.
4. **Порядок:** типы агрегатов и статусы — по `aggregate_type.id` (порядок справочника = порядок
   узлов схемы); регламенты — по модели, агрегату, затем новые версии первыми.
5. **Справочник:** повтор кода агрегата → `409 AGGREGATE_TYPE_EXISTS`.
6. **Проверка алгоритма (DoD):** сценарии S01–S19 и R01–R04 из
   `docs/specs/aggregate_status_scenarios.yaml` прогоняются не только через чистую функцию
   (глава 5), но и через сервис с реальной БД (регламент, замена, пробег и пороги — в таблицах);
   backend-ci требует покрытия строк ≥ 90% для `app/domain/aggregates` (`pytest-cov`).
7. **Объём:** только backend; лимитов запросов на операциях Aggregates нет. Мобильное приложение
   и конструктор регламентов web-admin остаются на фикстурах (главы 16, 22).
8. **«На staging»** — как ADR 0013/0014: образ `backend:staging` публикуется после smoke-теста;
   smoke дополнен операциями Aggregates в Swagger и `401` без токена на `/v1/aggregate-types`.

## Последствия
- OpenAPI 1.3.2 — только описания (коды ошибок, замена без регламента, «история работ не
  сбрасывает счётчик»), без ломающих изменений (`oasdiff`); `npm run gen:api`, Swagger sync.
- Спецификация `AGGREGATE_STATUS_ALGORITHM.md` §4 дополнена правилами п. 2.
- Глоссарий baseline v1.4: «Статус «светофор»» (уточнение: настраиваемые пороги, «Неизвестно»),
  «Замена агрегата»; после merge — тег `requirements-baseline-v1.4` (ADR 0002).
- Схема не меняется (таблицы — главы 2 и 5). Data-миграция `0007`: названия агрегатов seed `0002`
  были в форме Unicode NFD («и» + U+0306 вместо «й») и уходили клиентам через API — приведены к
  NFC; новые названия нормализует схема запроса. Остальные NFD-тексты репозитория (документы,
  комментарии) в БД не попадают — отдельная задача.
- Ограничение входа `interval_months ≤ 1200` (больше — выход за год 9999 в расчёте) — только в
  описании контракта и схеме запроса, без `maximum` в OpenAPI (не ломать v1).
