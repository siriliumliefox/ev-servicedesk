# 0004. Хранение файлов: ключ объекта S3 и метаданные вместо URL

**Статус:** Принято, 2026-10-08 (владелец проекта, Issue #8)

## Контекст
Вложения тикетов (C-08, X-03) загружаются напрямую в S3 по presigned URL
(`createPresignedUpload`). Исходный DDL хранил `ticket_attachment.file_url` — ссылку, которая зависит
от bucket/CDN, может быть публичной и не позволяет проверить тип, размер и автора загрузки.

## Варианты
1. Хранить URL (как было).
2. Хранить ключ объекта + метаданные; URL формировать при чтении.

## Решение
Вариант 2. `ticket_attachment`: `object_key` (UNIQUE), `file_type`, `mime_type`, `size_bytes`,
`uploaded_by_user_id`, `created_at`. CHECK: `size_bytes > 0`, MIME соответствует `file_type`
(`image/*` ↔ `photo`, `video/*` ↔ `video`). Составной FK гарантирует, что сообщение вложения
принадлежит тому же тикету. Контракт API не ломается: поле `file_url` из `PresignResponse` —
идентификатор объекта; backend проверяет (HEAD в S3), что объект загружен текущим
пользователем, и сохраняет ключ; при чтении выдаёт короткоживущий presigned GET URL.

## Последствия
- Доступ к файлу = object-level доступ к тикету (`ticket → vehicle.user_id` / назначенный инженер /
  admin); публичных ссылок нет.
- Смена bucket/CDN не требует миграции данных.
- Сервис тикетов (Глава 13) обязан читать MIME/размер из S3, а не доверять клиенту; лимиты
  размера и очистка «сиротских» объектов — там же.
