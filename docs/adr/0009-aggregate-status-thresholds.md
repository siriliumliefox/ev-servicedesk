# 0009. Алгоритм «светофор»: пороги, совмещение интервалов, границы

**Статус:** Принято, 2026-10-10 (владелец проекта, Issue #31)

## Контекст
Глава 5 требует формализовать статус агрегата и сделать пороги 🟢 < 70% / 🟡 70–100% / 🔴 > 100%
настраиваемыми администратором (ТЗ §5: «не зашиты в код»). На момент аудита:
- для порогов нет ни таблицы (DDL главы 2), ни операции в OpenAPI 1.0.0;
- регламент может задавать `interval_km` и `interval_months` одновременно — правило совмещения не задано;
  в `AggregateStatus` есть `remaining_km`, но нет остатка по времени (глоссарий: «остаток ресурса, км/дни»);
- не определены точность сравнения на границах и поведение при отсутствии регламента;
- ТЗ: масляный фильтр «привязан к интервалу замены масла» — механизма связи нет.

## Варианты
- **Хранение порогов:** одна глобальная запись / колонки в каждом `maintenance_regulation` /
  переменные окружения / универсальная таблица «ключ–значение».
- **Два интервала:** худший из двух / только км, месяцы — запасной вариант.
- **Границы:** точное сравнение / сравнение после округления до целого.
- **Нет активного регламента:** не возвращать агрегат / возвращать `unknown`.
- **Масляный фильтр:** отдельный регламент / ссылка на регламент масла в схеме.

## Решение
1. **Пороги — одна глобальная запись** в таблице `aggregate_status_thresholds`:
   `id SMALLINT` с `CHECK (id = 1)` (одна строка; осознанное отступление от `BIGINT IDENTITY` ADR 0003),
   `yellow_from_percent SMALLINT DEFAULT 70`, `red_above_percent SMALLINT DEFAULT 100`,
   `CHECK (1 ≤ yellow_from_percent < red_above_percent ≤ 200)`, `updated_by_user_id` (FK `app_user`,
   `RESTRICT`, NULL у seed-значения), `created_at`, `updated_at` (триггер `set_updated_at`).
   Строка создаётся миграцией с 70/100 и не удаляется. Переменные окружения отклонены — порог меняет
   администратор в UI, а не разработчик; колонки в регламенте — избыточная гибкость, усложняющая админку
   и тесты; «ключ–значение» теряет типы и CHECK.
2. **API (OpenAPI 1.1.0, добавление):** `GET /aggregate-status-thresholds` (engineer, admin) и
   `PUT /aggregate-status-thresholds` (admin), `x-rbac-action: "CRUD регламентов ТО"` — пороги считаются
   частью регламентов ТО, поэтому RBAC-матрица и baseline требований не меняются. Клиенту пороги не нужны:
   статус вычисляет сервер.
3. **Два интервала → худший:** `percentage = max(p_km, p_time)`. В `AggregateStatus` добавляется
   необязательное поле ответа `remaining_days` (OpenAPI 1.1.0).
4. **Границы — точно, без округления:** green `p < 70`, yellow `70 ≤ p ≤ 100`, red `p > 100`;
   расчёт в рациональных числах, `percentage` в ответе усекается до 0,1 только для показа.
5. **Нет активного регламента → агрегат не возвращается.** `unknown` означает только «нет истории замены».
6. **Масляный фильтр — отдельный регламент** с тем же интервалом, что у масла; связи в схеме нет.
7. Статус не хранится — вычисляется при запросе; полные правила, пограничные случаи и сценарии —
   [`docs/specs/AGGREGATE_STATUS_ALGORITHM.md`](../specs/AGGREGATE_STATUS_ALGORITHM.md).

## Последствия
- Новая Alembic-ревизия (таблица + seed + триггер `updated_at`), перегенерация DDL/ERD, тесты схемы.
- OpenAPI `1.0.0` → `1.1.0`: новые операции и необязательное поле ответа — не ломающие изменения
  (ADR 0007, проверяет `oasdiff`); `npm run gen:api`, Swagger sync, `backend/tests/contract`.
- Изменение порогов сразу меняет статусы всех авто; история прошлых порогов не ведётся
  (известны только `updated_at` и `updated_by_user_id` последнего изменения).
- Согласованность регламентов масла и масляного фильтра — ответственность администратора;
  админ-панель (глава 22) может подсказывать интервал масла при создании регламента фильтра.
- Порог N для push «за N км/дней» (N-10) — в главе 15, отдельной настройкой.
