# 0018. Knowledge Base Service: версии — опубликованные редакции, проверка тупиков, эскалация с версией статьи

**Статус:** Принято, 2026-10-12 (владелец проекта, Issue #63, grill-with-docs Q1–Q18)

## Контекст
Глава 14 реализует тег KnowledgeBase контракта (OpenAPI 1.4.0) поверх таблиц главы 2
(`knowledge_article`, `decision_tree_node`) и Tickets Service (глава 13, ADR 0017 п. 7 — эскалация).
Контракт и требования оставляли открытыми:
- чек-лист требует «Версионирование статей», а контракт (`updateKnowledgeArticle`) — «полная история
  версий не хранится», есть только счётчик `version`;
- «привязка к категории ошибки» — у статьи нет категории; мобильный прототип держит `category`
  вне контракта, чтобы подставить её в тикет;
- что такое «тупик»: контракт допускает `next_node_id = null` на узле эскалации, мобильный прототип
  считает узел без вариантов финалом «решено», прототип админ-панели не ловит циклы без выхода;
- можно ли публиковать статью с невалидным деревом и править дерево опубликованной статьи;
- «тикет с пометкой» — `createTicket` проверяет только принадлежность узла статье; источник в
  карточке тикета — одни id;
- поиск (морфология русского языка), видимость общих статей и черновиков (контракт: инженер видит
  черновики — риск отправить черновик клиенту «быстрым ответом», ADR 0012 п. 3);
- открытые вопросы ADR 0012 п. 3 и 5: вложения статей, ссылка на статью из чата.

## Варианты
- **Версии:** только счётчик / снимки опубликованных редакций с чтением истории / снимки + откат.
- **Правка опубликованного:** «вживую» с проверкой после каждой операции над узлом / дерево
  опубликованной статьи только для чтения / отдельная черновая редакция рядом с опубликованной.
- **Одновременная правка:** оптимистическая блокировка по `version` / сериализация блокировкой строки.
- **Поиск:** `ILIKE` / полнотекстовый поиск PostgreSQL / внешний движок.
- **Вложения статей и ссылка на статью из чата:** сейчас / позже.

## Решение
1. **Версия = опубликованная редакция** (глоссарий «Версия статьи»). Таблица
   `knowledge_article_revision` — снимок заголовка, текста и дерева решений на каждую версию;
   чтение истории — аддитивные операции (список версий и одна версия) для `engineer` и `admin`.
   Отката нет (администратор копирует текст; откат можно добавить аддитивно). Черновик до первой
   публикации версий не имеет (`version = 1`, снимков нет); первая публикация создаёт версию 1.
   Правка заголовка или текста опубликованной статьи, которая их реально меняет, — `version + 1` и
   снимок; повторная публикация создаёт версию, только если содержание отличается от последнего
   снимка.
2. **Категория ошибки** — колонка `knowledge_article.category` (`ticket_category`): обязательна для
   `troubleshooting` (иначе `422`), необязательна для `guide`; фильтр `category`. При эскалации
   клиентское приложение подставляет её в тикет; сервер категорию тикета не навязывает.
3. **Типы узлов:** вопрос — от 1 варианта; решение («проблема решена») — без вариантов,
   `is_escalation = false`; эскалация — `is_escalation = true`, варианты допустимы. `next_node_id`
   не бывает `null` и ссылается только на существующий узел своей статьи — иначе `422` при сохранении.
   Не больше 10 вариантов у узла и 100 узлов в дереве.
4. **Проверка дерева** (`validateDecisionTree`, чистая функция домена): `NO_ROOT`, `MULTIPLE_ROOTS`,
   `BROKEN_REFERENCE`, `UNREACHABLE` (недостижим из корня), `DEAD_END` — из узла недостижим ни один
   финал (решение или эскалация), в том числе замкнутый цикл; `NO_ESCALATION` — из корня не
   достижим ни один узел эскалации (C-07: переход в тикет). Глоссарий «Тупик дерева решений».
5. **Публикация:** `troubleshooting` публикуется только с валидным деревом —
   `409 DECISION_TREE_INVALID` с проблемами в `details`; у `guide` дерева нет — создание узла
   `409 ARTICLE_TYPE_HAS_NO_TREE`. Тип статьи не меняется. Дерево опубликованной статьи — только
   чтение (`409 ARTICLE_PUBLISHED`): снять с публикации → править → опубликовать.
6. **Корень и удаление:** второй корень — `409 DECISION_TREE_ROOT_EXISTS` (сначала снять `is_root`
   со старого); удаление узла, на который ссылаются другие, — `409 DECISION_TREE_NODE_REFERENCED`;
   корень без входящих ссылок удалить можно.
7. **Одновременная правка:** последняя запись побеждает; операции над статьёй и её деревом
   сериализуются блокировкой строки статьи (`FOR NO KEY UPDATE`, как пересмотр регламентов,
   ADR 0016) — номера версий, снимки, корень и проверка при публикации не расходятся.
8. **Доступ:** клиент и инженер видят только опубликованные статьи (глоссарий «Черновик статьи»);
   черновик для них — `404`, как и его дерево; CRUD — только `admin` (RBAC_MATRIX).
9. **Поиск** — полнотекстовый PostgreSQL: конфигурация `russian`, вычисляемая колонка `tsvector`
   (заголовок — вес A, текст — B) + GIN, `websearch_to_tsquery`; с `search` — по релевантности,
   затем `id`; без — `updated_at` по убыванию, затем `id` по убыванию. Фильтр `vehicle_model_id`
   включает общие статьи (без модели); `is_published` — только для персонала (клиенту игнорируется).
   Фильтр по прошивке — глава 15 (данных `firmware_release` нет); поле и проверка «прошивка той же
   модели» сохраняются.
10. **Текст:** `content` — Markdown (CommonMark) без сырого HTML, клиенты рендерят безопасно, сервер
    хранит как есть. Пределы: заголовок 1…200 символов после обрезки пробелов, текст до 50 000,
    `question_text` 1…1000, `label` 1…100 — иначе `422`.
11. **Эскалация (уточняет ADR 0017 п. 7):** `source_node_id` необязателен; если указан — узел
    эскалации этой статьи, иначе `422 INVALID_SOURCE_REFERENCE`. Эскалация допустима из статьи,
    у которой есть хотя бы одна опубликованная версия, даже если сейчас она снята с публикации
    (клиент мог проходить дерево в момент снятия; id такой статьи не секрет). Черновик без
    опубликованных версий — по-прежнему `422`. Тикет хранит версию статьи на момент эскалации
    (`ticket.source_article_version`); персонал видит источник в карточке тикета —
    `source_article {id, title, version}` (аддитивно). Ход диагностики — в описании тикета,
    его формирует клиентское приложение. Удалённый узел — `422`: клиент повторяет без `source_node_id`.
12. **≥5 реальных сценариев** — data-миграция (как `0006`): опубликованные статьи
    `troubleshooting` по одной на каждую категорию ошибки (сбой приложения после русификации,
    навигация, звук/Bluetooth, связь SIM/eSIM, ТО) с деревьями 4–8 узлов; тексты утверждает
    владелец в PR. Откат удаляет их, только если на них не ссылаются тикеты.
13. **Контракт 1.5.0** — аддитивно: `category` у статьи и в запросах (в `PATCH` — также привязка к
    модели и прошивке), `updated_at` у статьи, фильтры `category` и `is_published`, операции
    истории версий, `source_article` в карточке тикета, коды ошибок — в описаниях. `NO_ROOT` и
    `NO_ESCALATION` — новые значения в ответе с оговоркой в описании (ADR 0007); `oasdiff` считает
    их ломающими, поэтому они перечислены в `docs/api-breaking-allowed.txt` (`--err-ignore`).
    Запрет `null` в `next_node_id` и пределы длины — проверка сервера (`422`), контракт
    остаётся `nullable` (сужение запроса по ADR 0007 — только `/v2`; как длины в ADR 0017 п. 13).
    Описание `updateKnowledgeArticle` («история не хранится») исправлено.
14. **Отложено:** вложения статей — файлы прошивок к публикациям прошивок (глава 15), медиа — к
    конструктору админ-панели (глава 22), пока изображения и видео — ссылками в Markdown; ссылка на
    статью из чата (`TicketMessage.article_id`) — глава 21; экраны истории версий и поиска в
    клиентах — главы 16, 21, 22 (клиенты на фикстурах только приводятся к контракту).
15. **«На staging»** — как ADR 0013/0014/0016/0017: интеграционные тесты backend-ci на PostgreSQL
    (дерево → эскалация → тикет с пометкой, отсутствие тупиков в сценариях), smoke образа (операции
    KnowledgeBase в Swagger, `401` без токена). Деплой — глава 26.

## Уточнения реализации (2026-10-12)
- **Контракт и `oasdiff`:** запрет `null` в `next_node_id` — проверка сервера (`422`), в контракте
  поле остаётся `nullable` (п. 13). У nullable-перечислений `category` в `enum` входит `null` —
  иначе по OAS 3.0 валидатор ответа отклоняет `null` (как `UserPublic.phone`, ADR 0017).
- **`PATCH` статьи** меняет и привязку (`vehicle_model_id`, `firmware_release_id`, `null` — снять);
  снимок версии включает категорию и привязку. Все проверки (категория, привязка, дерево при
  публикации) выполняются до изменения объекта: отказ не оставляет полузаписанную статью, а запрос
  проверки не сбрасывает в БД запись, нарушающую FK.
- **Ответ записи** — состояние своей записи (flush + refresh до COMMIT), а не перечитанное после
  COMMIT, где уже может быть чужая правка: одновременные правки получают каждая свой номер версии.
- **Снимок версии неизменен** — триггер `trg_append_only` (как журнал корректировок пробега,
  ADR 0006); каскадное удаление со статьёй (откат сценариев) разрешено.
- **Эскалация** блокирует узел `FOR KEY SHARE`: удаление узла ждёт создания тикета, а не ломает
  его FK (`500`). Удалённый узел — `422`, ссылка уже созданного тикета обнуляется (FK `SET NULL`),
  версия статьи в тикете остаётся.
- **`validateDecisionTree` для `guide`** — `is_valid = true` без проблем (дерева нет).
- **Поиск:** запрос до 200 символов (иначе `422`), пустой — без фильтра; запрос только из
  стоп-слов — пустой результат.
- **Сценарии (миграция `0011`)** — SQL-блоки `DO` (рендерятся offline в
  `docs/EV_ServiceDesk_Glava2_DDL.sql`); общие для всех моделей; по одному на категорию ошибки.
- **Прототипы:** web-shared и web-admin получили категорию, `updated_at`, `source_article`,
  правила проверки дерева и смысл версии; упрощения прототипа — дерево опубликованной статьи
  можно править, вариант без перехода допускается в форме и считается тупиковым (финальные
  правила — подключение API, глава 22). Мобильный прототип уже соответствует контракту
  (категория у статьи, без `null` в вариантах) — без изменений.

## Исправления по ревью (2026-10-12)
Независимое ревью: 6 находок (critical/high нет) — все исправлены, у каждой — тест.
- **История версий снятой статьи:** инженер видел в карточке тикета `source_article`, но версия
  снятой с публикации статьи отдавала `404` (п. 8 против п. 11). Персоналу открыта история статьи
  с хотя бы одной опубликованной версией; черновое содержание по-прежнему видит только admin
  (RBAC-05 уточнено).
- **Эскалация блокирует узел `FOR SHARE`** (было `FOR KEY SHARE`): смена типа узла (эскалация →
  решение) тоже ждёт создания тикета, а не только удаление.
- **Поиск:** запрос с управляющими символами — `422` (NUL давал `500`); запрос приводится к NFC,
  как текст статей.
- **Однострочные поля** (`title`, `label`) отклоняют и C1 (`U+0080–U+009F`), как многострочные.
- **Откат `0011`** опознаёт сценарии по версии 1 с их заголовком и временем публикации самой
  ранней такой версии (одна транзакция миграции), а не по текущему заголовку: копия
  администратора с тем же заголовком не удаляется, переименованный сценарий — удаляется.
- Тесты: сценарии чек-листа — по заголовкам миграции `0011`; блокировка эскалации — через
  сценарии удаления и правки узла; append-only версии — и для `DELETE`.

## Последствия
- Миграции: категория, поиск и версии статей, версия источника в тикете, сценарии; экспорт DDL/ERD.
- Глоссарий baseline v1.6: «Дерево решений» (уточнение), «Эскалация в тикет», «Тупик дерева
  решений», «Черновик статьи», «Версия статьи».
- Прототипы (web-shared, web-admin, mobile) приводятся к контракту 1.5.0 без новых экранов.
- Правка дерева опубликованной статьи требует снять её с публикации — клиенты на это время статьи
  не видят; если это станет проблемой — черновая редакция рядом с опубликованной (новый ADR).
