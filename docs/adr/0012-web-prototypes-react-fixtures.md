# 0012. Прототипы веб-кабинета инженера и админ-панели — React на фикстурах, без изменения контракта v1

**Статус:** Принято, 2026-10-10 (владелец проекта, Issue #40)

## Контекст
Глава 8 требует прототипы: канбан-доска тикетов инженера с фильтрами по SLA, карточка тикета с контекстом
авто и быстрыми ответами из базы знаний, тёмная тема инженера; админ-панель — конструктор регламентов ТО,
конструктор статей, лента публикаций, дашборд. Проверки: адаптивность под Full HD (1920×1080), подсчёт кликов
для типовых операций инженера. ТЗ (раздел 9) предполагает прототипы в Figma, но Figma на тарифе Starter
(ADR 0010). Мобильный прототип уже сделан в коде на фикстурах (ADR 0011). В `web-engineer/` и `web-admin/`
до главы 8 была только витрина дизайн-системы, тестов в веб-воркспейсах не было.

При сверке с контрактом `docs/openapi.yaml` 1.1.0 нашлись расхождения с ТЗ:
- «приоритизация по SLA»: в `Ticket` нет поля приоритета, есть `sla_due_at` и `is_overdue`; у `GET /tickets`
  из SLA-фильтров есть только `overdue`;
- «быстрые ответы из базы знаний»: отдельной сущности «шаблон ответа» нет;
- «лента публикаций»: `GET /notifications` доступен только `client`, у админа операции чтения
  опубликованного нет;
- в `Ticket` (элемент списка) нет модели авто и краткого описания — на карточке канбана их не показать
  без `GET /tickets/{id}`;
- «конструктор статей (гайды, файлы прошивок, видео)»: у `KnowledgeArticle` есть только текст `content`,
  вложений нет.

## Варианты
- **Носитель:** Figma (Starter) / React + Tailwind на фикстурах / Prism mock по OpenAPI.
- **SLA:** добавить `priority` в контракт / выводить срочность из `sla_due_at`.
- **Быстрые ответы:** новая сущность шаблонов / статьи базы знаний.
- **Расхождения контракта:** исправить в главе 8 (контракт 1.2.0) / зафиксировать как открытые вопросы
  глав 13–15.
- **Тесты:** без тестов (ручная проверка) / Vitest + Testing Library.

## Решение
1. **React + Tailwind на фикстурах.** Прототипы — это клиенты глав 21–22 без сети. Экраны зависят от
   интерфейсов `EngineerRepository` / `AdminRepository` (`web-shared/src/data/repository.ts`): методы
   названы по `operationId`, типы — алиасы схем OpenAPI (`models.ts`). Прототип — `PrototypeRepository`
   (`web-shared/src/prototype/`) на фикстурах в памяти; главы 21–22 подставят реализацию на
   `createApiClient` без изменения экранов. Фикстуры согласованы с мобильным прототипом (модели, авто,
   статьи, деревья решений, тикет #1042). Prism не используется: прототип работает без Docker и детерминирован
   в тестах. Сценарии ревью («Нет сети», «Пусто», тема, сброс) — панель «Демо».
2. **SLA без изменения контракта.** Состояние SLA — `overdue` (`is_overdue` или срок прошёл),
   `due_soon` (до срока ≤ 1 ч), `ok`, `closed` (решён) — функция `slaState`
   (`web-shared/src/data/sla.ts`). Фильтр канбана — «Все / Просрочен / Истекает < 1 ч / В норме», в колонке —
   сортировка по `sla_due_at`. Порог «истекает» — константа веба `DUE_SOON_MS`; если владелец захочет
   настраивать его или приоритет — глава 13.
3. **Быстрые ответы — статьи базы знаний.** В карточке тикета поиск по опубликованным статьям
   (`listKnowledgeArticles`, `search`), статьи модели авто клиента — выше; «Отправить» сразу публикует
   заголовок и текст статьи в чат (`createTicketMessage`), «Вставить в ответ» — в поле ответа для правки.
   Ссылки на статью в приложении клиента в контракте нет — открытый вопрос главы 14.
4. **Дашборд — только `/analytics/*`:** `getTicketResolutionStats`, `listProblemModels`,
   `getMaintenanceConversionStats`; период 7/30/90 дней. Значения в прототипе — детерминированные,
   пропорциональные длине периода (реальный расчёт — глава 16).
5. **Расхождения контракта — открытые вопросы, контракт v1 не меняется:**
   - чтение ленты публикаций админом — метод `listPublishedNotifications` в `AdminRepository` помечен как
     отсутствующий в v1; аддитивная операция (например, `GET /notifications` для `admin` с фильтрами) —
     решение в главе 15;
   - модель авто и краткое описание в элементе `TicketList` — аддитивные поля, решение в главе 13; до тех пор
     карточка канбана показывает номер, категорию, SLA, дату и исполнителя;
   - вложения статей (фото, видео, файлы прошивок) — глава 14.
6. **Правила, которые проверяет backend, в прототипе упрощены:** переходы статуса (`new → in_progress` —
   только через claim; `in_progress ↔ waiting_vendor`, `→ resolved`, `resolved → in_progress`), claim чужого
   тикета — 409, статус и сообщения — только назначенному инженеру (403, RBAC_MATRIX), проверка дерева решений
   (`DEAD_END`, `UNREACHABLE`, `MULTIPLE_ROOTS`, `BROKEN_REFERENCE`). Финальные правила — главы 12–14.
7. **Подсчёт кликов и Full HD — автоматически и скриншотами.** Тесты Vitest + Testing Library (jsdom,
   dev-зависимости в корне) в `web-engineer`, `web-admin`, `web-shared`; `npm test` — в `web-ci`. Клик —
   одно нажатие мыши, ввод текста не считается. Full HD проверяется в браузере (нет горизонтальной прокрутки
   при 1920×1080), скриншоты — `docs/design/web-prototype/`. Тему можно задать ссылкой `?theme=light|dark`
   (не сохраняется) — для ревью и скриншотов.

## Последствия
- Отступление от ТЗ («прототипы в Figma»), как в ADR 0011: прототипы утверждает владелец по сборке
  (`npm run dev -w web-engineer` / `-w web-admin`) и скриншотам, а не по ссылке на Figma.
- Экраны прототипа — основа глав 21–22: подключение API меняет реализацию репозитория, добавляет вход
  сотрудника (`POST /auth/staff/login`, глава 10), пагинацию и серверные фильтры `GET /tickets`, обновление
  доски в реальном времени (глава 13/17).
- Компоненты веба дополнены (`Select`, `TextArea`, `Chip`, `Badge`, состояния) — на токенах главы 6;
  выбранный чип — как во Flutter (`primary` + `on-primary`).
- Три открытых вопроса контракта (п. 5) переходят в главы 13–15; при их решении — аддитивная версия
  контракта (ADR 0007).
