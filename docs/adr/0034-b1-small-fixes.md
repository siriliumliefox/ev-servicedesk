# 0034. Мелочи исследовательского тестирования B1: тексты ошибок, повтор уведомления о прошивке, минимум регламента, версия регламента

**Статус:** Принято, 2026-10-19 (Issue #105, S4; fix-PR до бета-пилота по ADR 0029 п. 4; решения —
рекомендации агента, приняты по правилу владельца 2026-10-12)

## Контекст
B1 (глава 23) оставил бэклог некритичных находок (№1, 6, 7, 13, 15, 16, 17); при исправлении #111
нашлась ещё одна — в чате мобильного клиента сообщение об ошибке закрывало поле ввода. Контракт v1
заморожен (ADR 0007): ломающие изменения схемы — только новые значения ENUM в ответах.

## Решение
1. **№1 — текст TICKET_RESOLVED по роли.** Клиенту: «Обращение решено — если проблема вернулась,
   создайте новое» (переоткрывает персонал); персоналу — прежний «сначала переоткройте». Код тот же.
2. **№6 — повтор уведомления о прошивке.** `createNotification` и `previewNotificationAudience` для
   релиза, о котором уведомление уже опубликовано (в том числе самим `createFirmwareRelease`), — 409
   `FIRMWARE_ALREADY_NOTIFIED`; предпросмотр предупреждает тем же ответом. Ручная публикация прошивки
   остаётся для релиза без уведомления (заведённого не через API). Две ручные публикации одного
   релиза упорядочены `FOR UPDATE` строки релиза. UNIQUE в БД не вводится: на стендах могут быть
   дубли прошлых прогонов, миграция упала бы на них.
3. **№7 — две замены в одну дату: по спецификации, без изменений.** E5 (глава 5): при равной дате
   текущая — последняя зафиксированная, даже с меньшим пробегом. История ТО не редактируется, и так
   инженер исправляет ошибочно внесённую замену (тот же день, верный пробег). Правило закреплено
   тестом `test_same_date_lower_mileage_becomes_current`.
4. **№13 — регламент.** `interval_km` меньше 500 — 422 («1» вместо «10 000» давало выработку
   1 600 000 %). Проверяет сервер и описание операции, схема остаётся `minimum: 1` — как у
   `interval_months > 1200` (схема v1 заморожена, ADR 0007). У версии регламента — дата
   (`created_at`, была в БД) и автор (`created_by_user_id`, миграция 0019; у старых версий — null):
   отложенное в ADR 0026 (U-44). Автор — только id: регламенты читает и инженер; админ-панель
   показывает телефон администратора из списка пользователей.
5. **№15 — тексты 422.** `details.fields[].msg` — по-русски по типу ошибки Pydantic («Обязательное
   поле», «Не меньше 500», «Нужен UUID», «Допустимые значения: …»), у своих проверок — их текст без
   префикса «Value error, »; `type` остаётся машинным кодом. Введённое значение в текст не попадает.
6. **№16 — refresh после завершения всех сессий.** Refresh-токен, отозванный блокировкой, сбросом
   или сменой пароля, отзывом согласия (`revoked_at` не позже `sessions_revoked_at`), — 401
   «Учётная запись недоступна» или «Сессия завершена — войдите заново», без события
   `auth.refresh_reuse` и без повторного отзыва: это не повтор токена. 404 «Тикет не найден» после
   переназначения — по ADR 0017 п. 6 (существование чужого тикета не раскрывается); кабинет
   инженера и так показывает «тикет передан» по закрытию WebSocket.
7. **№17 — вход сотрудника на узком экране.** Форма — `w-full max-w-96`: на 398 px — 350 px без
   горизонтальной прокрутки (было 384 px + поля страницы).
8. **Чат мобильного клиента.** Ошибка отправки — над полем ввода («Не отправлено. …»), а не
   всплывающим сообщением: оно на 4 с закрывало поле и «Отправить».
9. Контракт 1.16.0 — аддитивно (`oasdiff` без ломающих).

## Последствия
- Клиент не получает от сервера совет, которому не может последовать; администратор не разошлёт
  второе уведомление о той же прошивке; опечатка в регламенте не «краснит» все авто модели.
- Разработчик интеграции видит в 422 понятный русский текст; клиенты по-прежнему показывают свои
  тексты по коду и полю.
- Блокировка клиента больше не порождает ложные события повтора refresh-токена в журнале
  безопасности.
