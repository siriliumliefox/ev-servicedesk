# 0029. Тестирование безопасности: OWASP Top 10:2025 по сервисам, автотест RBAC и IDOR, ZAP на стенде из образа, отзыв access-токенов, анонимизация ПД

**Статус:** Принято, 2026-10-18 (Issue #120, grilling Q1–Q12 — все рекомендации приняты владельцем;
пп. 11–17 — рекомендации агента, приняты по правилу владельца 2026-10-12)

## Контекст
Глава 25 требует: чек-лист OWASP Top 10 по каждому сервису, тест IDOR (чужой тикет/авто подменой ID),
защиту от SQL-инъекций и XSS в тикетах и чате, автоматизированную проверку RBAC-матрицы (глава 1) по
каждому эндпоинту, пентест или сканирование (OWASP ZAP); все уязвимости классифицированы, критичные
закрыты, повторное сканирование — 0 критичных; DoD — отчёт по безопасности приложен к пояснительной
записке. Факты на начало главы:
- каждая операция `docs/openapi.yaml` несёт `x-required-roles` и `x-rbac-action` (строка
  `RBAC_MATRIX.md`); `test_deny_by_default` требует проверку ролей у каждого маршрута, обход «все
  маршруты → 401» есть; обход «роль × операция → 403» — только для тегов Tickets/Uploads, матрица
  object-level — только для тикетов;
- SQL — только ORM и параметры, LIKE экранируется; веб выводит тексты как текст React, Flutter —
  `Text` и `MarkdownBody` без картинок; сервер принимает HTML в статьях, хотя контракт обещает
  «CommonMark без HTML»;
- в CI из средств безопасности — только gitleaks; нет проверки зависимостей, dependabot, bandit, ZAP;
- заголовков безопасности в backend нет, Swagger открыт во всех окружениях, образ работает от root;
- uvicorn пишет журнал доступа со строкой запроса — `GET /users?search=<телефон>` попадает в логи;
- открыты #102 (блокировка входа сотрудника по номеру, access-токен живёт после выхода, политика
  паролей — только длина) и #103 (SMS-код уходит заблокированному клиенту);
- отложено «до главы 25»: анонимизация ПД в 15-дневный срок (ADR 0013 п. 9, 0017 п. 12, 0021,
  99-З п. 14/19), сроки хранения журнала доставок и push-токенов (ADR 0019), подтверждение владения
  Telegram (ADR 0013, 0021 п. 13), смена пароля самим сотрудником (ADR 0026), сквозное маскирование
  логов (99-З п. 2), юридический текст политики (ADR 0022) и основание трансграничной передачи
  (99-З п. 12);
- staging-сервера нет до главы 26; стенд — `scripts/integration_stack.sh` из образа
  `backend:staging-<sha>` (ADR 0027 п. 5).

## Варианты
- **Эталон:** Top 10:2021 / Top 10:2025 + API Top 10:2023 + сокращённый MASVS / полный MASVS.
- **Пентест:** только ZAP / ZAP + агент-сессия «чёрный ящик» / внешний пентестер.
- **Классификация:** S1–S4 / CVSS → S1–S4 / закрывать всё.
- **ZAP:** локально / отдельный workflow на стенде из образа / в `ci-gate` на каждом PR.
- **Блокировка входа:** по номеру (как было) / по паре «номер + IP» и общий потолок на номер / CAPTCHA.
- **Отзыв access:** короткий TTL (как было) / список отозванных `jti` в Redis / версия токенов в БД.
- **SMS заблокированному:** отказ с кодом ошибки / тот же ответ без отправки.
- **Telegram:** как есть / одноразовый код от бота / Telegram Login Widget (HMAC).

## Решение
1. **Эталон (Q1).** OWASP Top 10:2025 — основной чек-лист; для backend — сверка с OWASP API Security
   Top 10:2023 (BOLA, неограниченный расход ресурсов); мобильное приложение — сокращённый MASVS
   (хранение токенов, сеть, логи). Сервисы — модули backend (Auth, Vehicle, Aggregates, Tickets, KB,
   Notifications, Analytics), веб-кабинеты инженера и администратора, мобильное приложение. В отчёте —
   таблица «пункт × сервис»: PASS / N/A / находка со ссылкой на тест или доказательство.
2. **Пентест (Q2).** ZAP (активное сканирование API по контракту с токенами каждой роли + пассивное
   сканирование веб-кабинетов) и независимая агент-сессия «чёрный ящик» по заданию, как в главе 23
   (ADR 0027 п. 11). Отклонение от чек-листа: внешнего пентестера нет; внешний пентест — после релиза
   по решению владельца (глава 28).
3. **Классификация (Q3).** Каждой находке — базовая оценка CVSS v3.1 и уровень S1–S4: Critical/High
   (≥ 7,0) → S1/S2, Medium (4,0–6,9) → S3, Low (< 4,0) → S4. Для находок безопасности это уточняет
   ADR 0027 п. 7 («уязвимость — S1»). Критичные — S1/S2: закрываются в главе обязательно; S3 —
   в главе или в Issue с обоснованием; S4 — бэклог. «0 критичных» повторного сканирования — 0 находок
   ZAP уровня High и 0 открытых подтверждённых S1/S2.
4. **Объём (Q4).** В главу входят #102 и #103; из #74 — пункт C15 (ограничения длины в схемах),
   только если ZAP или тесты покажут вход без ограничения. #104, #105, #111–#114, #73 и остальное
   из #74 — отдельные fix-PR до бета-пилота (глава 27).
5. **Исправления (Q5).** Один PR главы: на каждую находку — регрессионный тест и исправление;
   ломающее изменение контракта — отдельный коммит и `docs/api-breaking-allowed.txt` (ADR 0007).
6. **RBAC и IDOR (Q6).** `backend/tests/api/test_rbac_matrix.py`: каждая роль × каждая защищённая
   операция контракта (роли — из `x-required-roles`): чужая роль — 403, своя — не 401/403. Матрица
   object-level по образцу тикетов — для авто, агрегатов и ТО, уведомлений, вложений, статей и
   пользователей (владелец / чужой / бывший владелец / engineer / admin). Правило кодов: запрещённая
   роль — 403; чужой или невидимый объект — 404 (существование не раскрывается). Сценарий E2E-33
   матрицы `docs/specs/e2e_matrix.yaml` выполняется этими тестами.
7. **ZAP (Q7).** `.github/workflows/security.yml`: стенд `integration_stack.sh` из образа
   `backend:staging-<sha>` (по digest, как `regression.yml`) + ZAP в Docker (образ закреплён по digest):
   API-скан по `docs/openapi.yaml` от имени client, engineer и admin (токены — тестовые номера и
   `E2E_CODE`, пароли сотрудников — одноразовые секреты стенда), baseline веб-кабинетов на
   production-сборке (`vite preview`). Запуск вручную и раз в неделю, в `ci-gate` не входит. Сжатые
   отчёты — `docs/reviews/security/<дата>/`, сырые — артефакт workflow. В главе 26 — повтор на сервере.
8. **Настройки (Q8, A02).** Backend добавляет `X-Content-Type-Options: nosniff`,
   `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy:
   same-origin` ко всем ответам и `Cache-Control: no-store` к ответам `/auth/*`; `/docs`, `/redoc` и
   `/openapi.json` отключены при `ENVIRONMENT=production`; образ работает от непривилегированного
   пользователя. HSTS, CSP заголовком и `frame-ancestors` — nginx главы 26.
9. **Цепочка поставок (Q9, A03).** В `ci-gate`: `pip-audit` (backend), `npm audit --omit=dev
   --audit-level=high` (веб), `osv-scanner` для `mobile/pubspec.lock`; `.github/dependabot.yml` —
   раз в неделю для pip, npm, pub и github-actions; правила `S` (bandit) в ruff, исключения — `noqa`
   с объяснением. Уязвимости уровня High и выше обновляются в главе.
10. **XSS и HTML (Q10).** Сервер отклоняет HTML-теги в содержимом статьи (`422 VALIDATION_ERROR` —
    исполнение контракта «CommonMark без HTML», схема не меняется). Набор XSS- и SQLi-нагрузок —
    через чат, описание тикета, статьи, поиск и фильтры: API хранит текст как есть и не отвечает
    500; Playwright — скрипт в веб-кабинетах не выполняется; виджет-тест Flutter — `MarkdownBody` не
    выводит HTML.
11. **Вход сотрудника (#102, B1 №3).** Лимит неудач — по паре «номер + IP» (5 за 15 мин), по IP — 20
    за 15 мин (как было), общий потолок на номер — 300 в час (распределённый подбор; при пароле
    п. 13 подбор недостижим). Злоумышленник со своего адреса больше не запирает сотрудника. Срабатывание
    потолка пишется в лог `WARNING` с маской номера. Сброс пароля администратором и смена пароля
    снимают все счётчики номера.
12. **Отзыв access-токенов (#102, B1 №4).** Выход вносит `jti` предъявленного access-токена в
    список отозванных (Redis, TTL — остаток жизни токена). Сброс пароля администратором, смена пароля,
    блокировка и отзыв согласия ставят пользователю отметку «токены до момента T недействительны»
    (Redis, TTL — срок жизни access). `get_current_user` проверяет обе отметки одним `MGET`; Redis
    недоступен — 503 (fail closed). Открытые WebSocket закрываются с 4401 не позже чем через 30 с —
    той же проверкой, что и блокировка (ADR 0021 п. 3).
13. **Политика паролей (#102, B1 №5).** Длина 12–128 и оценка `zxcvbn` не ниже 3 из 4 с номером
    телефона как известными данными; слабый пароль — `422 VALIDATION_ERROR` «Пароль слишком простой»
    (схема не меняется). Применяется к созданию сотрудника, сбросу и смене пароля.
14. **Смена пароля сотрудником (ADR 0026).** `POST /auth/staff/password` (`changeStaffPassword`,
    engineer/admin; контракт 1.12.0, аддитивно): текущий и новый пароль → новая пара токенов; все
    прочие сессии и access-токены отзываются; неверный текущий пароль — `400 PASSWORD_INVALID`,
    попытка входит в лимит п. 11. Строка RBAC-матрицы — «Регистрация/авторизация (свой аккаунт)»,
    только роли с паролем (уточнение RBAC-06). Форма — в обоих веб-кабинетах.
15. **SMS заблокированному (#103).** `POST /auth/phone/request-code` для заблокированного или
    анонимизированного клиента и для номера сотрудника отвечает так же, как обычно (200, `ttl_seconds`),
    но код не создаётся и SMS не отправляется; лимиты считаются одинаково. Ответ не раскрывает, чей
    номер и заблокирован ли он; платные SMS не уходят. Отказы `ACCOUNT_DISABLED` и
    `STAFF_PASSWORD_LOGIN` на verify-code остаются второй линией.
16. **Telegram (ADR 0013, 0021 п. 13).** `POST /auth/telegram/link` принимает данные Telegram Login
    Widget: `telegram_id` — поле `id`, плюс `auth_date`, `hash` и необязательные поля виджета;
    сервер проверяет HMAC-SHA256 с ключом SHA-256(токен бота), `auth_date` не старше 24 ч. Новые
    поля в схеме необязательны (аддитивно, ADR 0007), обязательны для сервера — как прочие
    серверные границы строже схемы (ADR 0013 п. 8): без подписи — 422. Без `TELEGRAM_BOT_TOKEN` —
    `503 TELEGRAM_UNAVAILABLE`. Бот и токен — владелец (глава 27).
17. **Маскирование логов (99-З п. 2).** Журнал доступа uvicorn выключен; свой журнал пишет метод,
    шаблон маршрута, статус и длительность — без строки запроса. Фильтр корневого логгера маскирует
    телефоны, VIN и JWT в любом сообщении (вторая линия). Тест прогоняет сценарии всех сервисов и
    проверяет, что в логах нет телефонов, VIN, кодов, токенов и текстов.
18. **Анонимизация (99-З п. 14, 19; ADR 0013 п. 9).** Worker `app.workers.privacy` раз в час берёт
    очередь — клиентов без действующего согласия по последнему `withdrawn_at`, ещё не
    анонимизированных — и для каждого: SMS «данные удалены» (best effort, до обнуления телефона; не
    для тестовых номеров), затем одной транзакцией: `phone`, `telegram_id` → NULL, `anonymized_at`;
    авто — мягко удаляются, VIN → `00000000000000000` (`vehicle_guard` разрешает это только удалённому
    авто; формат и контракт не меняются); описания тикетов и тексты сообщений клиента → «Удалено по
    запросу клиента»; открытые тикеты → `resolved`; строки вложений удаляются, объекты
    `tickets/{id}/` — после COMMIT (сбой — повтор при следующем проходе по признаку анонимизации);
    push-токены, доставки, входящие уведомления и refresh-токены удаляются; `pd_consent` сохраняется
    (доказательство, ст. 5 п. 7). Клиент в очереди дольше 14 дней — лог `ERROR`.
19. **Сроки хранения (99-З п. 3, ADR 0019).** Тот же worker раз в сутки удаляет refresh-токены,
    истёкшие или отозванные более 30 дней назад; отозванные push-токены старше 30 дней — с их
    доставками; журнал доставок старше 180 дней.
20. **Отчёт (Q12).** `docs/reviews/SECURITY_25.md` (шаги чек-листа, стенд, таблица OWASP, находки с
    CVSS и S1–S4, ZAP до/после, отложенное) — источник истины; приложение к пояснительной записке —
    `docs/Prilozhenie_Glava25_Security.docx` в стиле приложения главы 1.
