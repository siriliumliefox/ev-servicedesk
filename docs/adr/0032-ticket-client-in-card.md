# 0032. Клиент в карточке тикета и признак блокировки: `TicketDetail.client`, ответ заблокированному не запрещается

**Статус:** Принято, 2026-10-19 (Issue #104, находка №9 исследовательского тестирования B1 главы 23,
S3; fix-PR до бета-пилота по ADR 0029 п. 4; решение — рекомендация агента, принята по правилу
владельца 2026-10-12)

## Контекст
B1 (глава 23): в `GET /v1/tickets/{id}` у инженера нет клиента — ни его учётной записи, ни признака
блокировки; сообщение заблокированному клиенту сервер принимает (201), и инженер не знает, что ответ
сейчас никто не прочитает. Issue просит решить, какие данные клиента видит инженер (ПД — ADR 0005,
0017 п. 12) и что показывать при блокировке. Факты:
- владелец тикета — `vehicle.user_id`, неизменяем (ADR 0003); отдельного `client_id` у тикета нет;
- инженер и администратор уже видят телефон клиента: автор-клиент в `TicketMessage.author`
  (`UserPublic`) отдаётся персоналу целиком, скрываются только контакты сотрудника от клиента
  (ADR 0017 п. 12) — то есть доступ персонала к телефону клиента уже принят;
- глоссарий «Блокировка пользователя» (v1.9): вход запрещён, данные и открытые тикеты сохраняются,
  уведомления заблокированному не отправляются, разблокировка возвращает доступ;
- до первого сообщения клиента в чате (тикет создан с одним описанием) инженер не видит клиента
  вообще.

## Варианты
- **Данные клиента:** отдельный объект с id и признаком блокировки / `UserPublic` владельца
  (id, телефон, роль, `is_active`, Telegram, дата регистрации) / ничего, только `is_active`.
- **Сообщение заблокированному:** 409 `CLIENT_BLOCKED` / принимать и предупреждать в кабинете.

## Решение
1. **`TicketDetail.client` — `UserPublic` владельца авто** (контракт 1.14.0, аддитивно, поле
   обязательное в ответе). Новых ПД персоналу не открывается: тот же объект он уже получает в
   авторе сообщений клиента. Клиенту в его же тикете — он сам. Анонимизированный клиент —
   `phone: null` и `telegram_id: null`, как везде (ADR 0029). Поле есть во всех ответах с
   `TicketDetail`: getTicket, claim, смена статуса, назначение, createTicket.
2. **Сообщение заблокированному принимается (201).** Блокировка обратима, тикеты заблокированного
   по глоссарию сохраняются: ответ, отправленный до разблокировки, клиент прочитает после неё, а
   запрет оставил бы его без ответа и не позволил бы администратору довести тикет. Push ему не
   уходит — как всем уведомлениям заблокированного.
3. **Кабинет инженера:** в шапке карточки — «Клиент: <телефон>» (без ПД — «#id (данные удалены)») и
   красная метка «Заблокирован»; над перепиской — пояснение: войти клиент не может, уведомления ему
   не приходят, ответ сохранится и будет виден после разблокировки; та же подсказка — у поля ответа.
   Поле ответа не блокируется. Прототип `web-shared` берёт клиента из своих пользователей —
   блокировка в демо-админке видна в карточке.
4. Мобильный клиент поле не использует (клиент знает, кто он); список тикетов и событие
   `ticket.updated` (`Ticket`) не меняются.

## Последствия
- Инженер видит, кому отвечает, ещё до первого сообщения клиента, и не пишет «в пустоту» вслепую:
  блокировка видна в шапке, над перепиской и у поля ответа.
- Ответ на `getTicket` — на один запрос к БД больше (строка владельца по первичному ключу).
- `docs/RBAC_MATRIX.md` не меняется: операции и роли те же, доступ к телефону клиента у персонала
  уже был.
