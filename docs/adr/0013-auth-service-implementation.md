# 0013. Auth Service: SMS через A1, токены, RBAC, лимиты, «staging» до главы 26

**Статус:** Принято, 2026-10-11 (владелец проекта, Issue #46). Развивает ADR 0005.

## Контекст
Глава 10 требует: вход по телефону с SMS-кодом (TTL в Redis), JWT access/refresh, RBAC в API,
rate limiting попыток, тесты (unit, интеграция, безопасность, 50 одновременных SMS) и DoD
«Auth Service на staging, Swagger соответствует контракту». Staging-сервера нет до главы 26
(ADR 0008). SMS-провайдер не был выбран (`.env.example`). Контракт v1 (ADR 0007) и
мобильный прототип (ADR 0011, глава 9) используют 4-значный код.

## Варианты
- **«На staging»:** поднять сервер сейчас / засчитать сборку и публикацию образа / оставить PARTIAL.
- **SMS-провайдер:** A1 / RocketSMS / SMSp.by и др.
- **Код локально:** писать в лог / отладочный эндпоинт только в local.
- **Длина кода:** 4 цифры (контракт, прототип) / 6 цифр (изменение мобильного клиента).
- **Refresh:** JWT / непрозрачная строка; без ротации / ротация с обнаружением повторного использования.
- **RBAC:** ASGI-middleware со списком публичных путей / зависимости FastAPI на маршрутах + тест.

## Решение
1. **«На staging» = образ `backend:staging` в ghcr.io, прошедший smoke-тест** (решение владельца).
   `cd-staging.yml` собирает образ, запускает `scripts/smoke_backend_image.sh` с
   `ENVIRONMENT=staging` и Redis (health, все операции Auth в Swagger, `request-code` → 200,
   повтор → 429, `/me` без/с поддельным токеном → 401, отладочного маршрута нет в таблице
   маршрутов, образ без `ENVIRONMENT` не стартует) и только потом публикует; тот же
   smoke-тест — job `image-smoke` в `backend-ci` на каждом PR. Реальный деплой на сервер —
   глава 26. Отклонение от формулировки DoD аналогично ADR 0008.
2. **SMS — A1 «Smart-рассылка»** (smart-sender.a1.by, HTTP API 1.2.3) за интерфейсом
   `SmsProvider`: `POST /api/send/sms`, авторизация `user` (msisdn) + `apikey` **в теле POST**
   (не в URL), номер без «+», `dlr_timeout` = TTL кода в минутах. Лимит A1 — 10 запросов/с:
   ограничитель частоты на процесс (`SMS_PROVIDER_RPS` ≤ 10) с потолком ожидания очереди
   6 с (дальше — сразу 503). Таймауты HTTP 5 с (соединение 3 с). Повтор — только когда
   запрос точно не ушёл: ошибка соединения или код A1 7. Таймаут ответа/непонятный ответ —
   «доставка неизвестна»: без повтора (иначе платный дубль), код остаётся действующим,
   пауза не снимается. Ошибки 100–103 (недопустимый получатель) → 422 `PHONE_NOT_SUPPORTED`,
   прочие → 503 `SMS_UNAVAILABLE`; если SMS точно не ушло, код удаляется, пауза и лимит
   номера возвращаются. Ошибки учётной записи (3–6, 8, 104) пишутся в лог как ERROR с
   расшифровкой, без ключа. Отправка идёт в отдельном пуле потоков (50), чтобы медленный
   A1 не занял общий пул остальных эндпоинтов.
   A1 должен разрешить IP сервера; учётные данные (`SMS_PROVIDER_USER`, `SMS_PROVIDER_API_KEY`,
   `SMS_SENDER`) вводит владелец. `fake` — для local/test; в production запрещён.
3. **Код локально — только `GET /v1/_debug/sms/last-code`** при `ENVIRONMENT=local` и
   `SMS_PROVIDER=fake`: в других случаях роутер не подключается и не входит в OpenAPI; в логи
   код не пишется. `ENVIRONMENT` — только `local`/`test`/`staging`/`production`; образ
   по умолчанию `production` (fail closed), локальный compose явно задаёт `local`.
4. **Код — 4 цифры** (как в контракте и прототипе; `SMS_CODE_LENGTH`), TTL 120 с,
   одноразовый. В Redis — `HMAC-SHA256(телефон:код, SMS_CODE_SECRET)` и счётчик попыток.
   Каждый ввод сначала атомарно (Lua) резервирует попытку кода и суточного счётчика, и
   только потом код сравнивается: параллельные запросы не обходят лимиты (регрессионный
   тест — 40 одновременных вводов). Верный код попытку возвращает; удаляется только
   проверенный код (compare-and-delete).
   Слабость 4 цифр компенсируется лимитами (п. 6): ≤ 5 вводов на код, ≤ 5 кодов в час,
   ≤ 20 неверных вводов в сутки на номер — не более 0,2 % шанса подбора в сутки.
   Переход на 6 цифр — без изменения контракта, вместе с мобильным клиентом (глава 20).
5. **Токены:** access — JWT HS256 (15 мин; `iss`, `aud`, `typ=access`, `jti`; алгоритм
   фиксирован). Роль и активность при каждом запросе берутся из БД, а не из токена.
   Refresh — случайная строка (`token_urlsafe(48)`, 30 дней), в БД только SHA-256
   (ADR 0005). Ротация при каждом `/auth/refresh` (`SELECT … FOR UPDATE`); предъявление
   отозванного токена отзывает все токены пользователя. В пересекающихся сценариях (ротация,
   отзыв всех токенов, вход по коду, отзыв согласия) сначала блокируется строка `app_user`
   (`FOR NO KEY UPDATE`), потом его токены/согласия: reuse
   detection не пропускает токен, выданный параллельной ротацией, а вход по коду не
   читает согласие, которое в этот момент отзывается. `logout` отзывает только свой токен.
   Вне local/test приложение не стартует с секретами-заглушками или короче 32 символов.
6. **Rate limiting (N-06), Redis, атомарно (MULTI/EXEC):** запрос кода — пауза 60 с,
   5 в час на номер, 30 в час на IP; ввод кода — 5 на код, 20 неверных в сутки на номер;
   вход персонала — 5 неудач за 15 мин на номер, 20 на IP (попытка учитывается до проверки
   пароля, успешный вход её возвращает). Ответ — 429 `RATE_LIMITED` с `Retry-After`.
   OpenAPI 1.2.0 (неломающие изменения): 429 у `/auth/staff/login`, заголовок `Retry-After`
   в `RateLimited`, коды ошибок и серверные границы в описаниях операций.
7. **RBAC — зависимость `require_roles` на каждом защищённом маршруте** (FastAPI выполняет
   её до обработчика, как middleware): 401 без/с негодным токеном, 403 при чужой роли.
   Те же роли попадают в `x-required-roles` сгенерированного OpenAPI. Deny by default
   обеспечивает тест: непубличный маршрут без проверки ролей валит CI, роли сверяются с
   `docs/openapi.yaml`. Object-level проверки — в сервисах.
8. **Сценарии входа:** `verify-code` без действующего согласия и без `pd_policy_version` →
   422 `PD_CONSENT_REQUIRED`, код не расходуется. Согласие с новой редакцией заменяет
   старое. Персонал по SMS не входит (400 `STAFF_PASSWORD_LOGIN`), заблокированный клиент —
   400 `ACCOUNT_DISABLED`. Пароли персонала — argon2id; при неизвестном номере хэш всё равно
   вычисляется, чтобы время ответа не выдавало номер. Серверные границы строже контракта
   (код 4–8 цифр, `telegram_id` ≤ 50 = VARCHAR, `refresh_token` ≤ 512, без управляющих
   символов; `pd_policy_version` обрезается, пустая = нет согласия) дают объявленный 422 и
   перечислены в описаниях операций; сужать сами схемы 1.x нельзя (ADR 0007).
9. **Отзыв согласия** (`DELETE /auth/pd-consent`) фиксирует `withdrawn_at` и отзывает все
   refresh-токены. Анонимизация в течение 15 дней — фоновая задача, глава 25 (до неё —
   открытый пункт `PD_99Z_CHECKLIST.md`). Очередь — **пользователи без действующего
   согласия** по последнему `withdrawn_at`, а не все строки с `withdrawn_at`: такую отметку
   получает и согласие, заменённое новой редакцией политики.

## Последствия
- **A1 (состояние на 2026-10-11):** договор «Smart-рассылка» заключён, API-ключ выдан.
  Одобрены альфа-имена `ETSGOMEL` и `ETSAUTOGML`; `ETSAUTO` отклонено как международное
  (нужен национальный признак). В заявках назначение — уведомления об акциях; использование
  того же имени для служебных SMS с кодом входа владелец согласует с A1 (при необходимости —
  отдельная заявка «коды подтверждения»).
- **Формат запроса проверен на живом API 2026-10-11** (без учётных данных): POST без
  параметров → код 3, с фиктивными `user`/`apikey` в теле → код 4 — тело POST читается,
  ключ в URL не нужен.
- Учётные данные A1 вводит только владелец: `scripts/a1_check.py` (проверка ключа, IP,
  альфа-имени, тестовое SMS) и `scripts/set-a1-secrets.sh` (secrets окружений); ключ
  вводится скрыто и не попадает в argv, логи и репозиторий. IP для A1 — staging/production
  сервера (глава 26) и, для локальной проверки, внешний IP машины владельца; раннеры GitHub
  Actions к A1 не обращаются (тесты — на подменённом транспорте).
- `scripts/set-environment-secrets.sh` создаёт и `SMS_CODE_SECRET`;
  `SECRETS=SMS_CODE_SECRET` добавляет его без ротации `JWT_SECRET`.
- Ограничитель 10 запросов/с действует в пределах процесса; при нескольких воркерах
  `SMS_PROVIDER_RPS` делится между ними (глава 26).
- За обратным прокси uvicorn нужен `--forwarded-allow-ips=<IP/CIDR прокси>`
  (`--proxy-headers` включён по умолчанию, но доверяет только 127.0.0.1), иначе лимит по IP
  считается по адресу прокси (глава 26).
- `POST /auth/telegram/link` принимает `telegram_id` без доказательства владения (так в
  контракте v1): занять чужой id или направить уведомления не туда возможно. Проверка
  (Telegram Login Widget с HMAC или одноразовый код от бота) — вместе с ботом, изменением
  контракта по ADR 0007 (главы 15/17).
- Ревизия PR #47 (4 направления, проверка каждой находки) нашла и устранила до merge:
  обход лимитов кода и пароля параллельными запросами, пропуск токена в reuse detection,
  fail-open `ENVIRONMENT`, повтор платной SMS при таймауте, блокировку общего пула потоков,
  чтение `.env` разработчика тестами; на каждую гонку есть регрессионный тест.
- Версия `pd_policy_version` не сверяется с опубликованной редакцией политики — до текста
  политики (глава 27).
