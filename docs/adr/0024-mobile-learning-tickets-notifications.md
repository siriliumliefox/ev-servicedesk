# 0024. Мобильный клиент: обучение, дерево решений, тикеты с вложениями, чат по WebSocket, push и центр уведомлений

**Статус:** Принято, 2026-10-13 (владелец проекта, Issue #83, grill-with-docs Q1–Q13; Q3 и Q5 —
решения владельца, остальные рекомендации приняты по правилу владельца от 2026-10-12)

## Контекст
Глава 20 доводит клиентские сценарии мобильного приложения: «Обучение» (Knowledge Base Service),
«Устранение неполадок» с деревом решений и эскалацией в тикет, создание тикета с фото/видео и чат
с инженером, приём push (FCM) и центр уведомлений, новости и акции. Проверки — E2E на staging
«дерево решений → эскалация → тикет → ответ инженера в чате», push в свёрнутом и закрытом
приложении; DoD — «полный клиентский сценарий пройден без ошибок минимум 3 раза подряд разными
тестировщиками». Факты на начало главы:
- экраны есть с прототипа (глава 7, ADR 0011), все операции `ClientRepository` идут по HTTP
  (глава 18, ADR 0022); эскалация уже передаёт категорию, ход диагностики и `source_*`;
- в HTTP-режиме вложения скрыты (`supportsAttachments=false`), чат — только REST, Firebase есть
  лишь в отладочной точке входа (ADR 0019 п. 18), центра уведомлений нет (уведомления — во вкладке
  «Новости»), текст статьи (CommonMark) режется по абзацам без разметки;
- контракт 1.9.0 и AsyncAPI 1.1.1 покрывают всё нужное: presign (фото 20 МБ, видео 200 МБ, до 10),
  `attachments` у тикета и сообщения, WebSocket с `ready` и догрузкой по `after_id`, push-токены,
  `opened`. У `GET /notifications` нет фильтра по типу; тикетов в ленте нет (ADR 0019 п. 13);
- на интеграционном стеке presigned URL ведут на `localhost:9000`, а порт MinIO не опубликован —
  ни симулятор, ни iPhone файл не загрузят;
- платного Apple Developer нет — FCM на iPhone невозможен (ADR 0019 п. 20, глава 27); на Mac есть
  Android-эмулятор с Google Play (android-33); тестировщиков, кроме владельца, нет.

## Варианты
- **E2E «на staging»:** стек из образа-кандидата / ждать сервер главы 26.
- **Push в фоне:** бесплатный проект Firebase + Android-эмулятор / только `simctl push` / всё в 27.
- **«Разные тестировщики»:** владелец + 2 человека / 3 прогона владельцем / владелец + агент.
- **Чат:** WebSocket с переподключением / WebSocket + периодический опрос / только опрос.
- **Фото:** как есть (HEIC, до 20 МБ) / уменьшение до 2560 px JPEG.

## Решение
1. **E2E «на staging» (Q1)** — стек из образа-кандидата (`scripts/integration_stack.sh`, как
   ADR 0021/0022): staging-сервера нет до главы 26. `api_e2e` (Dart, `HttpClientRepository`)
   проходит сценарий «дерево решений → эскалация → тикет с фото → ответ инженера через staff API
   → сообщение пришло клиенту по WebSocket» в `mobile-e2e` на каждом PR (свой тестовый номер
   `E2E_SUPPORT_PHONE`, данные — `docs/specs/support_flow.json`); UI E2E (`integration_test`) — в
   симуляторе, результат в отчёте.
2. **Хранилище на стеке (Q2).** MinIO публикуется на `INTEGRATION_BIND:19000`, адрес presigned URL
   (`S3_PUBLIC_ENDPOINT`) задают скрипты: CI и симулятор — `http://127.0.0.1:19000`, iPhone —
   `http://<mac>.local:19000` (`device_run.sh`). Логика backend не меняется.
3. **«Разные тестировщики» (Q3) — отклонение от DoD (решение владельца).** Других тестировщиков
   нет: полный клиентский сценарий проходит **владелец 3 раза подряд в разных сессиях** (новый вход
   по SMS, разные тикеты) на iPhone по чек-листу из отчёта главы. Прогон с ошибкой обнуляет серию.
   Проверка разными людьми — бета-пилот (глава 27).
4. **Push в основном приложении (Q4).** Firebase — в `main.dart` за интерфейсом `PushChannel`;
   без `FIREBASE_*` (`--dart-define`) push выключен, центр уведомлений работает. Токен
   регистрируется после входа (`POST /push-tokens`) и при обновлении, удаляется при выходе.
   Нажатие: `type=ticket` → чат тикета; `news|promo|firmware|maintenance` → уведомление в центре и
   `POST /notifications/{id}/opened`. Push на открытом приложении — баннер внутри приложения;
   в открытом чате того же тикета не показывается.
5. **Push в свёрнутом и закрытом приложении (Q5, решение владельца).** Владелец создаёт
   бесплатный проект Firebase (Spark) с Android-приложением `com.etsavtogomel.evServicedesk` и
   передаёт ключ сервисного аккаунта и конфигурацию приложения скриптом (значения не печатаются,
   в git не попадают). Настоящий FCM проверяется на **Android-эмуляторе с Google Play**: свёрнутое
   и закрытое приложение, нажатие открывает нужный экран; на iOS обработка нажатия — `xcrun simctl
   push` в симуляторе. FCM на iPhone — глава 27 (ADR 0019 п. 20).
6. **Центр уведомлений и «Новости» (Q6).** Колокольчик со счётчиком непрочитанных в шапке
   открывает центр уведомлений — прошивки, ТО, новости, акции. Вкладка «Новости» — только новости
   и акции. Фильтр по типу — на клиенте (контракт не меняется). Тикетов в центре нет.
7. **Текст статьи (Q7)** — CommonMark через `flutter_markdown_plus` (прежний `flutter_markdown`
   снят с поддержки); картинки в v1 не показываются, ссылки — во внешнем браузере (`url_launcher`).
8. **Чат в реальном времени (Q8)** — по AsyncAPI 1.1.1: первый кадр `auth`; после каждого `ready`
   — `GET messages?after_id=` (курсор — из REST) и `GET /tickets/{id}`, дедупликация по id;
   переподключение с паузой 1 → 30 с; `4401` — refresh и переподключение (блокировка — выход),
   `4403` — стоп, `4429` — пауза 60 с; при возврате приложения — переподключение; без связи —
   «Переподключаемся…». Отдельного опроса нет: догрузка после `ready` закрывает пропуски.
9. **Вложения (Q9)** — `image_picker` (камера и галерея). Фото уменьшается до 2560 px, JPEG 85
   (всегда < 20 МБ, без HEIC); видео — как есть (`.mov`/`.mp4`), 200 МБ проверяется до загрузки;
   до 10 файлов. Загрузка по одному с прогрессом и повтором; «Отправить» — когда загружены все;
   только пока приложение открыто. Шов `AttachmentSource` — фейк для автотестов (системный выбор
   фото не нажать).
10. **Дерево решений (Q10)** — без изменений по сути: «решено» — узел без вариантов, никуда не
    пишется (в контракте некуда); эскалация подставляет категорию статьи, ход диагностики
    (редактируется), `source_article_id`/`source_node_id`. Без авто — общие статьи.
11. **Контракт (Q11)** — без изменений (1.9.0, AsyncAPI 1.1.1); backend не меняется, кроме
    compose и скриптов стека (п. 2, 5).
12. **Ответ инженера на устройстве (Q12)** — меню инженера в Terminal (`mobile/scripts/staff_menu.sh`, его
    запускают `device_run.sh` и `android_push_run.sh`): ответ в чат тикета (claim или переназначение +
    сообщение через staff API), решение, новость и акция — `backend/scripts/e2e_support.py`. Веб-кабинета
    инженера нет до главы 21. Уточнено при реализации: стек и инженер — в одном окне.
13. **SMS-код (Q13)** — остаётся 4 цифры (ADR 0013 п. 4), не в этой главе.
14. **Термины** — глоссарий v1.12: «Центр уведомлений», «Вложение».

## Последствия
- Новые зависимости клиента: `image_picker`, `web_socket_channel`, `flutter_markdown_plus`,
  `url_launcher`.
- DoD главы выполняется с отклонением п. 3 — записано здесь и в `PROJECT_STATUS.md`.
- Проверка push зависит от действия владельца (проект Firebase); без него п. 5 — `BLOCKED`.
- Android впервые запускается (эмулятор), а не только собирается: нужен cleartext к стеку в debug.
- Проверка на iPhone (3 прогона) — действие владельца; до неё глава — PARTIAL.
