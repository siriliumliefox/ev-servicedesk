# 0017. Tickets Service: SLA — срок решения, граф статусов, чат на WebSocket, вложения через S3

**Статус:** Принято, 2026-10-11 (владелец проекта, Issue #60, grilling Q1–Q23)

## Контекст
Глава 13 реализует теги Tickets и Uploads контракта (OpenAPI 1.3.2) поверх таблиц главы 2
(`ticket`, `ticket_message`, `ticket_attachment`, ADR 0004), Vehicle Service (глава 11, ADR 0014)
и Aggregates Service (глава 12, ADR 0016). Контракт и требования оставляли открытыми:
- что такое SLA: глоссарий говорил о первичном ответе («до 15 минут»), а контракт и аналитика
  считают просрочку как `resolved_at > sla_due_at` / `now() > sla_due_at` — то есть срок решения;
- нормативы SLA и «приоритизацию по категории» (поля приоритета в контракте нет);
- допустимые переходы статусов и кто их выполняет; какие тикеты видит инженер
  (RBAC_MATRIX: «все/назначенные»); пишет ли админ в чат (RBAC_MATRIX — «просмотр всех»,
  контракт — `admin` в `x-required-roles` у `createTicketMessage`);
- реал-тайм чата: «WebSocket/long-polling», вне OpenAPI;
- S3: хранилища нет ни в `docker-compose`, ни в CI; лимиты, проверка вложений, «сиротские» объекты;
- открытый вопрос ADR 0012 п. 5 (модель авто и описание в элементе `TicketList`), снимок прошивки
  (N-09) при том, что `vehicle_context` отдаёт текущую;
- ПД сотрудника в `TicketMessage.author` (`UserPublic` содержит телефон и Telegram).

## Варианты
- **SLA:** срок решения (первый ответ — метрика) / два срока (ответ и решение, новое поле) /
  срок первого ответа (переопределить аналитику и `is_overdue`).
- **Время SLA:** календарное 24/7 / рабочие часы; пауза в «Ожидает вендора» / без паузы.
- **Нормативы:** в коде / таблица из миграции / таблица с API администратора.
- **Видимость для инженера:** очередь + свои (как доступ к авто) / все на чтение.
- **Сообщение в решённый тикет:** `409` / автоматическое переоткрытие.
- **Реал-тайм:** WebSocket + Redis pub/sub / только long-polling.
- **ПД автора-сотрудника:** `null` в `phone`/`telegram_id` / новая схема автора (ломающее) / как есть.

## Решение
1. **SLA — срок решения тикета.** `sla_due_at` = `created_at` + норматив категории; вычисляется
   один раз при создании и не меняется (ни переоткрытием, ни изменением норматива, ни ожиданием
   вендора). Время календарное, 24/7. Первичный ответ — только метрика: `first_response_at` —
   первое сообщение `engineer`/`admin`, заполняется однократно (`WHERE first_response_at IS NULL`).
   Глоссарий baseline v1.5: «SLA» (уточнение), «Просроченный тикет», «Первичный ответ».
2. **Нормативы** — таблица `ticket_sla_policy` (категория → минуты), значения — миграция `0008`:
   `app_crash` 4 ч, `navigation` 8 ч, `sim` 8 ч, `audio` 24 ч, `maintenance` 48 ч. API нет
   (в контракте его нет); изменение — миграцией, конструктор — при необходимости глава 22.
3. **Приоритет** отдельным полем не вводится: он следует из категории через срок SLA. Персонал
   получает список по `sla_due_at` по возрастанию, клиент — по `created_at` по убыванию. Просрочка
   (`is_overdue`, фильтр `overdue`) вычисляется при чтении: `now() > sla_due_at` и статус не
   `resolved`; фоновой задачи нет. Порог «скоро истекает» остаётся в веб-клиенте (ADR 0012).
4. **Граф статусов:** `new → in_progress` — только claim или назначение админом;
   `in_progress ↔ waiting_vendor`; `in_progress | waiting_vendor → resolved` (`resolved_at = now()`);
   `resolved → in_progress` — переоткрытие (`resolved_at = NULL`, глоссарий «Переоткрытие тикета»).
   Статус меняет назначенный инженер или админ (по тому же графу); чужой видимый тикет — `403`.
   Вне графа — `409 INVALID_STATUS_TRANSITION`; запрос текущего статуса — `200` без изменений.
5. **Claim** атомарен (`UPDATE … WHERE assigned_engineer_id IS NULL AND status = 'new'`):
   тикет у другого — `409 TICKET_ALREADY_CLAIMED`; повторный claim своего — `200` без изменений.
   **Assign** (admin): только активный `engineer`, иначе `422 ASSIGNEE_NOT_ENGINEER`; назначение
   на `new` переводит в `in_progress`; переназначение статус не меняет; `null` возвращает
   нерешённый тикет в `new` (в очередь); на `resolved` — `409 TICKET_RESOLVED`.
6. **Доступ (RBAC-04):** client — тикеты своих авто; engineer — очередь (`new` без исполнителя) и
   назначенные ему, чужой — `404` (как `vehicles.access`, минимизация ПД); admin — все.
   Создание — только на своё активное авто, иначе `404`.
7. **Создание:** снимок текущей прошивки авто (`firmware_release_id`, может быть `NULL`);
   `source_article_id`/`source_node_id` должны существовать, узел — принадлежать статье, узел без
   статьи запрещён — иначе `422 INVALID_SOURCE_REFERENCE`; описание — 1…4000 символов после
   обрезки пробелов; лимит — 10 тикетов в час на клиента (`429` + `Retry-After`). Ограничения на
   число открытых тикетов нет.
8. **Чат:** клиент пишет в свой тикет (в т. ч. в `new`), инженер — только в назначенный (тикет из
   очереди — сначала claim, иначе `403`), админ — в любой. В `resolved` не пишет никто —
   `409 TICKET_RESOLVED` (иначе «спасибо» переоткрывало бы тикеты и портило аналитику). Текст —
   1…4000 символов; лимит — 30 сообщений в минуту на пользователя. История — по `id` по
   возрастанию, `after_id` — сообщения с `id > after_id` (догрузка после переподключения).
9. **Реал-тайм — WebSocket** `/v1/tickets/{ticketId}/ws`, только доставка сервер → клиент;
   отправка — только `POST /messages` (один путь записи: проверки, вложения, `first_response_at`).
   Авторизация — первым сообщением `{"type": "auth", "access_token": …}` в течение 5 с, иначе
   закрытие `4401`; токен в URL не передаётся (URL попадают в логи прокси). По истечении
   access-токена — закрытие `4401`, клиент переподключается и догружает через `after_id`.
   События `message.created`, `ticket.updated` (статус, исполнитель) публикуются в Redis-канал
   `ticket:{id}` (несколько экземпляров backend); при смене исполнителя доступ открытых сокетов
   проверяется заново, лишние закрываются `4403`. Описание — `docs/asyncapi.yaml` (AsyncAPI 3.0).
10. **Вложения (ADR 0004):** `POST /uploads/presign` — presigned PUT на 15 мин в
    `uploads/{user_id}/{uuid}{расширение}`; из `file_name` берётся только расширение (имя может
    содержать ПД и не хранится); MIME к подписи не привязан. При привязке к тикету или сообщению
    backend делает HEAD: префикс владельца, MIME и размер — из S3, не со слов клиента; затем
    копирует объект в `tickets/{ticket_id}/{uuid}{расширение}`. Правило жизненного цикла удаляет
    `uploads/` старше 24 ч — «сиротские» объекты чистятся сами. Допустимо: фото
    `image/jpeg|png|heic|webp` до 20 МБ, видео `video/mp4|quicktime` до 200 МБ, до 10 вложений на
    тикет или сообщение. Ошибки `422`: `ATTACHMENT_NOT_FOUND`, `ATTACHMENT_ALREADY_USED`,
    `ATTACHMENT_TYPE_NOT_ALLOWED`, `ATTACHMENT_TOO_LARGE`, `TOO_MANY_ATTACHMENTS`. При чтении
    `file_url` — presigned GET на 15 мин. Лимит presign — 60 в час на пользователя.
11. **S3:** локально и в CI — MinIO (`docker-compose`, service-контейнер backend-ci); тесты идут
    против настоящего S3 API. Вне `local` backend не стартует, если бакет недоступен (fail closed).
    Провайдер staging/production — глава 26 (99-З: размещение в РБ/ЕАЭС).
12. **ПД:** клиенту в `TicketMessage.author` для сотрудника отдаются `phone: null`,
    `telegram_id: null` (описание поля уточняется: «анонимизирован или скрыт от клиента»);
    персонал видит телефон клиента. Тексты сообщений, описания и имена файлов не пишутся в логи.
    Анонимизация тикетов и объектов `tickets/{id}/` при отзыве согласия — глава 25; push о новых
    сообщениях и статусах — глава 15 (подписка на события Redis без изменений Tickets).
13. **Контракт 1.4.0 — только аддитивно:** `Ticket.vehicle_model` (`VehicleModelInfo`) и
    `Ticket.summary` (первые 140 символов описания) — закрывает ADR 0012 п. 5;
    `TicketDetail.firmware_version_at_creation`; параметр `after_id` у `listTicketMessages`;
    `429` у `createTicket`, `createTicketMessage`, `createPresignedUpload`; длины 4000 —
    `maxLength`, а если `oasdiff` сочтёт ограничение запроса ломающим — в описании поля
    (проверка на сервере остаётся); коды ошибок — в описаниях операций.
14. **«На staging»** — как ADR 0013/0014/0016: полный цикл (реальные токены Auth → presign → PUT в
    MinIO → тикет с вложением на своё авто → карточка с моделью, прошивкой и статусами агрегатов →
    claim → чат → `resolved` → presigned GET) — интеграционный тест backend-ci на PostgreSQL и
    MinIO; smoke образа — MinIO-сайдкар, fail closed без бакета, операции Tickets/Uploads в
    Swagger, `401` без токена, WebSocket без авторизации закрывается `4401`. Деплой — глава 26.

## Последствия
- Миграция `0008` (`ticket_sla_policy`), экспорт DDL/ERD; зависимость S3-клиента в backend.
- RBAC_MATRIX: RBAC-04 — уточнены «Просмотр тикета» (engineer) и «Сообщения в чате» (admin).
- Глоссарий baseline v1.5; после merge — тег `requirements-baseline-v1.5` (ADR 0002).
- `npm run gen:api`, Swagger sync, `backend/tests/contract`; `docs/asyncapi.yaml` проверяется в docs-ci.
- Известные ограничения: SLA не учитывает рабочие часы и ожидание вендора; нормативы меняются
  только миграцией; размер загрузки ограничивается проверкой после загрузки (presigned PUT не
  ограничивает размер) — лишний объект удаляет правило жизненного цикла.
- Клиенты (мобильное приложение, web-engineer) остаются на фикстурах — главы 16, 21.
