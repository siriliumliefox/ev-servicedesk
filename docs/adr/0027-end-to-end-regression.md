# 0027. Сквозное E2E: матрица сценариев со стражем, P0 в CI (Playwright, Flutter на Android-эмуляторе), regression по опубликованному образу, RC1 принимает владелец

**Статус:** Принято, 2026-10-14 (Issue #96, grill-with-docs Q1–Q21; рекомендации приняты по правилу
владельца 2026-10-12; Q11–Q13 — решения владельца)

## Контекст
Глава 23 требует матрицу пользовательских сценариев по всем ролям и их пересечениям, автоматизацию
ключевых сценариев («Cypress/Playwright — веб, Detox/Appium — мобильное»), полный regression на
staging, исследовательское тестирование людьми, не участвовавшими в разработке; проверки — «100 %
критичных сценариев (P0) автоматизированы и зелёные», «критичные дефекты закрыты, некритичные — в
бэклоге»; DoD — «система принята QA как release candidate (RC1), зафиксирован тег версии». Факты на
начало главы:
- бэклог `docs/requirements/BACKLOG.md` — 34 Must из 44 требований; трассировки «требование → тест» нет
  (`TRACEABILITY.md` — только «пункт ТЗ → ID бэклога»);
- Playwright: `web-engineer` — 2 теста, `web-admin` — 7, на стеке из образа-кандидата
  (`web-e2e.yml`, в `ci-gate` только Chromium); Flutter: `test_api_e2e` — 3 теста в CI (`mobile-e2e.yml`),
  `integration_test` — 3 теста только локально в iOS Simulator (`mobile/scripts/e2e_ui.sh`): на
  macOS-раннерах GitHub нет Docker (ADR 0022 п. 2); Detox/Appium отклонены в ADR 0022;
- сквозного прогона с интерфейсами нескольких ролей нет: наборы изолированы по приложениям, сторону
  сотрудника в мобильных тестах играют скрипты (`e2e_support.py`), сторону клиента в веб-тестах — API;
- без сквозного теста остаются C-10 (push о прошивке), E-04 и N-09 (карточка авто из тикета в
  интерфейсе не проверяется), E-05, X-02, X-04, N-01, N-08;
- **E-05 «Фиксация замены агрегата» (Must) не имеет интерфейса**: `replaceAggregateStatus` и
  `createMaintenanceRecord` вызывают только скрипты и тесты;
- staging-сервера нет до главы 26 (ADR 0008 п. 6): `cd-staging` публикует `backend:staging-<sha>` и
  артефакты `web-*-staging-<sha>`, но опубликованный образ после публикации ничем не проверяется;
- репозиторий публичный — минуты стандартных раннеров (в т. ч. macOS) бесплатны.

## Варианты
- **Матрица:** таблица в Markdown / YAML со стражем в CI.
- **Мобильная автоматизация:** Detox / Appium / Patrol / Flutter `integration_test`.
- **Мобильный UI в CI:** только локально / iOS Simulator на macOS-раннере (без Docker — стек негде
  поднять) / Android-эмулятор на ubuntu-раннере рядом со стеком.
- **Regression «на staging»:** повтор `ci.yml` / отдельный workflow по опубликованному digest.
- **Межролевые сценарии:** один тест с тремя интерфейсами (Playwright + Flutter одновременно) / две
  половины на одном стеке (веб + клиент по API; мобильный UI + сотрудник скриптом).
- **Исследовательское тестирование:** владелец + независимая агент-сессия / внешние люди / только агент.

## Решение
1. **Матрица (Q1).** `docs/specs/e2e_matrix.yaml`: сценарии `E2E-NN` — название, роли, приоритет
   P0/P1/P2, ID требований бэклога, уровни (`web`, `mobile-ui`, `mobile-api`, `backend`, `unit`,
   `widget`, `tokens`), ссылки на тесты `файл::имя теста`. Страж `scripts/check_e2e_matrix.py` в
   `docs-ci`: тест, на который ссылается сценарий, существует; каждое Must-требование покрыто хотя бы
   одним сценарием; у P0 есть ссылка уровня E2E; ID уникальны.
2. **Приоритет (Q2).** P0 — сбой блокирует основной путь роли или затрагивает безопасность и данные;
   P1 — важная функция с обходным путём; P2 — прочее. Каждый P0 — Must, не каждое Must — P0.
3. **Мобильная автоматизация (Q3) — отклонение от формулировки чек-листа.** Flutter `integration_test`
   (UI) и `test_api_e2e` (API) вместо Detox/Appium (Detox — для React Native, Appium дублирует
   `integration_test`; ADR 0022).
4. **Мобильный UI в CI (Q4, Q19).** P0 мобильного UI — на Android-эмуляторе ubuntu-раннера (KVM), стек
   backend на том же раннере, эмулятор ходит к нему по `10.0.2.2`. В `regression.yml` — всегда; в
   `ci-gate` — при изменениях `mobile/`. iOS Simulator — локальная часть regression перед RC1,
   реальный iPhone — приёмка (п. 13).
5. **Regression «на staging» (Q5, Q20).** `regression.yml`: ручной запуск с `git_sha` и вызов из
   `cd-staging` после публикации. Берёт опубликованный `backend:staging-<sha>` по digest и артефакты
   `web-*-staging-<sha>`; наборы — `e2e_backend` и аудит, Playwright (`web-engineer`, `web-admin`,
   `system-e2e`) в Chromium, Firefox и WebKit, `test_api_e2e`, мобильный UI на Android. Каждый набор —
   отдельный job со своим стеком из того же digest, своими данными и тестовыми номерами. В `ci-gate`
   на PR остаётся быстрый набор.
6. **«P0 зелёные» (Q6).** Три прогона `regression.yml` подряд на одном sha кандидата без падений,
   повторы Playwright выключены (`retries: 0`). Нестабильный P0 — дефект S2: чинится, а не перезапускается.
7. **Дефекты (Q7, Q21).** S1 — блокер (P0 не проходит, потеря данных, уязвимость); S2 — серьёзный (P1
   без обходного пути, нестабильный P0); S3 — некритичный; S4 — косметика. Критичные (S1, S2) — Issue
   и исправление в PR главы, повтор regression; S3/S4 — Issue с метками `bug` и `severity:S3`/`S4` в
   бэклоге, список — в отчёте и release notes. #73, #74 — S3.
8. **Межролевые сценарии (Q8).** Две половины на одном стеке: npm-workspace `system-e2e/` — Playwright
   открывает `web-engineer` и `web-admin`, клиент действует по API, как в E2E глав 21–22; клиентская
   половина — Flutter-тест, сотрудник — скрипт. В матрице у сценария обе ссылки. Данные —
   `backend/scripts/e2e_system.py seed` (каждый ответ сверяется с контрактом, как `e2e_backend.py`).
9. **Тег RC1 (Q9).** `v1.0.0-rc.1` на squash-коммите `develop` и GitHub pre-release с release notes
   (сценарии, открытые S3/S4, отклонения). `main` и production — глава 28.
10. **Глоссарий v1.15 (Q10).** «Критичный сценарий (P0)», «Критичный дефект», «Релиз-кандидат (RC)».
11. **Исследовательское тестирование (Q11) — отклонение (решение владельца, вариант «а»).** Людей вне
    разработки нет: владелец проводит 3–4 сессии по 30–45 минут по заданиям (клиент на iPhone,
    инженер, администратор, пересечения ролей); дополнительно — независимая агент-сессия «чёрный
    ящик» без доступа к коду и истории (только URL, тестовые аккаунты и задания). Проверка настоящими
    людьми — бета-пилот (глава 27).
12. **QA, принимающий RC1 (Q12) — владелец.** Приёмка — подписанный чек-лист в
    `docs/reviews/E2E_REGRESSION_23.md`: 3 зелёных regression, 0 открытых S1/S2, итоги исследовательского
    тестирования, затем тег.
13. **Глава 20 (Q13).** Три прогона клиентского сценария владельцем на iPhone (ADR 0024 п. 3) — часть
    приёмки RC1 на кандидате; после них глава 20 → DONE.
14. **E-05 (Q14) — дефект S1, исправляется в главе.** В `web-engineer` (`VehiclePanel`) у агрегата —
    «Зафиксировать замену / работу»: дата, пробег, комментарий; ошибки по коду контракта
    (`422 REPLACED_AT_IN_FUTURE`, `409 MILEAGE_AHEAD_OF_VEHICLE`); после сохранения обновляются статусы
    и история ТО. Контракт не меняется.
15. **Состав P0 (Q15).** 16 сценариев: E2E-01 SMS-вход, ПД, сессия, 429; E2E-02 авто по VIN → карточка
    → пробег; E2E-03 схема «светофор» = backend; E2E-04 обучение → дерево → эскалация → тикет с фото →
    чат; E2E-05 канбан → в работу → быстрый ответ → решено, клиент вживую; E2E-06 конфликт взятия;
    E2E-07 карточка авто из тикета (модель, прошивка на момент тикета, статусы); E2E-08 замена инженером
    → у клиента 🟢; E2E-09 регламент → статус без деплоя; E2E-10 статья → клиент видит; E2E-11 прошивка
    на модель X → уведомление клиенту X, не Y; E2E-12 напоминание о ТО в центре уведомлений; E2E-13
    пользователи (создание, переназначение, сброс пароля, блокировка → 401); E2E-14 дашборд =
    контрольный набор; E2E-15 вход по ролям во всех приложениях; E2E-16 главный межролевой (клиент →
    инженер: ответ и замена → клиент 🟢 → дашборд +1). P1 — видео, список обращений, несколько авто,
    новости и акции, фильтры канбана, тёмная тема, A-06/A-07, переоткрытие, просрочка SLA; P2 — Could.
16. **Must вне E2E (Q16).** X-04 (хэширование), N-01, N-02 (контраст), N-03, N-05, N-08 — в матрице с
    уровнем `unit`/`widget`/`tokens` и ссылками на существующие тесты; не P0. Uptime — главы 24 и 26.
17. **Реальные push и SMS (Q17).** В regression push проверяется до отправки (фейковый транспорт
    staging: outbox `sent` и запись в ленте); доставка на iPhone — глава 27 (ADR 0019 п. 20). Реальный
    SMS A1 — один ручной прогон по заданию (`scripts/a1_check.py`), не в CI.
18. **Граница с главой 25 (Q18).** В P0 — доступ по ролям и 401; IDOR, SQL-инъекции, XSS — глава 25
    (IDOR сейчас — pytest RBAC-04).

## Последствия
- Новые: `docs/specs/e2e_matrix.yaml`, `scripts/check_e2e_matrix.py` (в `docs-ci`), workspace
  `system-e2e/`, `backend/scripts/e2e_system.py`, `.github/workflows/regression.yml`, job мобильного UI на
  Android-эмуляторе; `cd-staging` вызывает regression после публикации.
- CI на PR с изменениями `mobile/` удлиняется на job Android-эмулятора (15–25 мин).
- `web-engineer` получает форму замены и работы по агрегату (E-05) без изменения контракта.
- Отклонения в `MASTER_CHECKLIST.md`: инструмент мобильной автоматизации (п. 3), исследовательское
  тестирование (п. 11), QA — владелец (п. 12).
- Отчёт главы — `docs/reviews/E2E_REGRESSION_23.md`; глоссарий — тег `requirements-baseline-v1.15`.
- Отложено: доставка push на iPhone и проверка людьми вне разработки (глава 27), IDOR и OWASP
  (глава 25), нагрузка и uptime (главы 24, 26).
