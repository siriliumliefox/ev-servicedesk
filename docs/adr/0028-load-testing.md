# 0028. Нагрузочное тестирование: целевая нагрузка и нормативы времени ответа, k6 на стенде из образа с ресурсами будущего сервера, параллельная отправка push

**Статус:** Принято, 2026-10-15 (Issue #116, grill-with-docs Q1–Q20; все рекомендации приняты владельцем)

## Контекст
Глава 24 требует определить целевые показатели («напр. 500 одновременных пользователей, 50 RPS»),
настроить инструмент (k6/JMeter/Locust), прогнать пиковый сценарий «push-рассылка + всплеск обращений к
Aggregates/Tickets», найти и устранить узкие места, повторить прогон со сравнением p95/p99 и error rate;
DoD — «система держит целевую нагрузку: error rate < 1 %, p95 latency в пределах SLA». Факты на начало
главы:
- в ТЗ нет требований ко времени ответа и числу пользователей — только uptime 99,5 % (раздел 7);
- «SLA» в глоссарии — срок решения тикета (глава 13, ADR 0017), а не время ответа API;
- staging-сервера нет до главы 26 (ADR 0008 п. 6); стенд главы 23 — `scripts/integration_stack.sh`
  из опубликованного образа в режиме `ENVIRONMENT=staging`;
- backend — один процесс uvicorn (`backend/Dockerfile`), синхронный SQLAlchemy с пулом по умолчанию
  (5 + 10 соединений, `app/core/db.py`); PostgreSQL с настройками по умолчанию;
- лимит WebSocket на пользователя (`ws_max_sockets_per_user`) считается в памяти процесса;
- worker уведомлений отправляет push последовательно: при ответе FCM ~100 мс рассылка на 10 000
  получателей занимает ~17 мин; аренда сообщений — `FOR UPDATE SKIP LOCKED`, копии worker совместимы;
  `FakePushSender` отвечает мгновенно;
- лимиты N-06 и WebSocket считаются по IP; k6 с одной машины — один IP;
- канбан инженера опрашивает API раз в 15 с (`web-engineer/src/board/boardData.ts`).

## Варианты
- **Норматив:** «SLA» с пометкой / «SLO» / отдельный термин «Норматив времени ответа».
- **Инструмент:** k6 / Locust / JMeter.
- **Стенд:** локальный с ограничением ресурсов / раннер GitHub / ждать сервер главы 26.
- **Вход нагрузочных пользователей:** SMS через отладочный маршрут / отключить лимиты / токены от сида.
- **IP пользователей:** медленный разгон / `X-Forwarded-For` за доверенным прокси / поднять лимиты.
- **Скорость рассылки:** параллельная отправка в процессе / копии worker / оба.
- **Если норматив не достигнут:** оптимизировать без границ / PARTIAL и решение владельца / ослабить сам.

## Решение
1. **Термины (Q1).** «Норматив времени ответа», «Целевая нагрузка», «Одновременный пользователь» —
   глоссарий v1.16. DoD главы читается как «p95 в пределах норматива времени ответа».
2. **Целевая нагрузка (Q2).** 500 одновременных пользователей (действие в среднем раз в 10 с) ≈ 50 RPS:
   85 % клиентов (главный экран, схема агрегатов, тикеты, уведомления, база знаний), 13 % инженеров
   (канбан с опросом раз в 15 с, карточка, чат, статусы), 2 % администраторов (дашборд, публикации).
   Пик — 150 RPS в течение 5 мин.
3. **Нормативы (Q3).** Чтение — p95 ≤ 300 мс, p99 ≤ 1 с; изменение данных — p95 ≤ 500 мс, p99 ≤ 1,5 с;
   сообщение чата доходит до второго участника по WebSocket за p95 ≤ 1 с. Ошибка — 5xx, тайм-аут
   (> 10 с) или неожиданный 4xx; ожидаемые `409` (одновременное взятие тикета) и `429` (сценарий
   лимитов) ошибками не считаются. Error rate < 1 % — на каждом этапе прогона. На пике 150 RPS —
   только error rate < 1 % и p99 ≤ 2 с.
4. **Инструмент (Q4).** k6 в Docker (`grafana/k6`, закреплён по digest); сценарии на JS в `load/`;
   пороги в сценарии дают «прошло / не прошло» и код выхода.
5. **Стенд (Q5, Q18).** `scripts/load_stack.sh` — обёртка над `integration_stack.sh` (режим `staging`,
   одноразовые секреты, удаление стека, проверка логов на утечку) с `docker-compose.load.yml`:
   backend 2 vCPU / 2 ГБ, PostgreSQL 2 vCPU / 2 ГБ, Redis 0,5 vCPU, worker уведомлений 0,5 vCPU,
   `analytics-worker` работает; k6 — вне ограничений. Образ — собранный из ветки тем же `Dockerfile`;
   после merge — контрольный прогон на опубликованном `backend:staging-<sha>` (status-PR). Полный
   прогон на сервере — глава 26.
6. **Данные (Q6).** `backend/scripts/seed_load.py` в разовом контейнере из того же образа: 10 000
   клиентов с авто, 20 000 тикетов за 2 года и 60 000 сообщений, 8 000 работ ТО, 30 000 доставок
   уведомлений, 200 статей, 20 инженеров, 3 администратора; у каждого клиента один push-токен.
   При `ENVIRONMENT=production` сид завершается с отказом.
7. **Вход (Q7).** Сид выпускает access- и refresh-токены подписью секрета стенда; лимиты — как в
   production; сценарий обновляет токены через `/auth/refresh` (access живёт 15 мин).
8. **IP (Q13).** uvicorn на стенде с `--forwarded-allow-ips` на адрес контейнера k6; каждый виртуальный
   пользователь шлёт свой `X-Forwarded-For` (10.x) — так проверяются лимиты production за прокси.
9. **Лимиты (Q14).** Отдельный сценарий параллельно с целевой нагрузкой: 31-й запрос SMS-кода с IP →
   `429 + Retry-After`, 61-е подключение WebSocket в минуту → `4429`, 21-й неверный вход сотрудника →
   `429`; у остальных пользователей нет `429` и ухудшения p95. SMS — `fake`, к A1 стенд не обращается.
10. **Пиковый сценарий (Q10, Q19).** 25 мин: 0–5 разгон до 500 пользователей; 5–10 целевая нагрузка и
    200 чатов WebSocket; на 10-й мин администратор публикует рассылку о прошивке всем 10 000 клиентам;
    10–15 всплеск ≈ 150 RPS — 20 % получателей открывают приложение (центр уведомлений, «прочитано»,
    схема агрегатов), 5 % создают тикет (каждый пятый — с фото ~500 КБ: presign → MinIO → привязка),
    инженеры разбирают очередь; 15–25 — 50 RPS, p95 возвращается в норматив за ≤ 2 мин.
11. **Эмуляция FCM (Q11).** `fake`-push получает настраиваемое поведение (запрещено в production):
    задержка 50–200 мс, 0,5 % «токен недействителен» (отзыв), 0,5 % временных ошибок (повтор).
12. **Доставка рассылки (Q12).** 10 000 получателей — не дольше 5 мин от публикации до последней
    доставки (с повторами) под пиковой нагрузкой. Worker отправляет параллельно пулом потоков (число —
    настройка, по умолчанию 16), одна копия; масштабирование копиями (`SKIP LOCKED`) — запас.
13. **Прогоны (Q15).** Замер по операциям — каждая 2 мин, 20 пользователей; смешанная нагрузка — 20 мин;
    пиковый сценарий; долгий прогон — 60 мин при целевой нагрузке, один раз на финальной версии.
    Финал: смешанная и пиковая — по 2 зелёных прогона подряд.
14. **Данные прогонов (Q16).** Итог k6 (JSON), `docker stats` раз в 5 с, топ-20 `pg_stat_statements`,
    журнал запросов > 100 мс, EXPLAIN тяжёлых запросов. В репозиторий — сжатые итоги в
    `docs/reviews/load/` и отчёт `docs/reviews/LOAD_TEST_24.md`; сырые данные — вне git. Grafana и
    InfluxDB — глава 26.
15. **Разрешённые оптимизации (Q9, Q20).** Базовый прогон — как есть. Далее: число процессов uvicorn
    через `WEB_CONCURRENCY` (по умолчанию 2), размер пула SQLAlchemy из настроек, индексы через Alembic,
    запросы (N+1, `selectinload`), настройки PostgreSQL под 2 ГБ (`shared_buffers` 512 МБ,
    `effective_cache_size` 1,5 ГБ, `work_mem`, `max_connections` = процессы × пул + worker'ы + запас) —
    обязательное требование к production главы 26. Лимит WebSocket на пользователя переносится в Redis
    (атомарный счётчик с TTL), чтобы не умножаться на число процессов.
16. **Защита от регресса (Q8).** В `backend-ci` — тесты EXPLAIN для найденных тяжёлых запросов на
    данных объёма п. 6 (нет Seq Scan по большим таблицам), по образцу ADR 0020 п. 10;
    `.github/workflows/load.yml` — ручной запуск, облегчённый профиль (50 пользователей, 3 мин, те же
    пороги), в `ci-gate` не входит. Ночные прогоны — после главы 26.
17. **Если норматив не достигнут (Q17).** Фиксируется фактическая ёмкость, глава — PARTIAL, решение
    принимает владелец (ресурсы главы 26 или пересмотр нормативов); агент нормативы не меняет.
