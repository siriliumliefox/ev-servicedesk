# Выкладка и план отката

ADR 0030 пп. 7, 8, 16. Выпуск = digest образа backend (`backend:staging-<sha>`) + статика кабинетов того же
sha + ревизия Alembic. Конфигурации ВМ (`deploy/`) — из того же коммита.

## Как выкладывается
- **staging** — каждый push в `develop` (`cd-staging.yml` → `deploy-server.yml`): сборка и проверки образа
  (smoke, интеграционный стек, страж отката), затем `ssh deploy@<ВМ> deploy staging < bundle`.
- **production** — release-PR `develop → main` (merge-коммит) → `cd-production.yml`: проверка, что
  cd-staging этого коммита успешен (включая regression), сборка статики под production, **Approve
  владельца**, выкладка, теги `production` и `production-<sha>`.
- На ВМ `deploy.sh`: миграции **до** переключения (провал — работающий выпуск не тронут) → `current` →
  новый выпуск → `up -d` → health и smoke через nginx (`/health`, `401` без токена, `/metrics` закрыт,
  кабинеты с CSP и HSTS). Провал — **автооткат** на предыдущий выпуск (второй перезапуск контейнера при
  старте — отказ сразу, без ожидания тайм-аута).

## Правило миграций (expand → contract)
Миграция выпуска N+1 совместима с кодом выпуска N: добавлять столбцы и таблицы (nullable или с default),
не переименовывать и не удалять то, что читает N. Удаление — следующим выпуском (contract), когда N уже не
нужен для отката. Страж — `scripts/rollback_compat.sh` в cd-staging: текущий `backend:staging` стартует на
схеме кандидата, ORM читает все таблицы, аудит целостности проходит. FAIL — миграция несовместима: в PR
пометка «откат требует downgrade», `alembic downgrade` проверен в backend-ci.

## Откат
| Ситуация | Действие | Время (стенд) |
|---|---|---|
| health или smoke после выкладки не прошли | автоматически `deploy.sh` | 20 с от выкладки до работающего предыдущего выпуска |
| critical-алерт в течение 30 мин после релиза | `ssh deploy@<ВМ> rollback <env>` (предыдущий) | 11 с |
| откат на конкретный выпуск (из последних 5) | `ssh deploy@<ВМ> rollback <env> <sha>`; staging — `scripts/rollback-staging.sh <sha>`; production — cd-production, ручной запуск с `rollback_sha` | 11 с |
| миграция несовместима (страж FAIL был принят) | `docker compose … run --rm migrate alembic downgrade <ревизия>` предыдущего выпуска, затем откат образа | минуты |
| данные испорчены релизом | PITR на момент до релиза — [RESTORE.md](RESTORE.md) (`--time`) | ≤ 2 ч |

Откат не меняет секреты и не трогает данные; статика кабинетов переключается symlink на выпуск.
Наблюдение учения (стенд, 2026-10-19): access-токены, выданные выпуском до главы 25, после обновления
не принимаются (обязательный `iat_ms`) — клиенты один раз обновляют пару по refresh-токену.

## Учение (ADR 0030 п. 22)
`scripts/infra_stack.sh drill-rollback` (стенд) и workflow `infra-drill.yml` (раз в неделю): N → N+1 с
миграциями → откат на N без downgrade → снова N+1 → выпуск с неверными настройками (отклонён миграциями)
→ выпуск без бакета S3 (автооткат). Итоги — `docs/reviews/PRODUCTION_INFRA_26.md`.
