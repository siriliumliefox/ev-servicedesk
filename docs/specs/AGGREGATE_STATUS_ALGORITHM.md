# Спецификация: статус агрегата «светофор» и регламенты ТО

**Глава 5** (`MASTER_CHECKLIST.md`), Issue #31, ADR [0009](../adr/0009-aggregate-status-thresholds.md).
Требования: ТЗ §5, C-04, C-05, E-05, A-01, N-10. Контракт: `docs/openapi.yaml` — тег `Aggregates`
(`AggregateStatus`, `listAggregateStatuses`, `replaceAggregateStatus`, регламенты, пороги).
Реализация сервиса — глава 12; эта спецификация — единственный источник правил расчёта.

## 1. Термины и входные данные

| Вход | Источник | Примечание |
|---|---|---|
| `current_mileage` | `vehicle.mileage` | целое ≥ 0, монотонен, уменьшается только корректировкой (ADR 0006) |
| `today` | дата «сегодня» в часовом поясе сервиса `Europe/Minsk` | передаётся в функцию параметром — расчёт детерминирован |
| регламент | активная строка `maintenance_regulation` для (`vehicle.vehicle_model_id`, агрегат) | `interval_km` и/или `interval_months` (хотя бы одно, оба > 0) |
| последняя замена | `vehicle_aggregate_status` (`last_replaced_at`, `last_replaced_mileage`) | строки может не быть |
| пороги | `aggregate_status_thresholds` (одна строка, ADR 0009) | `yellow_from_percent` (по умолчанию 70), `red_above_percent` (по умолчанию 100) |

**Регламент ТО** — данные, не код: пара «модель авто + тип агрегата» → интервал. Типы агрегатов —
расширяемый справочник `aggregate_type` (A-07). Изменение регламента не редактирует строку: старая версия
архивируется (`is_archived = true`), создаётся новая (`reviseMaintenanceRegulation`); активная версия на пару
одна (`uq_maintenance_regulation_active`). Масляный фильтр — отдельный регламент: администратор задаёт ему
тот же интервал, что у масла двигателя; связи между регламентами в схеме нет (решение владельца, 2026-10-10).
Фреон — регламент по `interval_months` («по году последней заправки»).

## 2. Алгоритм

Статус вычисляется при каждом запросе и **не хранится**: смена регламента или порогов сразу меняет статусы.

### 2.1. Какие агрегаты возвращаются
В `listAggregateStatuses` попадает агрегат, только если у модели авто есть **активный** регламент на него.
Нет регламента (не задан или архивирован без замены) → агрегат не отслеживается и в ответ не входит.
Порядок — по `aggregate_type.id`.

### 2.2. Составляющие выработки
Каждая составляющая считается, только если заданы и интервал, и нужное значение последней замены.

**По пробегу** (`interval_km` и `last_replaced_mileage` не NULL):
```
used_km      = max(0, current_mileage − last_replaced_mileage)
p_km         = 100 · used_km / interval_km
remaining_km = interval_km − used_km            # < 0 — перепробег
```

**По времени** (`interval_months` и `last_replaced_at` не NULL):
```
due_date       = last_replaced_at + interval_months календарных месяцев
                 (день месяца ограничивается последним днём: 31.01 + 1 мес = 28.02 / 29.02)
elapsed_days   = max(0, today − last_replaced_at)
p_time         = 100 · elapsed_days / (due_date − last_replaced_at)
remaining_days = due_date − today               # < 0 — просрочено
```

### 2.3. Итог
```
нет ни одной составляющей → status = unknown, percentage = remaining_km = remaining_days = null
иначе p = max(p_km, p_time)                     # худший из двух интервалов
    p <  yellow_from_percent                    → green
    yellow_from_percent ≤ p ≤ red_above_percent → yellow
    p >  red_above_percent                      → red
```
- Сравнение **точное**: `p` — рациональное число (`fractions.Fraction`/целочисленная арифметика), без
  округления и без `float`. Ровно 70% — `yellow`, ровно 100% — `yellow`, 100,01% — `red`.
- `percentage` в ответе = `p`, усечённое (вниз) до 0,1. Усечение не даёт зелёному показать «70.0», но
  красный в диапазоне (100; 100,1) показывается как «100.0» — **цвет определяет только `status`**.
- `remaining_km` / `remaining_days` возвращаются независимо (null, если составляющей нет) — для карточки
  агрегата (C-05) и push «за N км/дней до порога» (N-10, глава 15).

## 3. Пограничные случаи

| # | Случай | Правило |
|---|---|---|
| E1 | Новый авто без истории замен (нет строки `vehicle_aggregate_status`) | `unknown` — не ошибка, HTTP 200. Отсчёт «от нуля» не применяется: дата и пробег последней замены неизвестны |
| E2 | Известна только дата или только пробег, а регламент — по другой величине | составляющей нет → если других нет, `unknown` |
| E3 | Пробег исправлен вниз ниже `last_replaced_mileage` (ADR 0006) | `used_km = 0` (не отрицательный %); корректные данные восстанавливаются новой фиксацией замены |
| E4 | `last_replaced_at` позже `today` | `elapsed_days = 0`; API замены такую дату не принимает (§4) — случай возможен только при сдвиге часового пояса/ручной правке |
| E5 | Несколько замен подряд | текущей становится замена с наибольшей `replaced_at`, при равной дате — последняя зафиксированная; история (`maintenance_record`) хранит все |
| E6 | Замена внесена задним числом (дата раньше текущей последней) | только запись в историю; `vehicle_aggregate_status` не меняется |
| E7 | Замена в тот же день, что и предыдущая | становится текущей (§E5) → обычно 0%, `green` |
| E8 | Регламент пересмотрен | статус сразу считается по новой активной версии; история замен не меняется |
| E9 | Регламент архивирован без замены | агрегат пропадает из `listAggregateStatuses` (§2.1); история замен сохраняется |
| E10 | Администратор изменил пороги | применяются ко всем статусам сразу; прошлые статусы не хранятся и не пересчитываются |
| E11 | Конец месяца в `interval_months` | 31.01 + 1 мес = 28.02 (29.02 в високосный год), §2.2 |
| E12 | Авто удалено (`deleted_at`) | статусы не запрашиваются (404 на уровне Vehicle Service, глава 11) |

## 4. Требования к сервису (глава 12)

1. Функция расчёта — чистая доменная функция (`backend/app/domain/aggregates/`), без БД и HTTP;
   сервис загружает входы и вызывает её.
2. `replaceAggregateStatus`:
   - `replaced_at > today` → `422`;
   - `mileage_at_replacement > vehicle.mileage` → `409` (сначала обновить пробег, `updateVehicleMileage`);
   - всегда создаёт `maintenance_record`; `vehicle_aggregate_status` обновляет по правилу E5/E6
     в одной транзакции с блокировкой строки статуса.
3. Пороги — `GET/PUT /aggregate-status-thresholds` (ADR 0009), валидация
   `1 ≤ yellow_from_percent < red_above_percent ≤ 200`.
4. Модульные тесты — все сценарии §5 (DoD главы 12: ≥ 90% сценариев главы 5).
